## Current engine asks

- **No public way to persist or drain in-flight human commands, so a save in the ≤1-tick window before an early return drops them (surfaced 2026-07-11, full-review M4).** aoe2 human orders go through `world.submitWithResult(type, data)`, which validates AND enqueues to the engine's TRANSIENT `commandQueue` (a plain array on `World`, not part of `world.state`, so it is not serialized). The AI path avoids this by staging into aoe2's own Tier-3-persisted `pendingCommands`, but the human facades cannot: they need the SYNCHRONOUS accept/reject that `submitWithResult` returns (to drive the HUD's rejection toasts), and there is no public validate-without-enqueue — `world.validateCommand` is PRIVATE. So a human order issued in the tick before the game-menu auto-pause (which returns from `bridge.step` before `world.step()`/`processCommands` runs) is lost when Save serializes a world whose engine queue is omitted. Both clean fixes need an engine API aoe2 lacks and may not add itself: **(a)** a PUBLIC synchronous command-validate (so aoe2 can validate for the toast, then stage into its own persisted queue), OR **(b)** a PUBLIC `processCommands`/queue-drain (both are `protected` on `World`; the only public drain is a full `world.step()`, which would advance a tick at save time). **Ask:** expose either a public `validateCommand`-style precheck OR a public queue-peek/drain, so in-flight human commands can be persisted or flushed at save time without a tick advance. Narrow, low-consequence today (one dropped command in a rare ≤1-tick + menu-open window; no crash/corruption), so deferred; recorded here per the report-don't-modify-engine policy.
- **A* has no position-stable tie-break, so an equal-cost route recomputed from a different start cell can pick different intermediate cells (surfaced 2026-07-11, full-review H5).** `civ-engine/src/pathfinding.ts` orders the open set on `f` only (no secondary key on `h`/`g`/node hash) and admits a predecessor on strict `newG < prevG` (first-reach-wins), so among equal-cost 4-connected shortest paths the chosen route depends on the START node's expansion order. aoe2's bridge-side `movePathCache` is transient (not serialized), so on save/load and on `SessionReplayer.openAt` (which re-sims from the nearest 1000-tick snapshot with an EMPTY cache) a unit mid-non-straight-move recomputes a possibly-different equal-cost route than the live run committed — a transient, same-destination, intermediate-cell-only divergence that `selfCheck` structurally misses (it compares serialized state at boundaries, which excludes the cache, and routes that re-converge before the next boundary leave identical state). Proven by explicit trace: ordered (0,0)→(2,2), standing on (0,1), the committed route's next cell is (1,1) but a fresh recompute yields (0,2). **Ask:** add a position-stable secondary tie-break (e.g. break equal-`f` by `h`, then by a deterministic node hash) so a recompute from any node on a path reproduces that path's suffix — making the cache a provably pure memoization and closing the divergence for BOTH replay and save/load with no save-format change. aoe2 cannot fix this cleanly on its own (a cache codec is a save-format change; a snapshot-boundary cache reset is replay-only and couples the sim to the recorder cadence), and per policy does not modify `civ-engine` directly.
- **Terrain surfaces are per-cell voxel columns, so coastlines and kind seams cannot curve at the geometry level (observed 2026-08-17, terrain-colour/surf work).** The terrain chunk contract (`DensePaletteChunk` + `meshVisibleFaces`) gives each cell one palette entry and axis-aligned cube faces; there is no sub-cell surface tint gradient or non-cube shore meshing (marching-squares/dual-contour style). aoe2 approximates the user-requested soft boundaries render-side in v0.3.12 — per-cell colour fields (patch noise, shallow-water band, cross-kind blends) plus a connected instanced-box surf curve — which reads well but keeps the underlying colour seam square at cell resolution. **Ask (low priority, no blocker):** a sub-cell terrain surface contract (per-vertex/corner palette blending on the chunk top face, or a shore-profile mesh hook) would let waterlines and terrain transitions curve in geometry rather than by overlay. Recorded per the report-don't-modify-engine policy; the current render-side approximation is shippable.
- Engine 1.5.0/1.6.0 (visual runner hardening + improvement-loop contract completion) adopted cleanly on 2026-07-08: `minimalImprovementFindingSchemaVersion` keeps aoe2's v1-vocabulary payloads stamping schema version 1, `createImprovementRunManifest`/`assertImprovementRunManifest` back the new `playtest:recursive` pass manifests, and the strict `requireVerificationEvidence` mode guards the verified-by-metric upgrade. Two adoption notes, no asks: the widened `ImprovementNextAction` union broke a local exhaustiveness `never` guard (expected consequence of input-vocabulary widening — handled), and the constant bump flipped two local schema-version pins until minimal stamping was adopted (the engine's changelog migration note called this exactly).
- The earlier `SessionRecorder` / `SessionReplayer` `TComponents`/`TState` generics ask is RESOLVED (engine 1.2.0) **and now adopted here** — the `toEngineWorld`/`fromEngineWorld` recorder/replayer cast seam was removed and a component-typed `GameWorld` flows through recording and replay by inference (history in [past.md](./past.md)). `toEngineWorld` survives only at the `WorldDebugger` / `RenderAdapter` boundary, which 1.2.0 did not thread (those classes still take a default-generic `World<TEventMap, TCommandMap>`, and `World`'s `TComponents` is invariant).
- The previous occupancy/crowding concerns have moved to [past.md](./past.md).
- Why they moved: `civ-engine` now ships a higher-level `OccupancyBinding`, measurable occupancy scan counters, and blocker metadata that closed the earlier FU8 revisit conditions.

- **A voxel chunk's vertical step is one whole tile, so raised terrain can only be a mesa (measured 2026-08-23, raised-terrain presentation).** `VoxelChunkV1` carries `origin: Int3V1` and `size: Int3V1` with an implicit unit-size voxel and no per-chunk scale or transform, so a terrain chunk's Y resolution is exactly its X/Z resolution: one elevation level is one tile tall. AoE2's elevation step is a fraction of a tile — a hill is a slope you read at a glance and shoot down from, not a cliff. aoe2's data path for elevation is already proved end to end (the projector stamps `terrain.elevation` on every entity, the chunk builder fills the column from y=0, and units and trees already stand ON a raised tile rather than inside it), so the only thing between the current flat map and raised terrain is the vertical granularity of the chunk lane. The instance-batch lane does take float positions and sizes, but covering a whole map's raised surface with instanced boxes trades a dense-meshed chunk for thousands of parts, which is the wrong shape for terrain. **Ask:** either a per-chunk scale or non-uniform voxel extent on `VoxelChunkV1` (a `voxelExtent: Vec3V1`, defaulting to 1,1,1, would do it and keeps `origin` integral in chunk space), or a fractional-Y origin. Recorded per the report-don't-modify-engine policy; aoe2 conveys elevation by shading in the meantime, which reads as high ground but has no geometry.
