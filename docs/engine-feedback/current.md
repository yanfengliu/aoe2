## Current engine asks

- M8 reader work assigned, 2026-10-02 UTC: engine_reader_contract_audit owns the fixed64KiB incremental reader and physical-tail corruption tests; engine_m2_acceptance independently reviews parsing order, UTF8 and descriptor/error contracts. - **Every component write deep-walks the component to assert JSON compatibility, with no way to turn it off — measured at ~10% of late-game tick time (surfaced 2026-09-01, engine 2.4.1).** `ComponentStore.set` calls `assertJsonCompatible(component)` on EVERY write in the default `strict` diffMode (and `jsonFingerprint`, another full walk, in `semantic`). `assertJsonCompatible` allocates a fresh `WeakSet` per call and recursively visits every field of the component. There is no opt-out: no `NODE_ENV` gate, no constructor option, no sampling — `grep -rln "skipValidation|validateComponents|NODE_ENV" dist/*.js` returns nothing. **Measured**, CPU profile of `default-seed` self-play warmed 33,000 ticks (55 units, 50 buildings, 8.48 ms/tick): `visit @ json.js` **8.2% self time**, plus `jsonFingerprint` 1.5% and GC 1.8%. The writes driving it are legitimate, not aoe2 waste — instrumenting `world.setComponent` over 300 late-game ticks counted **43.5 writes/tick (42.2 of them `unitTransform`) of which only 0.2% were redundant** (value identical to what was stored), i.e. 0.77 writes per unit per tick for units that move every tick. So aoe2 cannot buy this back by writing less. **Ask:** a way to disable or sample the JSON-compatibility assertion once a build is past development — an explicit opt-out or sampling policy with unchanged safe defaults and invalid-value/serialization controls; first-write-per-type validation alone does not protect later values. A correctness assertion of this value is worth paying during development and is pure overhead in a shipped match. Recorded per the report-don't-modify-engine policy.
- **`buildDiff()` runs unconditionally inside `world-tick`, so headless runs pay for a diff even without a renderer (surfaced 2026-09-01, engine 2.4.1).** `world-tick.js:131` calls `this.buildDiff()` in every tick with no consumer check; it then iterates every component store's dirty set plus tag and meta diffs. Profiled at **2.2% `buildDiff` + 1.2% `buildSnapshot`** in the same headless self-play run above. These are historical renderer-free measurements; `SessionRecorder` still consumes `onDiff` when attached, so recording is a diff consumer even in a headless run. **Ask (lower priority than the above):** skip or lazily build the diff only when no consumer needs it, including recorder, debugger and subscriptions; any opt-out must preserve their recording, failure and metrics contracts. Renderer absence alone is insufficient. Recorded per the report-don't-modify-engine policy.
- **No public way to persist or drain in-flight human commands, so a save in the ≤1-tick window before an early return drops them (surfaced 2026-07-11, full-review M4).** aoe2 human orders go through `world.submitWithResult(type, data)`, which validates AND enqueues to the engine's TRANSIENT `commandQueue` (a plain array on `World`, not part of `world.state`, so it is not serialized). The AI path avoids this by staging into aoe2's own Tier-3-persisted `pendingCommands`, but the human facades cannot: they need the SYNCHRONOUS accept/reject that `submitWithResult` returns (to drive the HUD's rejection toasts), and there is no public validate-without-enqueue — `world.validateCommand` is PRIVATE. So a human order issued in the tick before the game-menu auto-pause (which returns from `bridge.step` before `world.step()`/`processCommands` runs) is lost when Save serializes a world whose engine queue is omitted. Both clean fixes need an engine API aoe2 lacks and may not add itself: **(a)** a PUBLIC synchronous command-validate (so aoe2 can validate for the toast, then stage into its own persisted queue), OR **(b)** a PUBLIC `processCommands`/queue-drain (both are `protected` on `World`; the only public drain is a full `world.step()`, which would advance a tick at save time). **Ask:** expose either a public `validateCommand`-style precheck OR a public queue-peek/drain, so in-flight human commands can be persisted or flushed at save time without a tick advance. Narrow, low-consequence today (one dropped command in a rare ≤1-tick + menu-open window; no crash/corruption), so deferred; recorded here per the report-don't-modify-engine policy.
- **A* has no position-stable tie-break, so an equal-cost route recomputed from a different start cell can pick different intermediate cells (surfaced 2026-07-11, full-review H5).** `civ-engine/src/pathfinding.ts` orders the open set on `f` only (no secondary key on `h`/`g`/node hash) and admits a predecessor on strict `newG < prevG` (first-reach-wins), so among equal-cost 4-connected shortest paths the chosen route depends on the START node's expansion order. In the historical reproduction reported here, aoe2's bridge-side `movePathCache` is transient (not serialized), so on save/load and on `SessionReplayer.openAt` (which re-sims from the nearest 1000-tick snapshot with an EMPTY cache) a unit mid-non-straight-move recomputes a possibly-different equal-cost route than the live run committed — a transient, same-destination, intermediate-cell-only divergence that `selfCheck` structurally misses (it compares serialized state at boundaries, which excludes the cache, and routes that re-converge before the next boundary leave identical state). Proven by explicit trace: ordered (0,0)→(2,2), standing on (0,1), the committed route's next cell is (1,1) but a fresh recompute yields (0,2). **Ask:** investigate route selection that reproduces a chosen path's suffix under explicitly stated graph, cost and passability assumptions. An `h`/node-hash tie-break is a candidate, not a proved guarantee for weighted or directed graphs, cold starts or changing occupancy. Work 107 separately prepares a game-owned chosen-route persistence repair; its acceptance does not prove general suffix stability or cache purity. This engine property remains open, and per policy aoe2 does not modify `civ-engine` directly.
- **Dense terrain chunks use per-cell voxel columns; curved geometry needs consumer proof (observed 2026-08-17, terrain-colour/surf work).** The terrain chunk contract (`DensePaletteChunk` + `meshVisibleFaces`) gives each cell one palette entry and axis-aligned cube faces; there is no sub-cell surface tint gradient or non-cube shore meshing (marching-squares/dual-contour style). aoe2 approximates the user-requested soft boundaries render-side in v0.3.12 — per-cell colour fields (patch noise, shallow-water band, cross-kind blends) plus a connected instanced-box surf curve — which reads well but keeps the underlying colour seam square at cell resolution. **Fresh source audit:** public `GeometryResourceV1` already accepts positions, normals, vertex colors and indices, and the aoe2 adapter advertises geometry resources. **Ask (low priority, no blocker):** first prove that existing lane through the actual terrain presentation path, including curved seams, adjacent chunks, normals/colors and picking; request a top-surface or shore-profile hook only for a demonstrated remaining gap. Consumer proof and adoption remain open. Recorded per the report-don't-modify-engine policy; the current render-side approximation is shippable.
- **No occupancy claim that reserves a cell for PLACEMENT while admitting MOVEMENT, so a walkable structure has to be held outside the engine (surfaced 2026-09-10, engine 2.4.1).** `OccupancyBinding.occupy(entity, area, { metadata: { kind } })` records ONE kind of claim: the cell is taken, and the engine's sub-cell grid then refuses a unit slot on it (`occupancy-cell-grid.isBlocked`). Age of Empires II's Farm needs exactly the other half of that pair — the ground is walkable by every land unit of every player, and nothing may be BUILT on it — and the Fish Trap is the same question on the water domain. There is no way to say it to the engine: a claim blocks both questions or neither, and `metadata.kind` is carried but not consulted by `isBlocked`. Flipping only aoe2's passability predicate does not work, and the failure is silent rather than loud: units route ONTO the farm and are then refused a slot there, so they stack as overflow on a neighbour — measured on the showcase fixture as `slot undefined,undefined overflow true` for a villager standing on its own farm cell. So v0.3.221 records a farm's footprint on aoe2's side only (`passableStructures.ts`, `worldOccupancyCells.blocksWholeCell`), which means the engine's grid does not know the cell is spoken for and aoe2 keeps a second list that has to agree with the first. **Ask:** a flag on `occupy` — `{ blocksMovement: false }`, or an `isBlocked` that consults `metadata.kind` against a caller-supplied set — so a cell can be reserved against further claims while still admitting unit slots, with the sub-cell allocator honouring it. Recorded per the report-don't-modify-engine policy; the aoe2-side split is shippable and is what v0.3.221 ships.

- **Fractional terrain height needs consumer proof; per-chunk extent remains absent (measured 2026-08-23, raised-terrain presentation).** `VoxelChunkV1` carries integral chunk-space origin/size and no per-chunk extent. The public scene coordinate convention already supplies non-uniform `worldUnitsPerVoxel`; the chunk presenter scales vertices, bounds and origin, so fractional world-space Y is an existing capability. The aoe2 adapter currently emits unit scale and deliberately keeps standalone terrain input at elevation zero. This corrects the original unit-size limitation claim; actual consumer adoption is not proved here. AoE2's elevation step is a fraction of a tile — a hill is a slope you read at a glance and shoot down from, not a cliff. The original raised-terrain investigation reported aoe2's data path for elevation as proved end to end (the projector stamps `terrain.elevation` on every entity, the chunk builder fills the column from y=0, and units and trees already stand ON a raised tile rather than inside it), but that historical proof does not establish current quarter-height bounds, public ray picking or float-positioned entity-ground contact. The instance-batch lane does take float positions and sizes, but covering a whole map's raised surface with instanced boxes trades a dense-meshed chunk for thousands of parts, which is the wrong shape for terrain. **Ask:** prove quarter-height terrain through the existing global scale on the pinned consumer, including cell-world bounds, public ray picking and entity-ground contact. Keep a per-chunk extent/scale or fractional-origin request only if that proof exposes a remaining requirement; no retirement or adoption is claimed. Recorded per the report-don't-modify-engine policy; aoe2 conveys elevation by shading in the meantime, which reads as high ground but has no geometry.

- **Single-layer transparency is implemented in the engine and unreachable from `voxel/three`'s public surface (measured 2026-08-30, behind-building silhouette).** A translucent instanced part that overlaps ITSELF blends twice. The behind-building silhouette mirrors a unit's own posed parts, and a villager overlaps itself in several places — belt inside tunic, apron coplanar with the tunic face, hair over the head's crown, arms rolled into shoulders. Solved per-pixel from three captures (background, opaque, translucent) at 0.55 declared opacity: 452 pixels at 0.55, **68 at 0.7975 (= 1−0.45², two blends)** and **6 at 0.9089 (= 1−0.45³, three)** — an exact match for multi-layer compositing, and about 14% of the body area drawing at the wrong opacity, visible as seams down one arm, streaks on the torso and bands across the boots. Two units behind one building are the same batch and hit it the same way. The cause is `transparent: true` with three's default `depthWrite: true`, plus instance ordering by key STRING rather than by depth. **The engine has a restricted nearest-depth technique** — `markSingleLayerTransparencyInternal` / `createSingleLayerDepthPrepassInternal` in `voxel/src/three/singleLayerTransparencyInternal.ts`, whose own header describes the overlap artefact but explicitly permits double blending at exact coplanar ties and excludes chunk/paged lanes without a companion prepass — but it is reachable only through `THREE_MATERIAL_DECORATOR_INTERNAL`, which `voxel/three`'s index does not export. **Ask:** a safe public material/lane contract for the actual posed-body consumer, with exact coplanar ties, supported presenter lanes, opaque occlusion, intentional two passes and borrowed GL state/buffers proved. A bare export of the internal decorator is insufficient; no robust public capability is claimed. **Updated 2026-09-06 (v0.3.216): the silhouette is no longer opaque, so this ask is now load-bearing rather than hypothetical.** It moved to the translucent `memory` lane and is drawn in TWO coincident passes on purpose (one 0.5 pass cancels against a complementary background — measured: a blue silhouette's head over an orange sunlit roof composited to a grey-mauve). Every part is therefore laid down twice, so wherever a part overlaps ITSELF the extra blending described above is doubled along with everything else. Not re-measured at two passes; the per-pixel census above is the 2026-08-30 single-pass one. Recorded per the report-don't-modify-engine policy.

Recorded per the report-don't-modify-engine policy.

- **A vision source can only stand on a whole cell, so a building whose footprint is an even size needs four sources to see from its middle (surfaced 2026-09-24, engine 2.4.1).** `VisibilityMap.setSource` asserts integer `x`/`y` (`assertGridPoint`, `src/visibility-map.ts:314`) and lights a cell when `(x - sx)^2 + (y - sy)^2 <= radius^2`. A 2x2 or 4x4 building's centre is a cell corner, which no source can stand on, and Definitive Edition measures a building's sight from its centre. aoe2 now expresses it as four sources on the four central cells with one radius whose union is exactly the centred circle (`src/game/simulation/buildingVisionSources.ts`, exact to a sight of 22), keyed `id`, `id:1`, `id:2`, `id:3`. It works, but it costs four times the loop work of one circle (3.2-3.6 times the lit cells at sights 6-11) for every House, camp, Mill, Monastery, University, Market, Town Center, Castle and Wonder on every recompute of its layer (next item), and it made the sync keep a per-entity source count so an owner flip, a destruction or a recycled id removes all four. **Ask:** a fractional source centre (accept `x + 0.5`), or a rectangle source that lights the circle around a footprint's centre. Either would make each building one source again. Recorded per the report-don't-modify-engine policy.
- **A player's whole visible set is re-stamped from every source whenever any one source changes, so a static building pays on every tick a unit moves (surfaced 2026-09-24, engine 2.4.1).** `update()` recomputes each dirty player with `computeVisible(player.sources)` (`src/visibility-map.ts:104-121`), which sorts all the player's sources and stamps every circle into a fresh `Set`. A unit moves almost every tick, so the player is dirty almost every tick, and its buildings — which never move — are stamped again each time. Measured when every aoe2 building gained sight (2026-09-24): 96% of `computeVisible`'s time is its own stamping loop (the sort is about 4%). AI self-play does not show the cost, because the AI never researches Town Watch or Town Patrol. A human base with both (+8 on every wall, Farm and House; 277 sources) took up to 9.2 ms a recompute against 0.54 ms before, and a fight's ticks peaked at 6.4 ms of recompute. aoe2 works around it by holding each owner's buildings under a second engine player (`src/game/simulation/bridge/layeredVisibilityMap.ts`, a `VisibilityMap` subclass over two engine maps that answers every sight question asked with an owner's id from both), which brought the fight back to what it cost before the change. Holding the second map's state cost more work: carried in the per-tick visibility slot it made the 20,000-tick boot-map bundle 351.3 MB against 284.6 MB, and every tick's state fingerprinting slower (next item but one), so aoe2 writes it to a slot of its own, holding only the explored cells no unit of the owner has explored and written only when that changes (`src/game/simulation/bridge/visibilitySlots.ts`). **Ask:** incremental visibility (a per-cell count of the sources that light it, so adding, moving or removing one source touches only that source's cells), which would remove both the recompute cost and the second map; failing that, a first-class static layer per player whose explored cells are not stored twice. Recorded per the report-don't-modify-engine policy.
- **`getState` sorts every player's sources and explored cells on every call, and in a world that grew live that is a full sort each time (surfaced 2026-09-24, engine 2.4.1).** `getState` spreads each player's source map and explored set and sorts both (`src/visibility-map.ts:161-180`); the source sort goes through `compareByNormalizedKey`, which builds two strings per comparison. aoe2 writes the map's state into the world on every tick a source changes, which in play is nearly every tick. In a live world the sets are in insertion order, so each call sorts from scratch: on the boot map at tick 30,000, `getState` was 3.8% of CPU. The same world loaded from a save paid 0.9% over the next 2,000 ticks, because `fromState` refills the sets in sorted order and the sort then meets sorted input. Found by an A/B that loaded one saved world into both arms (`scripts/profile-selfplay.mjs --load`). **Ask:** keep each player's explored cells in index order (a bitmap per player, or a sorted array kept on insert), and cache a player's serialized entry until it changes. Recorded per the report-don't-modify-engine policy.
- **World-state fingerprints scan unchanged slots at separate tick phases, so a tick pays for stored state (surfaced 2026-09-25, engine 2.4.1).** `clearStateDirty` establishes the baseline at tick start; `getStateDirty` fingerprints slots not already marked dirty at diff time, to catch a value changed in place (`src/world-tick.ts:266-299`; `jsonFingerprint` walks the whole value). Dirty-marked slots skip the second walk. These scans have different temporal roles; similar code does not make them interchangeable. A slot that never changes is walked twice on every tick of the match. On aoe2's boot map at tick 30,000, 52 KB of state, the two cost 1.3 s over 2,000 ticks, about 0.65 ms a tick of 6. It is why aoe2 keeps its static building sight out of the per-tick visibility slot and out of state it could rebuild (`src/game/simulation/bridge/visibilitySlots.ts`): kept whole it cost about +0.27 ms a tick in these two functions. Found by the same one-world A/B as the previous item. **Ask:** trust `setState` for dirtiness and fingerprint only slots a caller marks as mutable in place, or let a slot opt out (a frozen value); either could make a tick's cost follow what changed, but must preserve the existing between-tick/in-place mutation, deletion/reinsert and recorder contracts under an explicit policy with unchanged defaults. Recorded per the report-don't-modify-engine policy.
- **Adoption note, not an ask: `runMetrics` and `BundleCorpus` have been available since 2026-04-27 (engine 0.8.2 and 0.8.3) and have no reducer/corpus call sites here — for two different reasons, one of which is a consequence rather than an oversight.** `BundleCorpus` is directory-shaped (`new BundleCorpus(rootDir)`, each entry a `FileSink` directory), and aoe2 writes single-file JSON bundles, so the corpus has never had an input here — and adopting `FileSink` directories today would trade aoe2's own streaming reader for the sink's whole-file one, which its bundle sizes do not survive (the read-path item above). The 14-tool MCP server reads through `BundleCorpus` and is out of reach for the same reason. `runMetrics` is the one with no such excuse: it takes `Iterable<SessionBundle>` (`src/behavioral-metrics.ts:32-38`), not directories, so aoe2's own bundles could feed it today and simply never have. The metrics family is not wholly unused: `selfImprovementLoop.ts` already calls `compareMetricsResults`. Root can separately assign useful `runMetrics` adoption on existing JSON bundles with an actual metric denominator. A chunked FileSink reader would remove its whole-file string boundary, but `toBundle`, corpus and MCP still materialize bundles; directory migration and useful corpus adoption need their own memory and consumer proof.

**E11/E13 source freshness, 2026-10-02 UTC.** An independent12-file audit on engine main `eb61e448` confirms eager whole-file reading and a second reader defect: `_readJsonlLines` compares line text with the final line rather than checking its physical position, so `broken\nbroken` can hide a completed malformed line. This is source inference; no reader test or fix has run.
