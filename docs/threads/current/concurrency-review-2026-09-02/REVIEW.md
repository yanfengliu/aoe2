## Findings — bd844ae4, the traffic election

### Theme: what the clock measures

**E1 — HIGH — NEW — The clock measures "ticks since last cell change anywhere", not "ticks waiting in a contested passage", so the tuned constant was validated against a different quantity than the code counts.** [Lane B F1; Driver R3, I3]
Code path: `movementTrafficOps.ts:289-294` (stamp only when the cell changed or no record exists, and only on the unit's OWN calls) -> units that stand still stop calling the arbiter (`builderWorkStep.ts:134-136` moves only when not at target; the gather branch has no move call; an arrived army unit's command is cleared at `playerCommandsSystem.ts:208`) -> `movementTrafficOps.ts:122-134` (wait > 750 elects over the lowest id). Garrison keeps the transform (`garrisonOps.ts:198` removes only `position`) and ungarrison/unload place via `placeFreshSpawnUnit` -> `syncUnitTransformToPosition`, which spreads the old transform (`transformOps.ts:143-147`), so the stale stamp survives every teleport. The "healthy never > 500, pathological >= 1,250" figures behind 750 were stalls of WALKING villagers; the clock also runs across non-walking phases whose durations are unbounded on every map: a Town Center build is ~1,500 ticks, gather fills are 260-615 (under 750), garrisons and parked armies routinely exceed it. So "maps that do not starve keep their exact previous behaviour" is false by construction and held only on the two healthy seeds measured.
Reproduction: R3 (a unit idle 1,000 ticks on its recorded cell wins its first contested election; 100-tick control elects the lowest id). Lane B's trace: builder 500 stamped at (10,10), builds a TC ~1,500 ticks, is retasked through the adjacent one-wide gap, and is elected over the lowest id on its first attempt. In play: 7 consults across 6 units on `seed-2` in 20,000 ticks, 16 across 10 units on the boot map in 30,000, 0 on the default map in 3,000 (I3).
Consequence: a bounded admission-order inversion (one cell per parked unit); someone must win anyway. HIGH because it is reachable in ordinary play on every map and invalidates the constant's rationale, not because it breaks a match.
Fix: re-seed the stamp when the unit resumes asking after a gap — the wrapper already maintains `trafficAttemptTick` every call (`:329-338`); stamp fresh when `tick - trafficAttemptTick > 1`, so the clock measures continuous contested waiting and the preservation guarantee becomes mechanical.

### Theme: consistency and determinism of the election

**E2 — MEDIUM — NEW — The election reads `trafficProgressTick` live while every other input is snapshotted; on the tick after a starved winner crosses a cell, members of one closure elect different winners and the jam loses one admission tick.** [Lane B F2; Lane C F3; Driver R1, I1, I3]
Code path: `:281-301` (the outer wrapper stamps the CALLER before its own election) -> `:407-410` (`lastProgressTick` reads `activeWorld.getComponent(...)` at election time, not `snapshotForTick` at `:201`). Early callers read the ex-winner's stale record and yield to it; the ex-winner's own call stamps it fresh and it yields to the lowest id; later callers agree with the ex-winner. Zero admissions that tick; normal service at the next. Under the pre-fix `Math.min(...cycle)` the same configuration admits the lowest id that tick — `min` of a fixed set cannot change mid-tick — so the "no worse than lowest-id" claim fails for IDENTICAL closures by exactly one lost tick per relief crossing, a case the register's residual-risk note (cross-closure disagreement only) did not name. The file header ("ECS iteration order cannot decide who gets to enter first", `:4-5`) and the JSDoc ("every member of one closure must elect the SAME winner", `:97-99`) no longer hold. It is NOT non-determinism: lane C proved every iteration source is order-stable across continuous, save/load and replay runs (dense id-indexed stores, sorted query caches, free list serialised verbatim and consumed LIFO; systems by phase then registration order, `world-systems.ts:117-119`). Order-DEPENDENT, not order-independent, and the docs still claim the latter.
Reproduction: R1 (A-then-Z: both wait; Z-then-A: A proceeds; fresh-record control: A proceeds in both orders). Ten relief windows in 20,000 ticks on `seed-2`, 28 in 30,000 on the boot map (I3).
Fix: carry `trafficProgressTick` in `TrafficUnitSnapshot` and read it there; keep the stamp (it feeds the next tick). Reword the header and doc to the real invariant so nobody "restores" snapshot purity and changes behaviour.

**E3 — LOW — NEW — Two members can both be admitted in one tick only if one unit is arbitrated twice in the tick with a cell crossing in between; that never happens.** [Driver R2, I1; Lane B proof]
Lane B's five-line proof for a symmetric closure with at most one arbitration per unit per tick: within a tick the tick is constant and a stamp only moves a record to now, so the starved set is non-increasing; a member's own record is finalised before its own election; a member that proceeded keeps its stale record for the rest of the tick; a later member electing itself would need a longer stale wait (contradiction) or an empty starved set (impossible); hence at most one self-election per tick. R2 shows the double admission the moment the precondition is granted; I1 shows it is absent (exactly one consult per unit per tick on both seeds — playerCommands, monk and villagerEconomy each move a unit at most once and the economy loop skips commanded units, `villagerEconomySystem.ts:236-238`). Theoretical until a second mover per tick appears; E2's fix removes it for free.

**E4 — LOW — PRE-EXISTING, marginally widened — Cross-closure disagreement.** [Lane B F5; Driver argued]
`nextFor` (`:379-402`) uses the caller's live direction for itself and remembered/attempted directions for others (`:319` mutates `attemptedDirections` per call), so two movers with different closures could each elect themselves under `Math.min` already; the live stamp adds a second order-varying input. Theoretical because: a concrete double-admission instance needs a remembered heading (same intent key, attempt age <= 1) that differs from the live one in geometry that splits the BFS; neither lane B nor the driver could instantiate it. E2's fix removes the widening.

### Theme: the relief mechanism and the test that ships with it

**E5 — MEDIUM — NEW — The fairness test models the mechanism the commit rejected, its wait bound is false for the shipped one, and relief is one cell per ~750 ticks.** [Lane D F2; Lane B F4; Driver]
`tests/simulation/movementTrafficFairness.test.ts:26-36` (`runJam`) resets the winner's clock on ADMISSION — attempt 2's semantics, which the commit message names as the flaw — while the shipped clock resets on CELL CHANGE only (`:288-301`). Through a k-cell one-wide choke against replenished counter-flow the cost is ~750 x (k-1) plus crossings plus one lost tick (E2) per cell; after the ex-winner steps into the lane, the lowest-id counter-flow unit is admitted into the very cell it occupies, re-forming the head-on jam one cell over — consistent with `seed-7` remaining uncured. Each <= 750-tick stationary chunk sits below the "frozen >= 1,000 ticks" census, so a villager spending 3,000 ticks crossing four cells reads as cured by that instrument. Theoretical on the exact 862 (fine-position details could shave it, not below 765 by much); the modelling mismatch is read directly.
Fix: either re-derive the bound with cell-crossing reset semantics (reset only after ~13 consecutive wins) or delete it and rely on the E8 integration test; record the 750-vs-1,000 instrument gap in the register.

## Verdicts

**bd844ae4 (traffic election): ship, with two one-function fixes, the gate it lacks, and a corrected record.** The core mechanism — keep stable lowest-id, yield only to a member that has not changed cell for 750 ticks — is sound, engages on the pathological seed (I3: 66 starvation consults on `seed-2`) and, past the author's 20,000-tick horizon, on the boot map as well (2,800 consults across 17 villagers by 30,000 ticks, the pre-fix trajectory diverging — M1b), so it is a late-game mechanism on every map rather than a no-op on healthy ones, persists and replays deterministically (I4, lane C), and cannot produce a double admission in the current bridge (I1, lane B's proof). What determines the verdict is E1 together with E8: the clock the election trusts counts any standing still — builders, garrisons, parked armies — while the constant was tuned against walking villagers, so the adoption guarantee ("healthy maps keep their exact previous behaviour") is false by construction and merely held on the two healthy seeds measured; and the fix's only load-bearing difference can be reverted in one line with every gate in the repository staying green, because the shipped test models the mechanism the author rejected. Re-seeding the stamp when a unit resumes asking (E1) and reading the clock from the tick-start snapshot (E2) are each a few lines; the integration test and boundary cases in E8 are what make the defect gated rather than observed. The recorded justification — 44 consults per tick, 0.32 tiles per tick, 3.2 admissions per cell — is wrong in every number (E7) and lives in the defect register; correct it before the next session reasons from it.

**87cc3df4 (approach-plan cache): ship with the one-line fix; do not leave the "by construction" claim standing.** The cache design is right — the start cell in the key is exactly what makes the memo safe against everything the author considered, the plan objects are used read-only, loads and replay scrubs start cold, and the equivalent-mutant reasoning holds.
