# Debugging session — the bottom command bar changes height with the selection

## Symptom
Owner report (2026-09-05): "the info panel at the bottom should not have different heights for different units. This is visually confusing when switching between units." Reproduce in `npm run dev` on the default map: click nothing, then a villager, then the scout, then the Town Centre, then a sheep — the bottom bar's TOP edge is somewhere different each time, and the minimap panel beside it stays put, so the bar reads as a box that pops to a new size on every click.

## Expected vs actual
- Expected: the bottom bar is a fixed-height band, as AoE2's is. Selecting anything (or nothing) changes what is drawn INSIDE the band, never the band's height or its top edge.
- Actual (measured in phase 2 by the gate itself on the unfixed tree, `tmp/hud-height-red.txt`, and by `tmp/probes/hud-panel-internals.mjs`, `tmp/hud-internals-before.txt`): at 1280x720 and 1920x1080 the bar is 72px with nothing selected, 114.2px with a tree, bush or mine, 144.4px with a sheep, 154px with every villager, 185.6px with a villager or a House foundation, 212.6px with the scout, 242.8px with the Town Centre, and 259.2px / 268px (the viewport ceiling) with the 8-unit box selection; at 800x600, 65 / 82 / 186.6 (Town Centre) / 196 (scout) / 226.6 (villager) / 232 (every villager) / 252 (the ceiling: Town Centre with one villager queued, and the box). The 2026-09-02 numbers in `hud-floating-controls.spec.ts` (villager 208px at 1280x720) were stale by the time of this session: the villager card is 185.6px now, and the phase-1 premise that it is the tallest card was wrong — the Town Centre's is, by 57px.

## Reproduction
- Which engine debug tool answers this: **none.** The height is a DOM/CSS property of the HUD; `replay:inspect`, `diffBundles`/`forkAt` and the path-queue/occupancy probes observe simulation state and no replay re-renders the HUD. The instrument is a Playwright spec measuring `getBoundingClientRect()` on `[data-hud="selection-panel"]` over a set of selections made through `window.__AOE2_TEST__` — `tests/browser/selection-panel-height.spec.ts`, which is also the gate. Two scratch probes under `tmp/probes/` (each with its `// harness: none` line) read the boxes INSIDE the panel, which the gate does not print: `hud-panel-internals.mjs` (every child of the panel per state per viewport, and the queue column per entry count) and `hud-panel-dom.mjs` (the summary's markup with each box).
- Command: `PREVIEW_PORT=4182 npx playwright test tests/browser/selection-panel-height.spec.ts` against a `npm run build` of the tree (the config starts `vite preview` on that port). Seed `aoe2-prototype`, paused at boot, viewports 800x600, 1024x768, 1280x720, 1920x1080; 5.8-9.6s per test.
- No temporary instrumentation in `src/`. The RED runs are the spec against the tree before the fix (`tmp/hud-height-red.txt`) and against the fixed tree with the `height:` declaration commented out (`tmp/hud-height-red-mutation.txt`); GREEN is `tmp/hud-height-green.txt`.

## Hypotheses
- [x] Hypothesis 1 — the panel has no `height`/`min-height`, only a `max-height` ceiling, so its box is content-sized; the bottom row is bottom-aligned, so a content change moves the top edge. CONFIRMED by reading the CSS and by the measurement: the panel's height is its tallest flex child plus 28px of padding and 2px of border in every state.
- [x] Hypothesis 2 — a stats block or command group that only some selections render. TRUE but it is the mechanism of hypothesis 1, not a separate cause: `renderSelectionIcons`/`renderSelectionDetails`/the command deck/the queue column are all conditional, and every one of them is meant to be. The fix is not to make them unconditional; it is to stop the box following them.
- [ ] Hypothesis 3 — `min-height` present but exceeded by some selections. RULED OUT: there is no `min-height` on the panel anywhere in `src/*.css`.
- [x] Hypothesis 4 (phase 2) — the villager's card is the tallest, so a villager-sized band holds every common card. FALSE. Above 1120px the tall thing is the SUMMARY, not the deck: the Town Centre's name wraps to two lines beside its 186px portrait chip (a 90px first row against the villager's 63px) and its seven stat chips, one of them the 176px-wide `0 / 15 garrisoned`, wrap to four rows (114.8px against 84.6px) — 212.8px of summary beside a 72px deck. The scout's card is 212.6px for the same wrapping reason ("Scout Cavalry"). A villager-sized band would make the Town Centre card scroll, which `command-deck-fits.spec.ts` and §14.2's "the common cards FIT outright" both forbid.
- [x] Hypothesis 5 (phase 2) — a second, pre-existing defect makes the mixed box selection taller than any lawful band. TRUE: `.hud-selection-unit-list--compact` is `repeat(auto-fill, minmax(48px, 1fr))` inside the summary grid's `auto`-width first column (a shrink-to-fit flex item below 1120px), and against an indefinite width auto-fill resolves to ONE column, so the 8-unit box's three kinds stacked 269px tall in every regime — a grid written so that "8-16+ distinct unit types stay visible" that could never wrap. Under the old ceiling it scrolled (297px of content in a 257px box at 1280x720; 407 in 250 at 800x600).

## Investigation log
- 2026-09-05 — Read `src/ui/hud/hudTemplate.ts`: the bar is `.hud-panel.hud-panel--selection[data-hud="selection-panel"]`, first child of `.hud-bottom`, beside `.hud-panel--map` (the minimap). `src/ui/hud/selectionPanel.ts` rewrites the panel's `innerHTML` per selection signature: a `.hud-selection-summary` (heading + optional portrait + optional stat chips), an optional `.hud-queue-list` column, an optional placement status, and an optional `.hud-command-deck` of `section.hud-command-group`s (Orders, Stance, Formation, Train, Trade, Tribute, Research, Build) — each present only when the selection has options for it.
- 2026-09-05 — CSS, in cascade order (`main.ts` imports `styles.css`, `hudChrome.css`, `hudIcons.css`, `hudCommandPanel.css`):
  - `src/styles.css` `.hud-bottom { display: grid; grid-template-columns: minmax(0, 1fr) auto; align-items: end; }`: the bottom row is bottom-aligned, so a child's height change moves its TOP edge, not its bottom.
  - `src/hudCommandPanel.css` `.hud-panel--selection { width: auto; max-height: min(36vh, 268px); display: flex; align-items: stretch; overflow-x: auto; overflow-y: auto; ... }`. There was NO `height` and NO `min-height`. The comment said so in words: "The bar is as tall as what it holds, up to a ceiling".
  - The same file's `@media (max-width: 1120px)` block sets a different ceiling (`min(42vh, 252px)`), `flex-wrap: wrap`, and lays the summary and the deck out as two lines; `@media (max-width: 700px)` another ceiling; `#hud-root:has(.timeline-panel:not([hidden])) .hud-panel--selection` raises the ceiling under the replay timeline. All four are ceilings; none is a floor.
  - `src/hudChrome.css` `.hud-panel { padding: 14px }`; the panel's border is 1px; `styles.css` sets `box-sizing: border-box` globally, so a `height` on the panel includes padding and border (client box = height − 2).
- 2026-09-05 (phase 2) — The spec as written by phase 1 failed twice for reasons that were not the height, both the same class: a `queue.train` click and a `building.placeConfirm` are commands the sim handles at the start of its NEXT step, so a paused match shows no queue entry and has no foundation until one tick runs. Fixed in the spec with `advanceTicks(1)` after each (atomic: unpause, step, repause). The other phase-1 doubts held: the plural is `3 Villagers Selected`, the box is `8 Units Selected`, and every base resource (sheep, tree, berry bush, gold mine, stone mine) carries `baseOwner` 1 so `getOwnedResourceCells` finds it.
- 2026-09-05 (phase 2) — Measured what each selection puts inside the bar (`tmp/hud-internals-before.txt`). Above 1120px the panel is its tallest child + 30: nothing = a 42px heading; villager = summary 155.6 (63px portrait row + 84.6px of chips in three rows) beside a 124px deck; scout = summary 182.6 (90 + 84.6) beside 122; Town Centre = summary 212.8 (90 + 114.8, four chip rows) beside a 72px deck; every villager = 90 (one compact chip beside the name); the 8-unit box = 269 (three compact chips in ONE column, hypothesis 5). The queue column beside the Town Centre's summary is 66px an entry plus 8px gaps (66 / 140 / 214 / 288 for one to four) and only changes the panel's height once it passes the summary: 242.8 / 242.8 / 244 / 259.2 (the ceiling; 316px of content). Below 1120px the summary is one line and the deck another: villager 84.6 + 10 + 102 at 800 (the chips take three rows there) and 56 + 10 + 102 at 1024 and 1100; the queue takes a LINE of its own between them, 66 + 10 per entry, so a Town Centre with one villager queued is 232px of content at 1024x768 and 1100x700 and 262.6 at 800x600, and every further entry adds 74.
- 2026-09-05 (phase 2) — Read the summary's DOM (`tmp/probes/hud-panel-dom.mjs`): the 90px first row is the NAME wrapping ("Scout Cavalry" 93.6px wide, "Town Center" 101.8px) because the portrait chip beside it, in the summary grid's `auto` column, takes 186-194px of the 300px; the villager's chip is 155px and "Villager" fits on one line. This is the design of v0.3.187 (portrait beside the name) and is not changed here.

## Root cause
`.hud-panel--selection` had a `max-height` ceiling and no `height`, so the bottom-aligned bar was exactly as tall as whichever conditional blocks the selection rendered, and its top edge moved with every click. Beside it, a second cause found in passing: the compact multi-select list could never wrap (hypothesis 5), so no lawful band could hold the box selection until that was fixed.

## Fix
CSS only — the DOM and the render functions are untouched:
- `src/styles.css` `:root`: `--hud-selection-bar-height: 246px`, the bar's ONE height above 1120px — the tallest card the boot scenario shows plus 2px: the Town Centre's 242.8px, or 244px with three entries in its production queue.
- `src/hudCommandPanel.css` `.hud-panel--selection`: `height: var(--hud-selection-bar-height)` and `align-content: flex-start` (below 1120px the bar is a multi-line flex container, and the default would split the band's free space between the summary line and the deck line, so the deck would sit lower under a short summary than under a tall one); the "as tall as what it holds" comment rewritten. The `max-height` ceilings are KEPT as the screen's own limit: they bite only on a window shorter than the band needs (36vh is under 246px below 684px tall) and then clamp every selection alike.
- `src/hudCommandPanel.css` `@media (max-width: 1120px)` `:root`: `--hud-selection-bar-height: 236px` — the tallest wrapped card plus 2px: every villager selected 232px at 800x600, 1024x768 and 1100x700; a Town Centre with one villager queued 234px at 1024x768 and 1100x700.
- `src/styles.css` `.hud-selection-unit-list--compact`: `width: calc(3 * 48px + 2 * 6px)`, a definite width so `auto-fill` has something to fill — three chips per row, leaving the heading beside it about 130px of the 300px summary (a name wraps to two lines there, the height of one chip row). The 8-unit box's summary went from 269px to 90px; up to six kinds fit the unwrapped band in two rows, seven or more scroll.
- Why 246 and not the villager's 187: hypothesis 4. Why not the ceiling (259-268px): 13-22px more empty glass under every selection for nothing the boot scenario needs. Why not `min-height`: a floor still lets a taller card grow the bar, so the height would still depend on the selection; with `height`, a Castle's or a Market's card scrolls inside the band under §14.2 rule (b), as it did above the ceiling.
- Known cost, measured (`tmp/hud-internals-after.txt`): the Town Centre's queue. Above 1120px THREE entries fit the band (214px column + 28px padding = 242 of 244) and the fourth scrolls (316px of content). Below 1120px the queue line costs 76px an entry: ONE entry fits at 1024x768 and 1100x700 (232 of 234) and NONE at 800x600 (261 of 234), where the summary's chips take three rows. It did not fit there before either (261 in the 250px ceiling box). The queue's shape — a vertical column of 66px cards in a horizontal bar — is the cause and is deliberately not reshaped here.

## Follow-ups
- Engine-level gaps: none; this is HUD CSS.
- The gate that now prevents this: `tests/browser/selection-panel-height.spec.ts`; its header carries the reasoning and the bound. The rule is persisted in `design/spec-final.md` §14.2 ("The command bar keeps ONE height, whatever is selected") — its phase-1 wording names the villager as the tallest card and promises the queued Town Centre fits at every viewport; both need the phase-2 numbers (handed to the integrator).
- Architecture: none (no structural change; a CSS token, three declarations, one width).
- Seen, worth a decision: (1) the band is only as WIDE as its content, so the empty state is now a tall narrow slab (120x236 at 800x600, 330x246 at 1280x800) — DE's band is full-width; a minimum width, or the minimap panel sharing the band's height (`align-items: stretch` on `.hud-bottom`), would make the bottom of the screen read as one band. (2) The production queue as a compact row inside the band, which is what would let three entries fit below 1120px and a deeper queue above it. (3) The Town Centre and scout names wrap to two lines beside their portraits because the chip takes 186-194px of the 300px summary; a narrower chip would bring the unwrapped band down toward 220px.
