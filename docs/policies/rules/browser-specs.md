# A browser spec asserts on frames rendered or on game state, never on ground covered inside a wall-clock window (2026-09-06)

One of [this repo's local rules](../local-rules.md), where "above" and "below" mean earlier and later in its list.

No browser spec may require that a quantity move by some amount within a fixed `waitForTimeout`. Hold the input WHILE polling for the state you actually mean and release it in a `finally`; or wait on `waitForRenderedFrames` when the claim is that something did NOT move, because a sleep containing no frames cannot tell "held still" from "never rendered". A duration threshold is NOT available as a gate here, and this rule replaces the lessons-queue entry that asked for one.

**Why.** `game-hud-and-camera-camera.spec.ts` held D for 250 ms and required `scrollX` to grow by more than 40. CI read exactly 35, and 35 is not luck: keyboard pan is `deltaMs / 1000 × 420 / zoom` (`KEYBOARD_SCROLL_SPEED_PX_PER_SECOND`) and `AoeVoxelGameView.frame` clamps `cameraDeltaMs` to `MAX_CAMERA_FRAME_DELTA_MS` = 100, so one rendered frame contributes at most `100/1000 × 420 / 1.2` = 35.00 px at boot zoom. Requiring more than 40 required TWO frames inside 250 ms — an eight-frames-per-second requirement written as a camera assertion. Five more specs had the same shape, and the worst was a scroll helper in `playOpening.ts` that covered 0.0 px on a starved host and then chose its direction from what amounted to a coin toss.

**Why the threshold was refused, with the numbers.** The per-spec duration budget was built, wired into `playwright.config.ts`, and proven to fire. Then two full-suite runs on the SAME machine and the SAME bundle, nothing else changed, gave 95/59/46/40/39 and 48/47/44/41/38 percent of budget for the five specs closest to their timeouts. One test went 28.4 s → 14.3 s and another moved the OTHER way, so it is not one load factor scaling everything — it is per-test and it points in both directions. A threshold above the worst observation lands past 100%, which is the timeout that already exists; anything below it goes red because somebody was compiling.

**How to apply.** The standing instrument is `tests/browser/helpers/durationBudgetReporter.ts`, a REPORT rather than a gate: four lines at the end of every `npm run test:browser` naming the five specs closest to their own timeouts. Those five names are where to look first when the suite gets slower, and they are the honest substitute for the gate. `BROWSER_DURATION_BUDGET=0.8` opts into failing on it for a deliberate investigation; do not put it in CI on the strength of these two runs, whose bound is ONE machine — the CI runner's distribution is unmeasured. When a spec is genuinely too slow, fix what it does rather than raising its timeout: `patrol-interaction.spec.ts:49` cannot be fixed inside the 30 s timeout without raising it and was deliberately LEFT rather than quietly given more room, and `game-combat-and-meta-meta.spec.ts:5` sits at 95% of budget and was deliberately not chunked, because a coarser break check would change what it asserts. One instrument note worth keeping: CPU throttling is the WRONG control for this class — at 20x it also delays CDP input handling, so the keyup lands late, the key stays down far longer than the spec intends, and the broken form covered 175 px and PASSED. Frame starvation is the right one: replace `requestAnimationFrame` with a 300 ms `setTimeout` shim, which starves rendering without touching input timing.

**Amended 2026-09-22 (the rasteriser):** The browser suite draws on the GPU on Windows (ANGLE Direct3D 11) and on SwiftShader everywhere else, including CI. A local run that needs CI's rendering sets `BROWSER_RASTERISER=swiftshader`. A spec whose verdict depends on frame rate uses driven frames or the frame-starvation shim, never the host's rasteriser.

**Amended 2026-09-23 (the double-click):** the frame-starvation shim models TOO FEW frames. It does not model a BUSY main thread, which is what drops a gesture timed across two inputs: under the shim, input is handled at once between rare frames, and the old handler-clock double-click selected all three villagers 8 of 8 times. A spec about two inputs on a slow page puts the busy time where it bites instead, as a long task in a window listener that runs after the game's own handler, and sends both inputs without waiting for the page (`mouse.dblclick`, or CDP sends that are not awaited one by one). A gesture's window is timed on its inputs' own `event.timeStamp`s, never on a clock read in the handler. `tests/browser/double-click-busy-page.spec.ts` and `tests/browser/control-group-double-tap.spec.ts` are the shape. Each asserts first that the two clocks disagree, then the outcome.

**Amended 2026-09-24 (the click-stack search):** a spec that searches for a point to click READS the click stack (`getClickStackAtWorldPosition`, which selects nothing) and asserts how many frames its search drew, rather than clicking at every candidate. A hit test draws the waiting snapshot first, and a selection makes one wait, so a search by clicks draws a full frame per call: `game-selection-click.spec.ts` made about 240 such calls in one `page.evaluate`, which left CI's SwiftShader seconds behind, and a panel check five seconds later found the panel one click behind about one run in five (register, 2026-09-24). A check that the HUD followed a click waits on rendered frames (`waitForRenderedFrames`), bounded by the wall clock the old check had, then reads the panel once: two frames is exact for the selection panel, which redraws on the first frame whose selection differs. That spec is the shape. A local SwiftShader run does not show this class: at CI's four CPUs the old search passed 20 of 20 here while failing about one run in five on CI, so its evidence is a repeated CI run.

**Amended 2026-10-12 (work 123, a per-test gate on CI).** The refusal above measured this shared development machine, and it stands for it: locally both reporters only print the closest tests. CI's runners were measured on 2026-10-11, 84 job logs from 14 runs. They run a job's tests together at 0.57-1.32x of their medians, so on CI `scripts/test-time-headroom.mjs` fails any test past two thirds of its own limit, browser and unit alike, and prints the thirty closest. When a test comes near that line, make its work cheaper or split it into cases that keep every check. Work 123's register entry of 2026-10-12 lists what was cheap to cut. Snapshot round trips cost 0.7-0.9 s each on CI, so read the one state you need (`game.getEconomyState`, `getSelectionState`, `getHudState`, `getCameraState`), and do not return `advanceTicks`' snapshot from `page.evaluate` unless you read it. A loop that checks a condition every tick steps with `stepTicks`, which draws nothing, and reads the one state it checks: `advanceTicks` draws the view and builds a whole snapshot after every call. Take evidence captures only on request. Aim a test at about half its limit on CI's slowest runners, not just under the line: on 2026-10-13 the slowest CPU model seen ran the same list 1.76x slower than the fastest. A limit rises only for work proven irreducible, with the reason written where it is set.
