# Several sessions, one repo: one writer per checkout (2026-09-03, owner)

One of [this repo's local rules](../local-rules.md), where "above" and "below" mean earlier and later in its list.

The owner runs multiple Claude sessions against this repo at once — three peers were live when this was written, two in aoe2 and one in fleet. The rule that makes that safe is not a habit, it is a boundary: **a checkout has exactly ONE writing session at a time.** Everything else in this entry is damage control for when that boundary is crossed.

**Why:** every cross-session loss this repo has paid for came from two sessions sharing one working tree, never from two sessions in separate worktrees. A `git stash` drop that deleted a sibling's named WIP; `git stash push -- <dir>` that reverted five of another session's in-flight files to HEAD (`ae1ec54`); three merges aborted on a shared `dist/` race; `git add -A` that swept `fleet`'s canon sync into a defect-register commit whose message never mentioned it (2026-09-03, twice in one day); and `git reset --soft`, which restores HEAD byte-perfectly while deleting `.git/MERGE_HEAD`, so a merge in progress loses its second parent and the next commit records the content with the branch never marked merged. While this very entry was being written, `scripts/cropZoom.mjs`, `src/game/simulation/civProfiles.ts` and `tests/content/civProfiles.test.ts` appeared untracked in the shared checkout — a peer's unfinished work, one `git add -A` away from being committed by the wrong session under the wrong message.

**How to apply.**

- **Take a lane.** One session owns the shared checkout at `github/aoe2` and does the integrating — merges, version bumps, changelog, gates, pushes. Every other session works in its own worktree, made by `node scripts/controlWorktree.mjs create <name>` (see "Worktrees are the default" above), on its own branch, and hands the branch over; it never commits in the shared checkout. Use available coordination tools to establish the designated integration owner and observed peer status. `git worktree list` shows worktrees, not whether their owners are live; do not infer visibility or ownership from an unavailable tool.
- **In a shared checkout, never use a whole-tree command.** Stage by explicit pathspec (`git commit -m ... -- path/one path/two`). Not `git add -A`, not `git commit -a`. A pathspec is not a scope either: `git stash push -- <dir>` takes everything dirty under that directory, not your change within it.
- **No `git stash` at all while a peer is live.** The stash list is shared across every worktree of the repo, so positional `stash@{0}` pops and drops cross sessions. To bring `main` into a branch, commit a throwaway WIP, merge, and squash before the final commit. If a stash is truly unavoidable, name it (`git stash push -m <name>`) and address it only by name (`git stash pop stash^{/<name>}`).
- **No `git stash` in a worktree while other worktrees are live.** The stash list is shared across every worktree of a repo, so two agents stashing to merge main cross each other's positional `stash@{0}` pops and drops (2026-09-02: one agent's `drop` removed another's "castshadow-wip-2"; the other may have popped the first's enemy-defence files into its own tree). Bring main in by committing a throwaway WIP on the branch, merging, and squashing before the final commit. If a stash is unavoidable, name it (`git stash push -m <name>`) and address it only by name (`git stash pop stash^{/<name>}`), never by position.
- **Never run destructive git in a checkout you do not own** — `reset`, `checkout --`, `merge --abort`, `clean`. If you have already disturbed someone's tree, say which invariant you broke rather than that the state is restored.
- **One preview port per session, never the default.** `PREVIEW_PORT` is honoured by `npm run test:browser`, `captureMapScreenshot.mjs` and `diffMapScreenshots.mjs`; whatever squats on 4173 belongs to a sibling. Capturing from a sibling's preview measures THEIR build as yours, which is why the capture script refuses a server whose served asset hashes differ from this checkout's `dist/`. Check first with `netstat -ano | grep LISTENING | grep -oE ':4[0-9]{3}'`.
- **One full suite at a time, machine-wide (2026-09-25).** Several sessions and their workers now merge their own branches, so each runs its own gate, and two full suites at once starve each other of CPU until timed tests fail for the host rather than the game (canon [R5]: an expensive gate runs one at a time). The lock covers ANY full suite: `npm run verify`, `npm test` or a full `npx vitest run`, `npm run test:browser`, or a full `npx playwright test`; one spec or test file is not a full suite and needs no lock. The unit suite joined the list the same night: four lanes ran full unit suites at once, the CPU sat at 100%, and `aiGarrisonedDefender.test.ts` timed out in two sessions' gates; alone under that load it took 87.8 s against its 30 s budget, with its digest proven identical by A/B (the coordinator's account). Take the lock with `mkdir C:\Users\38909\Documents\github\aoe2\tmp\gate.lock`, which fails while another holder has it: wait and retry. The holder then writes `owner.txt` inside the lock with its lane, its start time and the command it runs (the replay-exit session's practice), and the moment the suite ends, pass or fail, deletes `owner.txt` and removes the lock with `rmdir`, which refuses a directory that still holds a file. A lock whose `owner.txt` names a process that no longer runs is stale, and so is a lock older than the longest suite run (about 40 minutes) whose holder has no running process: say so in your handoff before removing it. A waiter queued for the lock in the background is stopped by killing its process tree (`taskkill /F /T /PID <pid>`) and checking that it is gone, not by stopping the harness task alone: on 2026-09-25 a waiting bash loop survived the harness's TaskStop on Windows, took the lock the moment its owner's real run released it, and held it for three minutes on a duplicate run. Only ever act on processes your own runs started; the machine is shared with other sessions. A run of `npm run verify` is read from its receipt, not its exit code alone, because a run cut short can exit 0 (register, 2026-10-11): `node scripts/verify-receipt.mjs check` exits 0 only when the last run reached its last step with both test suites' own reports of a whole, passing run and the checkout matching one commit's tree at both ends, and the tree being pushed is that one or differs from it only in `docs/` and `design/spec-final.md`.
- **A session that lands code holds the lock from its final rebase through its push (2026-10-10; announced to peer sessions 2026-09-25).** It takes `tmp/gate.lock` first, then rebases onto `origin/main`, then takes its version number on that tree, runs `npm run verify` there and commits nothing in that checkout while it runs, checks the result with `node scripts/verify-receipt.mjs check`, pushes `main` only once that exits 0, and only then releases the lock. Otherwise two sessions that verified on the same base and pushed one after the other leave on `main` a combination that no gate ran. A docs-only push needs no lock and may go while one is held. A holder whose push is then refused rebases again. It reruns the full gate if a new commit changes anything outside `docs/` and `design/spec-final.md`. Otherwise it reruns only the checks those files have, which for `docs/work` are `checkoutLineEndings.test.ts` and `workDocsIntegration.test.ts`. `check` runs again before every push; it accepts a receipt across such a rebase and names the files to recheck.
- **`dist/` is per checkout, not per session.** Two sessions running `npm run build` in one checkout race, and the loser's gate run measures the winner's bundle.
- **Pull before push; never force-push `main`.** Expect non-fast-forward rejections as normal traffic when peers are live.
- **A generated file changing under you is not a conflict to resolve.** `AGENTS.md`'s canon block is written by `npm run sync-canon` from `../fleet/FLEET.md`, and changed three times in one day here. Commit it on its own with a message that says so; never fold it into unrelated work.
- **Untracked files you did not create are someone's work in progress.** Leave them. Do not add them, do not clean them, do not assume they are debris.
