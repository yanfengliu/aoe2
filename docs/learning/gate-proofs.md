# Gate proofs

The standing answer to "did the gates actually do their job".

A lesson leaves [lessons.md](lessons.md) only when it becomes a gate, and a gate counts only once it has been made to go RED by reintroducing the defect. This file records the mutation, the failure it produced, and the bound the gate does not reach past. Without it, "this became a gate" is an unverified claim and the deletion it justifies is unearned.

## If a gate here is wrong

A gate and the claim in its header can be wrong together, and when they are they look exactly like a gate that is right. Auditing one means reaching what was believed, measured and abandoned at the time — never the sentence the gate carries about itself. The evidence deleted in a retirement commit is not lost; this repository's evidence file as it stood immediately before the first retirement reads back out of:

    git show 96ed269d:docs/learning/lessons-evidence.md

`git log -- docs/learning/lessons-evidence.md` lists every earlier revision, and `git log -S'<phrase from the gate header>' -- docs/learning/` finds the entry a particular gate retired.

## Every checkout of this repository gets LF, on every platform

- **Gate:** `tests/architecture/checkoutLineEndings.test.ts` :: five checks in two describes — `the instrument reads git, and reads more than nothing` (the row parse plus known paths; text-versus-binary really distinguished) and `a checkout of this repository gets LF, whatever platform runs it` (`eol=lf` resolved for every text file; nothing stored with CRLF in the index; the shebang scripts covered) — run by `npm test`, and so by `npm run verify`. Register-driven (register entry 2026-09-06, "A Windows checkout rewrote every tracked file to CRLF"): found by the remote gate, fixed and gated in one session, so no `lessons.md` entry is retired by it.
- **Claim it carries:** `.gitattributes` guarantees that a checkout of this repository writes LF on every platform, so the bytes CI compiles are the bytes that were authored. Git for Windows installs `core.autocrlf=true` in its SYSTEM config and the GitHub-hosted `windows-latest` image is that same install, so without the guarantee `actions/checkout` rewrites every tracked text file to CRLF. A CRLF shebang then breaks Vite: `ssrTransform` finds its import-injection offset with `hashbangRE = /^#!.*\n/` (vite 6.4.3, `dist/node/chunks/dep-Dm0c1Wj2.js:25674`), a JavaScript `.` does not match `\r`, the offset falls back to 0, and `__vite_ssr_import__` calls land in front of `#!/usr/bin/env node` — `SyntaxError: Invalid or unexpected token`. Eighteen tracked scripts carry a shebang.
- **Mutation 1 — the exact pre-fix state:** `.gitattributes` removed from the index and from the working tree. **Red:** `3 failed | 2 passed`. `.gitattributes is tracked but was not in the listing, so the scan is not seeing this repository`; `1767 tracked text file(s) do not resolve \`eol=lf\`, so a checkout under Git for Windows' default \`core.autocrlf=true\` ... writes them with CRLF`; `18 script(s) that begin with \`#!\` are not covered by the LF guarantee`. The binary control stays green, correctly — git sniffs `i/-text` for the 68 PNGs whether or not the file exists, which is why the classifier reads the index column and not the attributes alone.
- **Mutation 2 — the guarantee inverted:** `* text=auto eol=lf` changed to `eol=crlf`. **Red:** `2 failed | 3 passed`, naming all 1,768 text files and all 18 shebang scripts.
- **Mutation 3 — the scripts smuggled out of the guarantee:** `scripts/** binary` appended. **Red:** `1 failed | 4 passed`, on the enumeration control — `No tracked script starts with \`#!\`. There were 18 on 2026-09-06 ... the enumeration is broken and the assertion below is passing over an empty list`. This is the check refusing to report "did not run" as "passed".
- **Mutation 4 — a blob genuinely stored with CRLF:** `git hash-object -w --no-filters` on a CRLF file, added with `git update-index --cacheinfo`, which bypasses the `eol=lf` filter the way a bad merge or an old commit would. **Red:** `1 failed | 4 passed` — `1 tracked file(s) are stored with CRLF in the index. \`eol=lf\` fixes what checkout writes and cannot fix a blob that already carries \`\r\`, so these arrive with CRLF on Linux too.`
- **Green after revert:** yes. `.gitattributes` restored to SHA-256 `d8da2543c21f2554cf94532ca7afa872299139b17e43ca89366b598ba09d09ad`, identical to before the mutations; `npx vitest run tests/architecture/checkoutLineEndings.test.ts tests/scripts` gives `13 passed`, exit 0.
- **The defect itself, proved both ways.** `scripts/ci-status.mjs` converted to CRLF in place: `npx vitest run tests/scripts` gives `6 failed | 2 passed`, `SyntaxError: Invalid or unexpected token` at `tests/scripts/ciStatus.test.ts:131:21` — the Windows runner's failure reproduced exactly, on the machine where it passes. The discriminating control, which is what makes the cause the SHEBANG and not CRLF in general: the same CRLF file with only its `#!` line replaced by an ordinary comment gives `8 passed`.
- **Bound.** The gate speaks about tracked files and about what a fresh CHECKOUT produces. It deliberately asserts nothing about the working tree on disk: 810 of 1,766 tracked files were CRLF in the authoring tree on 2026-09-06, left over from checkouts that predate `.gitattributes`, and such a tree cannot reach CI, which always clones fresh — a check that went red for that would be deleted by the next person it annoyed. It says nothing about Vite's hashbang handling, so a future toolchain that mishandles LF leaves it green. It cannot see a per-clone override outside the repository (`.git/info/attributes`, `core.eol`). Deleting a `.gitattributes` rule and the check together would pass, as always. And it does not prove the runner is fixed — only a Windows CI run does that.

## The command that checks the remote gate answers for a commit, not for whatever ran last

- **Gate:** `tests/scripts/ciStatus.test.ts` :: eight cases in three describes — `ci:status reports on a commit, not on whatever run is newest` (UNGATED, NEVER ASKED, CARRIED), `ci:status separates a gate that could not start from a gate that failed` (the billing annotation, GREEN, RED), and `the fixtures are wired the way the script asks for them` (the two instrument controls) — run by `npm test`, and so by `npm run verify`. Register-driven (register entry 2026-09-05, "The command that checks the remote gate reported an earlier commit's run as the tip's"): found, fixed and gated in one session, so no `lessons.md` entry is retired by it.
- **Claim it carries:** `npm run ci:status` reports on the commit a session is about to build on — the local HEAD, and the pushed tip when they differ — and never on whatever run happens to be newest in a workflow's run list. A commit with no run of its own gets one of three answers rather than silence: NEVER ASKED (the workflow's `on.push.paths` matched nothing that changed, exit 0), CARRIED (a later push gated it at its tip), or UNGATED (a run was due and none exists, exit 1). `const latest = finished[0];` had bound the whole report to the newest entry of a run LIST, and no call in the script mentioned a sha, so a commit that produced no run read as whatever an earlier commit's run had said.
- **Mutation:** restore `scripts/ci-status.mjs` to `b1d0a0ff`, the shipped script before this change, with the gate file and its fixtures left in place.
- **Red:** 6 of the 8 fail. The UNGATED case — a pushed commit that changed `package.json` whose runs API returns `total_count: 0` — fails on `expected +0 to be 1`: the old script exits 0 and prints `CI: GREEN — 20+ consecutive, latest "Merge: motion smoothing survives a slow machine (v0.3.192)" at 2026-09-03T04:04:53Z`, a verdict about a different commit. The two instrument controls are among the two that stay green, which is what they are for.
- **Green after revert:** yes, `8 passed` (`npx vitest run tests/scripts`, exit 0), and the full `npx vitest run tests` exit 0 with 481 files and 3,478 tests on the same tree.
- **Bound. Fixtures are not the API.** Every fixture was captured from the live repo with `gh` on 2026-09-05, but they are the projections the script's own `--jq` asks for, not raw payloads. The suite proves the reporting logic and the exit codes; it proves nothing about whether GitHub still returns these shapes or whether `gh`'s flags still mean what they meant, so a field rename on GitHub's side leaves it green. Running `npm run ci:status` against the live repo is the only check on that. The YAML reader understands `on.push.paths` as the two watched workflows write it and refuses `!`, character classes and brace groups; `origin/main` is the locally cached ref, so an unfetched tip looks like the tip; the path filter is evaluated over the diff since the last gated ancestor, a stand-in for the push GitHub actually saw that is wrong for a force-push or a rewritten history; a `skipped` or `cancelled` run with no jobs still reads RED; and the third workflow, `playtest-corpus-llm`, is not watched at all.
- **Guard against a false green:** the fake `gh`/`git` throws on any command it has no fixture for, because a stub that silently returns `""` is exactly how a check reports "did not run" as "passed"; and one case asserts the recorded zero-run and never-started responses still have the shape the other cases depend on, so a fixture edited into uselessness fails by name instead of passing everywhere. The CARRIED case is the over-fix guard: an interior commit of a multi-commit push must not read UNGATED, or the command would cry wolf on every commit but the tip.

The mutation removes the `height` line and not the compact-list width, so the box state read 152px / 230px in the mutation run rather than its pre-fix 259.2 / 252: the gate's red does not prove the second defect's fix, and the box state's green needs it.

- **Claim it carries:** every unit walking at its own base rate reaches locomotion weight 0.9 or more, and the humanoid and mounted recipes posed at that weight move a boot, a leg and a horse's front leg between the two stride extremes by at least 0.25, 0.11 and 0.3 of the recipe scale. `resolveUnitAnimationState` had blended the weight toward `speed / 2.5` tiles per second — the uniform clock before §12.4.2 — and since v0.3.160 gave every unit its own rate (villager 0.8, militia 0.9, knight 1.35) no unit reaches 2.5, so every walker's weight sat at 0.2–0.6 and its gait, every amplitude of which multiplies by that weight, played at that fraction of the authored motion.

The leg check covers the villager, infantry, archer, cavalry and cavalry-archer roles, posed through the real recipes at gait phases pi/2 and 3pi/2 only, against lower bounds under the authored full-weight amplitudes (0.32, 0.14, 0.39). It says nothing about a unit slowed by traffic (the gait is meant to fade with speed), about movement technologies (faster only clamps at 1), about siege wheels or a monk's sway, or about what a pixel does at any zoom — the capture pair in the debugging doc is the pixel evidence (default view at tick 0: 0 px differ; the same view with four walkers: 1,399 px in two blobs on the two in frame; the militia at zoom 2.4: 175 px at t25, 2,023 px at t28), not this file.

The `docs/threads/` prefix is elided in this record because the literal would fail this file's own scan; the sentence-final dot on the first path and not the second is the normaliser at work.
- **Mutation, the casing half:** `docs/architecture/decisions.md:667` pointed at `…/done/render-realism-2026-09-02/design.md`, lower case. Windows resolves it; Linux CI would not. **Red:** the same message shape, naming the lower-cased path — 1 failed | 2 passed.
- **Mutation, the instrument:** `.ts` dropped from the extension list, which silences exactly the two roots the 2026-09-05 pointers lived in and had left an earlier total-count floor green (critic finding W3). **Red:** `src: 0 real pointers found, at least 3 exist | tests: 0 real pointers found, at least 3 exist` — 1 failed | 2 passed.
- **Green after every revert:** yes, 3 passed, the probe folders gone and the working tree's status identical before and after the seven runs. Driver: a script that applies each mutation, runs the gate and undoes the mutation in a `finally`, with one file per probe folder so no recursive delete was needed.

- **Bound.** (1) sees literal paths in the ten listed roots only: a template with `<objective>` placeholders resolves to the folder, an elided `...` path is checked up to the elision, and `docs/devlog/`, `docs/changelog.md`, `docs/debugging/` and `docs/threads/` are exempt by the rule's own decision because they narrate moves and pending states as they were ("the folder moves from `current/` to `done/` in this commit"); those hold about fifty stale pointers today. (2) catches only a thread closed by the ritual. (3) is a 30-day tail, as the matrix shows: two of the six were green under it alone. It reads `YYYY-MM-DD` dates as text from file contents and path names, so a deadline ("retry after 2026-09-06", live in `concurrency-review-2026-09-02` today) or a version's date counts as maintenance, and a status line that is false but dated today passes; a date followed by a timestamp's `T` counts. The clock is the newer of HEAD's commit date and the devlog's newest date, so an idle repo never goes red on its own, and a run of commits whose devlog was skipped still moves it. Thirty days: a thread closed without its closure line can sit for 29 days of commits without a word.
- **Guard against a false green:** each of `src`, `tests`, `design` and `docs/architecture` must yield at least three real pointers (a template resolving to the bare `current/` or `done/` folder is not counted), so a broken regex, extension list or root entry goes red; the clock throws if neither `git log -1` nor the devlog yields a date.

## An arithmetic claim about hardware is not a measurement, and the gate that measures it must read the buffer the work actually lands in

- **Gate:** `tests/browser/shadow-depth-precision.spec.ts` :: `every buffer the scene draws into resolves the shadow level step` — run by `npm run test:browser`, and so by `npm run verify`.
- **Claim it carries:** `SHADOW_LEVEL_STEP = 0.002` world units separates two casters' shadows in depth. That is derived arithmetically as about four depth quanta from the orthographic camera's 4000-unit range on a 24-BIT buffer, and nothing in the renderer requests 24 bits — the context asks for `{alpha, antialias, powerPreference}` and takes whatever the device gives. At 16 bits one quantum is 0.061 world units, thirty times the separation, and every shadow lands in one bucket: the level scheme degrades silently into the z-fighting stripes it exists to prevent.
- **Mutation:** in the spec's own `depthOf`, `return 16;` for every non-default framebuffer — a device whose offscreen targets are allocated `DEPTH_COMPONENT16`, which is Three's default internal format for a depth-only renderbuffer and therefore the realistic form of this defect rather than a synthetic one.
- **Red:** `the scene draws into a offscreen buffer with 16 depth bits; SHADOW_LEVEL_STEP = 0.002 needs at least 24 to separate two shadows (measured: {"drewAnything":true,"frames":13,"canvasSize":{"width":800,"height":480},"buffers":[{"target":"offscreen","depthBits":16},{"target":"offscreen","depthBits":16},{"target":"default","depthBits":24}]})`.
- **Green after revert:** yes, 1 passed in 2.7s.

**The finding that changed the gate, and the reason this entry is worth reading.** The lesson specified the gate as "a browser spec reading `gl.getParameter(gl.DEPTH_BITS)` off the live world canvas and asserting >= 24". **That gate would have measured the wrong buffer.** The default art style, Moebius, resolves the frame through a stylized pass, so the scene is rendered into offscreen targets first — and a Three render target's depth attachment is allocated independently of the canvas's. Instrumenting `bindFramebuffer` and the four draw entry points for twelve real animation frames shows the scene's draws landing in **three** buffers on this machine: two offscreen and one default. The canvas-only reading would have covered one of the three, and NOT the ones the shadow depth test actually runs in under the shipped default style. It would have been green for the same reason the defect is invisible.

Measured here, all three report 24. The specified gate would also have passed. That is precisely the problem with it: a gate that is right by luck is indistinguishable from a gate that is right, until the day the luck changes.

- **Bound.** ONE machine, ONE art style, ONE scene, ONE moment. It asserts what this device hands back when `aoe2-prototype` is drawn under the default style; a device that allocates 16-bit targets fails it, which is the point, but only if the suite is ever run there. It also only sees framebuffers that receive a draw call in the twelve frames it samples — a lane that draws rarely (a resize path, a picking pass) is outside it. It does not check that 0.002 is ENOUGH at 24 bits; that arithmetic is still arithmetic, and the thing that tests it empirically is the overlapping-shadow gate in `tests/rendering/aoeVoxelShadowLayering.test.ts`.
- **Guard against a false green:** the spec fails if the canvas is 1x1 or nothing drew. That is not hypothetical — measuring this by hand first, through a hidden browser pane, returned a 1x1 canvas, zero animation frames and zero draw calls, and every depth assertion would have passed vacuously because there was no buffer to fault.

## The unit-line table and the tier chains are two sources that can drift apart

- **Gate:** `tests/simulation/aiUnitLineTraining.test.ts` :: `resolves every mix entry against the REAL offers, at both tech extremes`.
- **Claim it carries:** every unit `pickUnitMix` names resolves to something its producer actually offers, at both ends of the tech state.
- **Mutation:** deleted the `'halberdier-upgrade': { from: ['pikeman'], to: 'halberdier' }` row from `UNIT_LINE_UPGRADES` — a tier known to `trainOptions.ts` but not to the line table, which is the drift this gate exists for.
- **Red:** `feudal-age: the mix wants spearman but barracks offers [champion, halberdier] with allResearched=true: expected undefined to be defined`.
- **Green after revert:** yes.

**This gate replaced a TAUTOLOGY, which is why it exists in this form.** The assertion it replaced was `trainableInSameLine(unit, [unitLineOf(unit)])`, which cannot fail for any input — `unitLineOf` is idempotent, so the single offer is always in the line. The binding form builds the REAL `createTrainOptions` so the tier chains come from `trainOptions.ts` rather than from the same table the assertion uses; a check built from the same symbol as the thing it checks proves only that the code agrees with itself.

**Bound.** One civilization with a complete tech tree (`getTrainOptions` filters civ denials, and a civ legitimately lacking a whole line would fail this for the wrong reason). Resolution only — not affordability, population, or whether the unit is worth training.

## A test cannot ask whether an entity survived with an id that may have been recycled

- **Gate:** the `no-restricted-syntax` rule for `tests/**/*.ts` in `eslint.config.js` — run by `npm run lint`, and so by `npm run verify`.
- **Claim it carries:** `world.isAlive(id)` takes a bare entity id with no generation, and `../civ-engine/src/entity-manager.ts` recycles ids from a free list. An entity that DIED and whose id was reused reads back as alive, and it carries the same components, so a follow-up `getComponent` check does not catch it either. A test is exactly where that bites, because a test captures an id, steps the simulation, and then asks whether the thing it captured survived. Production code is deliberately NOT restricted: its 27 call sites take the id from a live query and ask in the same tick, where there is no time for a recycle.
- **Mutation:** `expect(villagerIds.every((id) => bridge.world.isAlive(id)), ...)` in `tests/simulation/aiGarrisonedDefender.test.ts` — the exact check a critic proved unsound on 2026-09-04, restored.
- **Red:** `error  world.isAlive(id) cannot tell a recycled id from a surviving entity. Take a ref BEFORE the step — world.getEntityRef(id) — and ask world.isCurrent(ref) after it; the ref carries the generation  no-restricted-syntax`, and lint exits 1.
- **Green after revert:** yes, lint exits 0.

**Bound.** It is a syntactic rule on the NAME `isAlive` in the tests tree. It does not reach production code, where the same call is legitimate; it does not catch the same mistake spelled another way (a raw `entityManager` reach-through, say); and it says nothing about whether a test that DOES use a ref took it early enough to mean anything. What it covers is the whole class of the defect that was actually found: a test asserting survival across a step with an identity check that cannot tell two entities apart.

**Why the boundary is the tests tree and not the call.** The honest rule would be "do not hold an id across a step and then ask", and that is not lintable. The tests tree is where holding an id across a step is the normal shape, so restricting the call there catches the class without a false positive on the 27 production sites — one of which was checked and is correct. The single pre-existing test use, in `rightClickNeverGarrisons.test.ts`, was the same latent defect and was rewritten to take a ref before the step; it had been asserting "the unit is still on the field" in a way a recycled id would have satisfied.
