# Defect register

The standing list of what the gates could not see. One entry per defect that reached a build: the symptom as it presented, what the investigation found, the root cause, and the check that covers the defect's whole CLASS from now on.

Unlike a lesson, an entry stays after it becomes a gate. The register is not a to-do list — it is the record of where defects came from, which is the best available guide to where the next one is.

**What lives here, and what rolled over.** This file holds the 12 most recent CLOSED entries plus every OPEN one, whatever its age, newest first. Everything older and closed is in [`defect-register-past.md`](defect-register-past.md), moved verbatim. An OPEN entry never rolls over — it leaves this file by being closed, not by ageing, and a heading that says the defect is still live is not a closure however it spells it: "(LATENT, not fixed)", "(PARTLY FIXED: ...)" and "(... still unfixed)" all keep the entry here, and each of those three had been archived once before the gate learned to refuse them. The rollover is done by the task whose new entry pushes this file past 12 closed entries, in that task's own commit, the way the devlog archives its detailed file; never by a later sweep. `tests/architecture/defectRegisterRollover.test.ts` holds all of that. An "entry above" or "entry below" written before the split may name an entry that now lives in the archive, and a rollover can strand a pointer in either direction; the archive's header lists the seven that cross today.

## 2026-09-06 — A simulation step that refused to run said nothing, and two sessions then reasoned from a false model of the engine (found by the standing loop, FIXED and gated)

**Symptom.** `window.__AOE2_TEST__.advanceTicks(3000, 100)` against a game paused from the REAL Esc menu returns after zero ticks, throws nothing, and leaves `matchState.outcome === 'running'` and `engineHalted === null` — the two fields a caller would consult, both saying nothing is wrong. Confirmed live at v0.3.213.

**Investigation.** `bridge.step()` had FOUR paths that decline to advance the world and returned the same nothing for all of them: a manual pause (`setPaused(true)`, which is what the Esc menu applies), `haltState.halted`, a match that already has an outcome, and the replay bridge, which never advances from a frame by design because `ReplayController` owns playback. `advanceTicks` lifts only the pause IT applied (`pausedThroughTestApi`), so a pause set anywhere else survives every step in its loop.

**The expensive part was not the missing ticks.** A play session, reading that silence, published a hazard about the test seam in two forms: that `advanceTicks(n)` throws the engine's re-entrancy `EngineError`, and that it "silently under-advances when the simulation is not paused". Both were repeated in worker assignments as fact. A later session measured them at `d65f84aa` and found BOTH wrong — running and unpaused, 3,000 requested gave 3,000 advanced with no throw; paused through the test API, the same; and `advanceTicks` is a plain loop called from outside any tick, so it cannot reach the engine's re-entrancy guard at all. So two sessions spent effort reasoning from a false model of the engine, and the cause was not a wrong measurement: it was that a function which declined to do its job said nothing about declining, leaving a tick delta of zero as the only evidence and every explanation for it equally available.

**And a caller was already paying for it.** `src/game/playtest/llmRunner.ts` treats `advanced <= 0` as `stopReason = 'engineHalt'` under a comment that asserts the inference is safe — "Reached only when the match is still 'running' ... so no progress here IS a genuine halt". A world paused by anything other than the test API is still `running` and still advances nothing, so that branch reports a PAUSE as an engine crash. It is latent only because the LLM host happens to unpause around each call; nothing in the runner knows that, and nothing would tell it if that stopped being true.

**Root cause.** A function with four distinct refusal conditions and no return value. Every caller had to infer refusal from an unchanged tick counter, and no caller could tell the four apart.

**Fix.** `step()` returns `{ ticks, refusedBecause }` (`src/game/simulation/bridge/stepReport.ts`, typed in `simulationBridgeTypes.ts`), where `refusedBecause` is `'paused' | 'halted' | 'match-over' | 'replay'` or `null`. `ticks` is reported separately from the refusal because zero ticks is legitimate for a `deltaMs` shorter than one tick, so a short step is not a fault. A step that ran some ticks and then hit a failing tick reports BOTH halves. The refusal values are shared FROZEN module constants — one object each for the life of the process, no `Error`, no stack capture, no string building — because a halted, paused or finished match refuses on every frame for the rest of the session, sixty times a second, and that steady state must allocate nothing. `browserTestApi.advanceTicks` now returns the tally (`stepsRequested`, `stepsRun`, `ticksAdvanced`, `refusedBecause`) summed from the steps' own reports rather than read off a tick counter, and warns once per reason for callers that ignore the value.

**Two designs were rejected, and why is the useful part.** THROWING was rejected because the playtest runner polls a finishing match and a resolved match is a normal end there, not an exception. Fixing only the test seam — having `advanceTicks` compare tick counters and report the shortfall — was rejected because it leaves the production silence exactly as it was, and the production silence is the defect: the same `step()` is called by the frame loop and by `runPlaytest`, and it is those callers, not the test harness, that had no way to ask what happened.

**How this class is checked from now on.** `tests/app/stepRefusalIsReported.test.ts` (`npm test`, so `npm run verify`), 13 cases: all four refusal reasons on the REAL objects (`paused`, `halted` and `match-over` on a real `createSimulationBridge`, `replay` on a real `makeReplayBridge`), asserted to be four DISTINCT values — a signal that cannot tell them apart is the same defect in a new costume — plus a control in the other direction (a running unpaused bridge reports no refusal, so the gate cannot pass by refusing everything) and the seam end to end through the real `installBrowserTestApi`. Proven red at `bcdc88c3` with the source reverted: 12 of 13 failed. The 13th passes on both trees ON PURPOSE — it is the backwards-compatibility control for widening `advanceTicks`'s return value — and carries none of the gate's coverage.

**Bounds, named.** Seed `aoe2-prototype`, tick horizons in the tens, and match resolution FORCED with `gameLength` rather than played out, so it proves nothing about how a real match ends. It never runs the live frame loop, which calls `step()` every animation frame and correctly DISCARDS the report; nothing here measures that loop's cost or checks that discarding stays correct. The console warning's dedupe is asserted over two calls, not over a long run.

**Open follow-ups.** (1) `llmRunner.ts` should READ `refusedBecause` instead of inferring a halt from `advanced <= 0`; the signal now exists and the runner still guesses. (2) `src/app/bootstrap/browserTestApi.ts` is now at EXACTLY 500 lines, its cap in `tests/architecture/fileSizeBudget.test.ts`, so the next line added there goes red and the answer is a split by role rather than a trim.

## 2026-09-06 — A match the player LOST announced itself as "Conquest Victory", in 13px grey, in a corner (owner-reported, FIXED and gated v0.3.214)

**Symptom.** The owner played to conquest and LOST. The entire announcement was a `hud-footer` at (12, 611), 420x97, bottom-left, in 13px `rgba(226,234,243,0.56)` grey, reading "All of your units and buildings have been destroyed. / Conquest Victory / Player 1: 668 / Player 2: 1809". A loss announced as a Victory — and beside that, no winner named, no overlay, no dim, and nothing to act on, so a player can finish a match without noticing it has ended.

**Investigation.** Reproduced at `bcdc88c3` on `conquest-defeat-fixture`: `matchState.outcome` is `defeat`, and the rendered footer says "Conquest Victory". The outcome was CORRECT, sat one property away in the same object, and was rendered by nothing. `postGameSummary`'s own `formatWinConditionLabel` took `winCondition` alone and switched on it (`case 'conquest': return 'Conquest Victory'`), so a win and a loss printed the identical four characters. Nothing else on the HUD said which way the match went.

**Root cause.** Two, stacked, and the second is why the first survived: the words were built from a value that does not carry the answer, and the surface they were drawn on was never sized to be read.

**Fix (v0.3.214).** One module forms all the end-of-match words — `src/ui/hud/matchOutcomeText.ts` — and EVERY function in it takes the outcome, so a label without the outcome is not expressible rather than merely discouraged. Both surfaces build their text there: the footer record (`postGameSummary`) and a new dimmed modal (`src/ui/hud/matchResultOverlay.ts`) that states the result, names how the match was decided, names the winner where that is knowable, and carries one control. The modal follows the v0.3.211 halt-notice precedent deliberately — same dimmed full-screen root, one panel, one action, focused on open — rather than inventing a third modal idiom; a stopped match and a finished one are the same kind of event. The footer stays as the record after the overlay is dismissed.

**Naming the winner is derived honestly, and that is the part worth keeping.** `MatchState` records the outcome from the HUMAN's point of view and stores no winner at all. Score cannot stand in for one: in the conquest fixtures the WINNER HOLDS THE LOWER SCORE — 50 against 10 one way and 10 against 50 the other — so a "top scorer wins" shortcut would have named the loser in the very match this entry is about. So the derivation is refused wherever it would be a guess. A victory is the player's own. A draw has no winner and says so. A `score` defeat names the top scorer, because "highest score wins" is that condition's own published rule (`scoreTimerSystem`) rather than an inference. A conquest, wonder or relic defeat against ONE opponent names them, because only one player can have won. A conquest defeat with several opponents records only THAT an opponent won and names the winning SIDE — "Winner: your opponents" — instead of picking one.

**The one real gap, recorded rather than papered over.** `MatchState` has no `winner` field. Until it does, the multi-opponent conquest case cannot name an individual, and no amount of care in the HUD can invent the datum. This is the only case the announcement is vaguer than DE.

**How this class is checked from now on.** Two gates, and the split between them is the point. `tests/browser/match-result-announcement.spec.ts` (`npm run test:browser`, so `npm run verify`) plays FOUR real matches in the browser to resolution at 800x600 — `conquest-victory-fixture`, `conquest-defeat-fixture` (the human holds the higher score, 50 against 10), `score-timer-draw-fixture` (tied at 180) and `score-timer-defeat-fixture` (three players, P2 the sole top scorer) — and asserts the RENDERED TEXT, never `matchState.outcome`, because the defect is exactly that the field was right and unrendered. Each match must read the right outcome and never a different one, must name a winner, must be legible (visible, at least a quarter of the viewport, dimming what is behind it, headline at 24px or more in a colour at least 80% opaque), and must offer one control that dismisses it and leave the corrected footer behind. `tests/ui/matchResultAnnouncement.test.ts` (`npm test`) is the pure-render half: every `outcome` x `winCondition` pair the union allows, across four owner shapes. Red three ways: every `defeat` and `draw` case reported "Conquest Victory" or "Score Victory" at `bcdc88c3`, `renderMatchResult` did not exist, and the OVER-FIX guard bites too — deleting `.hud-match-result[hidden] { display: none; }` from `hudChrome.css` turns the live-match assertion red. That last one is the author-`display`-beats-UA-`[hidden]` trap `.hud-halt-notice` paid 99.98% of a frame for the day before, and it is now the third surface to carry the compound rule. Live-game capture diffs are 0.00% at both viewports.

**Bounds, named.** The browser spec covers no wonder or relic DEFEAT wording (no fixture ends a match that way; the unit test covers those labels as pure renders), no multi-opponent CONQUEST defeat (no fixture), no viewport but 800x600, no keyboard reachability of the dismiss control, and nothing about what the overlay does across a restart. The unit test proves nothing about mounting, visibility, type size, contrast or reachability — a surface never appended, `hidden` forever, or painting at 1px passes every line of it.

## 2026-09-06 — The AI abandoned foundations it had paid for, and stalled forever on the first building it could not afford (found by the coverage lab, FIXED, floor deferral recorded, OPEN)

**Symptom.** Two seats of a 45,000-tick self-play match, both stuck in ways a watching player would read as the AI simply not playing. Owner 2's Siege Workshop stood at 125 of 400 build progress from tick 13,750 to the horizon — 31,250 ticks of a half-built building nobody was working on — so that seat trained no Battering Ram, no Mangonel, and researched neither siege technology. Owner 1 spent the entire Castle Age with its wood pinned between 6 and 127 while sitting on **2,506 stone**, enough for three Castles, and a Castle alone would have qualified it for the Imperial Age (spec §7.2). It never left the Castle Age. Owner 1 also held three farm plots frozen at 0 of 150 and counted them among the farms it owned, keeping its food near zero.

**Attribution.** Found by the coverage lab (`tests/simulation/selfPlayContentCoverage.test.ts`), which went red when the placement fix in the entry below landed. That is worth stating plainly: the lab had been green over both of these defects, and only started reporting them once a neighbouring change moved the match onto a different path. Not owner-reported.

**Investigation, and why they compound.** `runBuildCrewPhase` built its list of construction sites from the LIVE build COMMANDS. `playerCommandsSystem` drops a build command the first tick `findBuildingApproachPlan` returns null — one blocked tick is enough — and from then on the site had no builder, so it was not in the command list, so nothing re-crewed it. Meanwhile `findOwnedBuilding` still found the foundation, because a foundation counts as a building, so `missing('siege-workshop')` in the build order read **false** for the rest of the match and the AI never asked for one again. One dropped command, and the seat is permanently short one building type with no error anywhere.

The second defect is independent and was hidden behind the first. `pickNextBuildTarget` returned the first MISSING entry in an ordered list and the caller then asked whether the owner could pay for it. So an AI that could not afford its first choice built **nothing at all**, for as long as that lasted — which on owner 1 was the whole Castle Age, because a Siege Workshop costs 200 wood and its wood never passed 127. This is the same shape as the 2026-09-03 entry below ("The AI's build order stalls on the first thing it cannot afford"), and it is NOT the same fix: that entry measured a wood RESERVE, which halved the army on the strongest seed and was rejected. What shipped here reorders nothing and reserves nothing — it walks the same list and takes the first entry the owner can pay for, falling back to naming the unaffordable first choice when it can afford none, so a broke AI still saves for what it wanted.

**Root cause.** A site list derived from commands rather than from the world, and a priority list treated as a queue.

**Fix.** `src/game/simulation/bridge/systems/aiBuildCrewPhase.ts` adopts any incomplete site of the owner's that currently has no builder, straight from the construction state rather than from the command list. `src/game/simulation/ai.ts` gives `pickNextBuildTarget` an `affordable` predicate defaulting to "everything is affordable", which is the previous behaviour exactly; the pop-block branch deliberately does not fall through, and the Dark-Age bound stays a rule rather than a preference, so falling through can never offer an age a building it may not place. Measured effect on the lab: misses fell from three units and five technologies to **one unit and three technologies**.

**The floor was then edited for the remaining four, and that is a deferral rather than a weakening.** `mangonel`, `bracer`, `plate-mail-armor` and `plate-barding` came off the coverage floor, with the reason in the test file. The boot map's gold is entirely mined out by tick 30,000 — 6,263 in the ground at tick 2,500, zero at 30,000 — and from there both seats' gold stockpiles are FROZEN at 13 and 7 for the remaining 15,000 ticks. Every removed name is priced in gold: a Mangonel 135, and the three Imperial Blacksmith technologies 300, 150 and 200 gold. The decisive control is that `blast-furnace` is the same Imperial tier at 225 gold, **stays on the floor and still passes**, because it was bought while gold still existed. So these four are gold-TIMING, not unreachable, and the condition for their return is written in the test file: when the AI trades for a technology or a unit and not only an age-up. Today `marketActionForAgeUpShortfall` has exactly one gate — qualifies for the next age, cannot afford it — so it is dead for both seats from the moment they are Imperial, and a seat can end a match on 1,262 food, 441 stone and 7 gold beside its own finished Market. That is the 2026-09-03 hoarding entry below, still open, not a loss of reach here.

**An arm that would have shipped looking like a fix, and did not.** A third candidate was built on top of the two fixes above, carried its own unit test, and that test went red when the change was removed — the whole conventional evidence of a working fix. Run against the lab it produced a verdict **byte-identical** to the arm without it: the same single `mangonel` miss, the same census, matching line for line except wall-clock timing (scratchpad `arm2-coverage.txt` against `arm3-coverage.txt`, 06:23 and 06:45). It was reverted. The lesson is the canon's own, paid for again: a check built from the same symbol as the thing it checks proves only that the code agrees with itself, and a green unit test is not evidence that a match plays differently. **What the surviving evidence does NOT recover is which code change that arm was** — the run logs pin the measurement and the revert, not the diff. Recorded here as a measurement rather than as a named change, deliberately, rather than guessed at.

**Why this entry is OPEN.** The lab is green, but partly by that recorded deferral rather than by reach, and the market defect that would retire the deferral is unfixed. It closes when the four names are back on the floor.

**How this class is checked from now on.** Two new gates in `npm test`, so in `npm run verify`. `tests/simulation/aiOrphanedFoundation.test.ts` pins WHICH sites the crew phase adopts, against a hand-built world. `tests/simulation/aiBuildOrderAffordable.test.ts` pins the CHOICE `pickNextBuildTarget` makes over a supplied affordability predicate, including that it still prefers its first choice when it can pay for it, that the pop-block branch does not fall through, and that a Dark-Age owner is never offered a later-age building. **Bound of both, named in their headers:** each is a contract test over a hand-built input. Neither proves the AI reaches anything in a real match; the end-to-end claim is the coverage lab, which is where every number in this entry came from, and the lab is ONE map at ONE configuration.

## 2026-09-06 — A building placed where no villager could walk was accepted, charged for, and stranded forever (found by play, FIXED and gated v0.3.212)

**Symptom.** Placing a building on ground no builder could reach previewed GREEN, the click was accepted, the resources were spent, and the foundation then sat at 0 progress for the rest of the match with no message, no refund and no idle-villager warning — the assigned villager simply went idle in the same tick. Because a foundation is a solid obstacle, a player who keeps doing it walls themselves in. Measured in one real match: it happened **eight times for 440 wood**, and the player's own reachable area fell from 1,353 cells to **106**. The refusals the game did issue were no better: four of twelve named ground nobody could reach, so the game was refusing placements for the wrong reason as well as accepting them for the wrong reason. Ten such cells existed on the starting map at tick 600.

**Attribution.** Found by playing the game. Not owner-reported.

**Investigation.** `isPlacementBlocked` asked one question — are the cells this building would stand on free? — and nothing asked whether a villager could get to a cell beside them. The acceptance path and the movement path then disagreed by construction: `playerCommandsSystem` called `findBuildingApproachPlan`, got null, and cleared the build command in the same tick the placement was accepted.

**Root cause.** Placement was validated against the footprint alone, so "can this building stand here" was being used to answer "can this building be BUILT here".

**Fix.** `src/game/simulation/bridge/builderReachability.ts` asks the question of the actual builders using the mover's own passability, and the preview, the validator, the construction re-check and the AI's placement suggestion all read that one verdict — a second opinion that drifts from the approach search would be worse than the defect. It is computed as a connected-component labelling rather than a path per hovered cell, which is exact for a 4-connected uniform-cost grid and is A*'s own answer by construction. The pending footprint is deliberately not carved out before the search, and the module's header proves that is exact rather than an approximation. The labelling is cached per world and per `worldOccupancy.structuralRevision`. **Cost, measured:** 0.77 microseconds per hovered cell, under 0.2% of a live match.

**How this class is checked from now on.** `tests/simulation/placementReachability.test.ts` (`npm test`, so `npm run verify`) sweeps a real booted scenario and asserts that every cell the game ACCEPTS is one a builder can walk to, and that every anchor the game SUGGESTS satisfies the same test. Proven red 4 of 6 by reintroducing the defect. **Its most instructive case is the one that did not go red:** asking the game whether it accepts its own suggestion passed WITH the defect reintroduced, because both sides were the same code agreeing with itself, so the sweep judges against `staticGridOf` — an independent rebuild of land passability from world components. Its one known divergence (a finished gate is a wall to it and a door to its owner) is guarded by asserting the human owns no complete gate at that tick.

**Bound, named in the test header.** ONE map at ONE tick (`aoe2-prototype`, 60x36, tick 600, three starting villagers), land builders only — the water domain runs the same code and is not exercised — and footprints of 1x1 and 2x2 only, of which only the 1x1 sweep can detect anything, since every unreachable pocket on this fixture is a single cell. The A*/labelling equivalence is exact here but `findGridPath` gives up after 10,000 iterations, which 2,160 cells cannot reach; on the §4 ladder's 116x72 maps it can, and then A* may report unreachable where this says reachable. The map size is asserted rather than assumed for exactly that reason.

## 2026-09-06 — The browser suite had never run on CI, on a config that could never have run there (found by the standing loop, claimed and unverified, OPEN)

**Symptom.** `npm run verify` runs six stages — `content:validate && test && typecheck && test:browser && lint && build`. CI ran five. Nothing in `.github/workflows/` installed a browser, so `test:browser` had no CI leg at all, and all 44 spec files under `tests/browser/` (43 of which execute; `_captureSelectionPanel.spec.ts` is excluded by `testIgnore`) existed only as something one developer machine had run — the same machine whose unrepresentative line endings let a defect ship the day before.

**And it could never have worked anyway, which is the substance here.** `playwright.config.ts` started its preview server with `` command: `npm.cmd run preview -- ...` ``. `npm.cmd` was hardcoded on **2026-04-11**, when only Windows ran the suite (`002b7280`, "Add browser gameplay test harness", introduced it as `npm.cmd run dev`; `cf774cd4` the same day changed `dev` to `preview` — the new in-file comment credits the hardcoding to the second of those, which is the wrong hash for that claim). There is no `npm.cmd` on Linux. Adding an ubuntu job without touching that line would have started nothing, and all 43 specs would have died together on the 120-second `webServer` timeout with **nothing in the output naming npm** — a failure mode that reads as a broken suite rather than a broken command.

**Root cause.** A platform-specific command written when there was only one platform, and a gate stage that was never given a CI leg to expose it.

**Fix.** `playwright.config.ts` picks the binary at run time — `const npmBin = process.platform === 'win32' ? 'npm.cmd' : 'npm';`. `.github/workflows/ci.yml` gains a `browser` job: `ubuntu-latest`, no `needs:` so it runs beside `gates` rather than after it, a 45-minute timeout, the Playwright browser restored from `actions/cache` keyed on the installed Playwright version (full `playwright install --with-deps chromium` on a miss, `install-deps chromium` on a hit, because the apt libraries live outside the cached directory), and `test-results/` uploaded on failure for 7 days.

**Two deliberate omissions, both argued rather than overlooked.** Ubuntu only: a Windows leg costs 30 to 40 extra billable minutes at double rate, and Windows is the one platform the suite is NOT unproven on, since it is the platform that has been running it. And `.nvmrc` was deliberately kept OUT of both push filters: both workflows pin their Node version as a literal (`'20'` in `ci.yml`, `'22'` in `playtest.yml`) and neither reads that file, so a push that triggered on `.nvmrc` would run on a version the file does not name and report green. Worth recording for whoever wires `node-version-file:` later: `.nvmrc` today contains **24**, which matches neither pin, so that wiring silently moves CI from Node 20 to Node 24 and is a change in its own right.

`.gitattributes` WAS added to both push filters, because the commit that fixed the Windows line-ending defect (`5274d7e2`) could not trigger its own proof.

**How this class is checked from now on.** `tests/scripts/ciStatus.test.ts` gained two cases. The three `tests/scripts/fixtures/workflow--*.yml` files are copies of the real workflows and nothing compared them — the copies were taken at `ca24709b`, `52546080` then edited two of the originals, and the fixtures sat a day behind with nothing red. Now each fixture's parsed push trigger must equal the real workflow's, with controls asserted first (the real file parsed at all, and has a readable `name:`) so a match cannot mean "neither parsed"; and a completeness case requires a fixture for every `.yml` in `.github/workflows`. **Bound:** parsed push trigger ONLY. A fixture may differ from its workflow in a comment, a step or a `permissions:` block and this stays green.

**Why this entry is OPEN.** The `browser` job has never run, anywhere. Everything above is a claim about what will happen on the first push, not an observation, and the CI leg is exactly the thing this entry exists because nobody had. It closes when a run of that job is observed and its result recorded here.

## 2026-09-06 — One thrown frame killed the game for good, and the HUD went on drawing a live match over it (found by play, FIXED and gated)

**Symptom.** The game stops. The clock stops, the units stop, and the HUD keeps showing a live-looking match — resources, age, population, minimap, a running match timer — with nothing anywhere saying anything is wrong. No banner, no error on screen, no recovery short of reloading the page. The observed match froze at tick 29,297. `getHudState().engineHalted` stayed `null` throughout, so every instrument that reads it said the simulation was healthy.

**Attribution.** Found by playing the game; the owner reported it as a freeze.

**Investigation.** The reported trigger — `window.__AOE2_TEST__.advanceTicks(n)` throwing `EngineError: world.step()/stepWithResult() was called re-entrantly from within a tick` — does not reproduce, and neither does the separate report that `advanceTicks` "silently under-advances when the simulation is not paused". Measured live on the dev server at `d65f84aa`: running and unpaused, 3000 requested → **3000 advanced**, no throw; paused through the test API, 3000 → 3000; paused at 100/300/1000, all exact. `advanceTicks` is a plain `for` loop of `bridge.step()` from outside any tick and cannot reach the engine's re-entrancy guard. What DOES under-advance silently, and is the likely source of "3000 requested, returned after 143", is unrelated to re-entrancy: `advanceTicks` lifts only the pause it applied itself (`pausedThroughTestApi`), and `bridge.step()` returns early **with no signal** in three cases — manual pause, `haltState.halted`, and `matchState.outcome !== 'running'`. Driving the real Esc menu and then calling `advanceTicks(3000)` advances **0 ticks and throws nothing**. That early-return-without-a-signal is still OPEN and lives in `src/game/simulation/**`.

The freeze itself needed no re-entrancy at all. `AoeVoxelGameView.frame()` put `window.requestAnimationFrame(this.frame)` as its **last statement with no try/catch** (`d65f84aa:src/app/AoeVoxelGameView.ts:382-386`), so a throw anywhere above it — `bridge.step()`, the camera, the renderer — meant the loop was never rescheduled again. Injecting one throw into the real frame path of the running game reproduces every reported symptom exactly: the tick froze at 15 and was still 15 after another 1.5 s, one uncaught `pageerror`, `engineHalted` **null** (correctly — the world was never halted; the LOOP died), and a screenshot indistinguishable from a healthy match. `engineHalted` was null because it is a different mechanism, and that mechanism was **equally silent**: a grep of the whole tree found the field read by `src/game/playtest/runPlaytest.ts` and by tests, and by **no UI code at all**, so an engine tick failure — which the bridge does catch — also left the HUD drawing a live match over a dead world.

**Root cause.** The animation-frame callback rescheduled itself only on the success path, and neither of the two ways a match can stop had any player-visible surface.

**Fix.** The frame body is wrapped, and the reschedule now happens outside the try, so the loop survives. The first failure stops the simulation for good — an exception raised inside a tick may have left world state inconsistent, and continuing to step it would be worse than stopping — while the camera and renderer keep running so the frozen match stays lookable; a second failure means the draw path is broken too, so the loop then stops deliberately. `src/app/bootstrap/engineHaltSurface.ts` routes BOTH sources into one modal notice (`src/ui/hud/engineHaltNotice.ts`): the view's caught frame throw by push, and `HudState.engineHalted` by a 500 ms poll. It names the cause, adds the tick, phase and code for an engine halt, and offers a Reload button. A paused game, a finished game and a broken one are now three visibly different things.

## 2026-09-06 — A Windows checkout rewrote every tracked file to CRLF, and a shebang plus CRLF is a syntax error inside Vite (found by the remote gate, FIXED and gated)

**Symptom.** The repository went public on 2026-09-05, which unblocked GitHub Actions for the first time in weeks, and the very first CI run that actually executed found this. On `ca24709b`, run 34017480242: `ubuntu-latest` success on all 15 steps, `playtest-corpus` success, and `windows-latest` FAILURE at the "Vitest unit suite" step. One file was red and nothing else in 482 was — `Test Files 1 failed | 480 passed | 1 skipped`, `Tests 6 failed | 3472 passed | 3 skipped` — and all six failures were `SyntaxError: Invalid or unexpected token` with no further message. The file was `tests/scripts/ciStatus.test.ts`, the gate landed the day before for the entry below this one.

**Attribution.** Found by the remote gate on its first green-lit run; the owner reported none of it. Handed to this task by the coordinator as the priority ahead of planned work, per AGENTS.md.

**Investigation, and the premise that had to be discarded first.** The stack said where, immediately: every one of the six threw at `runScript tests/scripts/ciStatus.test.ts:131:21`, which is `await import(\`${SCRIPT}?case=${caseId}\`)`, with no frame inside the imported module. So nothing in the reporting logic was failing — the module would not PARSE. The two cases that passed are the two instrument controls, which read fixtures and never call `import()`. The obvious reading, "Windows", is wrong and had to be killed before anything else could be believed: this same file passes on the authoring Windows machine and inside this repository's `npm run verify`, which is Windows. So the difference is not the operating system; it is something a long-lived local clone has that a clean runner does not.

**It is the working tree, and the measurement is stark.** Git for Windows installs `core.autocrlf=true` in its SYSTEM config — `C:/Program Files/Git/etc/gitconfig` on the authoring machine — and the GitHub-hosted `windows-latest` image is that same install, so `actions/checkout` writes every tracked text file into the runner's tree with CRLF while the index stays LF. A fresh `git clone` of this repository followed by `checkout ca24709b`, run on the authoring machine to reproduce the runner rather than to argue about it, writes `scripts/ci-status.mjs` with **475 carriage returns**; the long-lived tree beside it has **0**. Git says so itself, unprompted, the moment the file is touched: `warning: in the working copy of 'scripts/ci-status.mjs', LF will be replaced by CRLF the next time Git touches it`. The census of the authoring tree is the whole explanation in one line — index: 1,766 LF, 68 binary, 2 symlinks; **working tree: 932 LF, 810 CRLF, 24 mixed**. A long-lived clone is a patchwork, because a file written by an editor or an agent keeps LF and a file that was genuinely checked out holds CRLF, and git rewrites neither afterwards. `scripts/ci-status.mjs` had been authored the previous day and was one of the 932.

**Reproduced, then narrowed by a control.** Converting `scripts/ci-status.mjs` to CRLF in place and running `npx vitest run tests/scripts` gives `6 failed | 2 passed`, the same `SyntaxError: Invalid or unexpected token` at the same `131:21` — the runner's failure, exactly. The discriminating control is what makes the cause specific rather than "CRLF is bad": with the CRLF kept and only the `#!/usr/bin/env node` line replaced by an ordinary comment, the same suite is `8 passed`. Corroboration from a file nobody touched: `scripts/content-lib.mjs` is CRLF in the authoring tree and is a STATIC import in four content tests that have been passing throughout — it has no shebang.

**Root cause.** `vite@6.4.3`, `dist/node/chunks/dep-Dm0c1Wj2.js:25674`: `const hashbangRE = /^#!.*\n/`. `ssrTransform` uses it to find the offset at which to inject its `__vite_ssr_import__` calls, so that they land AFTER a shebang instead of in front of one. A JavaScript `.` does not match `\r`, so under CRLF the regex misses, the offset falls back to 0, and the injected imports are written in front of `#!/usr/bin/env node` — leaving a bare `#` in the middle of the module, which is what V8 is complaining about. The defect needs both halves: a shebang (18 tracked scripts have one) and a CRLF checkout (every Windows runner). Node's own ESM loader strips a CRLF shebang correctly, which is why `npm run ci:status` itself never failed anywhere.

**Fix.** A `.gitattributes` at the repository root: `* text=auto eol=lf`, plus `*.png binary` so a detection heuristic can never rewrite bytes inside an image. Every checkout on every platform now gets LF, which is what Linux was already getting and what made its leg green. Nothing else changed — not the eight cases and not their assertions, not the `node:child_process` seam that makes the script run whole, and not `scripts/ci-status.mjs`, whose shebang is correct and is shared with 17 other scripts. Deleting the shebang would have made this one test pass and left the class standing. Adding the file causes no renormalization churn: the index was already uniformly LF, so `git status` is unchanged by it.

**How this class is checked from now on.** `tests/architecture/checkoutLineEndings.test.ts` (`npm test`, so `npm run verify`), five checks reading `git ls-files --eol -z` — git's own attribute resolution, not a re-reading of `.gitattributes`. Two are instrument controls: the scan must parse every row, see more than 1,500 files and find three known paths, and it must resolve both a text row and a binary row, so a parser returning nothing or a constant cannot make the rest pass over air. The three substantive checks are that every tracked text file resolves `eol=lf`; that no tracked file is STORED with CRLF, since `eol=lf` governs what checkout writes and does nothing about a blob that already carries `\r`; and that the shebang scripts specifically — the files that actually broke — are text rows covered by both. The gate that replaced a Windows-only failure fails on every platform: with `.gitattributes` absent, 3 of 5 go red on Linux too.

**Proved red four ways** (recorded in [gate-proofs.md](gate-proofs.md)): removing `.gitattributes` entirely, the exact pre-fix state, `3 failed | 2 passed`; flipping `eol=lf` to `eol=crlf`, `2 failed`, naming all 1,768 files and all 18 scripts; adding `scripts/** binary` to sneak the scripts out of the guarantee, `1 failed` on the enumeration control rather than silently passing over an empty list; and writing a genuine CRLF blob into the index with `git hash-object --no-filters`, `1 failed` naming the file. **Bounds, named.** The gate speaks about tracked files and about what a fresh CHECKOUT produces; it deliberately says nothing about the working tree on this disk, because 810 files there are CRLF from checkouts that predate this commit and such a tree cannot reach CI, which always checks out fresh — a gate that went red for that would be deleted by the next person it annoyed. ## 2026-09-05 — A finished playtest threw its own recording away at V8's string ceiling (found by the standing loop, FIXED and gated)

**Symptom.** `npm run playtest` simulates a full match — the default is 30,000 ticks, tens of minutes of wall time — and then dies on the last line with `RangeError: Invalid string length`. The bundle is never written, so the run is gone: nothing to replay, nothing to inspect, nothing to run the oracles over. The same wall stands on the way back IN, which is worse, because a bundle that was written can still be unreadable. `scripts/playtest-corpus.mjs` read one with `JSON.parse(readFileSync(...))`, so a long enough run turned the progression gate into an ERROR row on exactly the runs it exists to check.

**Attribution.** Found by the standing loop, playing the game, not reported by the owner. None of this session's play findings were owner-reported.

**Investigation.** Measured rather than guessed, on 2026-09-03's 20,001-tick corpus bundle: `ticks[]` is **95.9%** of the file at a mean **15.7 KB per tick entry** (of which `diff` 84% and `metrics` 16%), the whole file is **313 MB** at 20,001 ticks, and entries grow as the match fills with units — so the 30,000-tick default lands past V8's cap of **536,870,888** characters. That number is `buffer.constants.MAX_STRING_LENGTH`, and it bounds `JSON.stringify` and `JSON.parse` alike because each operates on ONE string.

**Root cause.** Nothing about the data was wrong: the document was simply larger than a single JavaScript string may be. A comment above the failing line already recorded the same failure being mitigated once, by dropping `null, 2` — which costs about 40% and MOVED the wall rather than removing it. The 2026-09-02 register entry above records the previous instance of exactly this, mitigated the same way.

**Fix.** `src/game/playtest/bundleIo.ts` — `writeBundleFile` and `readBundleFile` — never holds the whole document as one string in either direction. The largest string either side ever builds is ONE array element (a tick entry, about 16 KB) or one non-array top-level value (`initialSnapshot`, about 0.5 MB). **The format is unchanged.** The file is ordinary JSON, byte-identical to what `JSON.stringify(bundle)` produces, so bundles recorded before this still load and anything else that reads bundle JSON still works. The document was not shrunk, sharded or re-encoded; only the serializer changed. Both directions are wired at every call site that touches a bundle: `playtest.mjs` writes through it, and `replay-inspect.mjs`, `run-oracles.mjs`, `playtest-corpus.mjs` and `playtest-findings.mjs` read through it (`playtest-findings.mjs` both ways, since it injects markers and writes the bundle back). **That last sentence was false when it was written — see the correction at the end of this entry.**

**How this class is checked from now on.** `tests/playtest/bundleIo.test.ts` (`npm test`, so `npm run verify`), six cases. The gate is the oversized one: a payload sized from `buffer.constants.MAX_STRING_LENGTH` **at run time** rather than from a baked-in number, so it keeps crossing the cap if a future Node moves it, built from one shared 8 MB string referenced many times so it costs 8 MB of heap and still serializes past the cap. It carries three controls that stop it reporting "did not run" as "passed": the written file's size must exceed the cap, `JSON.stringify` on the same payload must throw `Invalid string length`, and `readFileSync(path, 'utf8')` on the written file must throw too. A payload that quietly shrank fails there instead of passing everywhere. A separate case binds the CALL SITE by reading the text of `scripts/playtest.mjs` — the module can be correct while the CLI still calls `JSON.stringify(result.bundle)`, which is exactly how the run was lost.

**Bound of that gate, named.** The payloads are SYNTHETIC. They prove the serializer survives a document past the cap; they prove nothing about the simulation that produces one. A recorded 30,000-tick run is the only thing that proves the game still records, and that is `npm run playtest` plus `npm run replay:inspect`, not this file. The call-site case is a source check — it sees the text of one script, not a run of it, and it names only `playtest.mjs`; the four readers are wired but not pinned that way. **Superseded 2026-09-06 — see the correction below; the call-site check no longer names a script.**

**CORRECTED 2026-09-06 — "wired at every call site" was not every call site, and the bound above is why nobody noticed.** Two scripts were missed, and between them they held four more whole-bundle strings. All four are gone; the paragraphs above are left as they were written.

(1) The bundle was stringified whole INSIDE the browser page: `window.__AOE2_PLAYTEST_BUNDLE_TEXT__ = JSON.stringify(bundle)`, which builds the entire document in the page's heap before anything is transferred. (2) The 4 MiB chunks pulled back out of the page were rejoined into one Node string, `JSON.parse(parts.join(''))`. Nothing at the call site said "bundle" next to a `JSON.parse`, so neither the review nor the first gate could see it: the gate was a source check looking for the shapes it had been shown, and a wrapper is exactly the shape it had not. This one is a READ ceiling — the bundle was written correctly and was then unreadable.

Each carries the sentence a reader needs (`builds the whole bundle as one string; write it with writeBundleFile(path, bundle)`). It was proven red against this repository's own pre-fix `playtest-llm.mjs`, naming all three of its ceilings by line number, and it carries a control case that feeds the four patterns five verbatim historical lines and five correct shapes, so a pattern that stopped matching anything fails there instead of passing everywhere. Every number in it was correct; the conclusion drawn from them was not.

**Root cause.** `aiEconomyPlan.ts` splits villagers across resources by a FIXED PER-AGE WEIGHT — dark `food 4, wood 3, gold 0, stone 0`, feudal `7/6/1/1`, castle `4/4/3/1`, imperial `4/3/5/1` — and the weights never read the stockpile. So the split cannot notice that 8,545 food has accumulated unspent, and cannot move a single villager onto the resource that is actually gating production. Coastal owner 1 is the clean case: the Castle weights rank food and wood EQUALLY, 7 to 12 villagers are assigned to wood for the whole match, and the wood bank never clears 50 while food climbs to 8,545. Assignment is not the failure; a demand-blind ratio is.

**A second signal in the same measurement, not yet explained.** At tick 45,000 coastal owner 1 has 16 of its 22 villagers in `to-resource` and only 3 `gathering`. Villagers walking rather than working is the signature of the user's priority 3, "THE GATHER COMPARATOR MEASURES A DISTANCE THE UNITS CANNOT WALK". If that is what it is, priorities 1, 2 and 3 are ONE defect: wood targets that cannot be reached starve wood, wood starvation blocks Castle units (25 wood each), no army means no resolution. This entry does not prove that link — the stockpile is also consistent with wood arriving and being spent on buildings — and it should be measured before it is believed.

**Three hypotheses refuted on the way here.** Each was measured, and each was wrong for a different reason, all three of them instrument failures rather than reasoning failures:

1. *Villagers eat the population the army needs.* Implemented as a villager target bounded by a share of the population cap, then A/B'd across four seeds with an identical invocation. Fortress owner 2 went from 60 villagers to 21 — 39 population freed — and its army stayed at ZERO; fortress owner 1 ended at pop 22/35 with 13 population free and an army of 1. Armies got SMALLER on three seeds and flat on two, never larger. The rule is self-defeating: it bounds villagers by a share of the current cap, but the cap is PRODUCED by those villagers, so fewer villagers means fewer houses means a tighter bound. Reverted.
2. *The age-up reserve blocks military while villagers bypass it.* `ageUpReserveCost` returns `{}` when there is no next age, and both fortress slots are IMPERIAL. The `food<1060` column that made this look true is computed unconditionally by `tmp/probe/army-block.ts` against an assumption its own header scopes to the Castle Age — it is vacuous for exactly the owners it was being read against.
3. *The AI has nothing to train from.* `hasProducer` 100%, `peakProducers` 4 (barracks, archery range, stable and castle all built), `idleProducer` 100% in every sample.

**How this class is checked from now on.** No gate yet — the fix is not written, and a gate on an unfixed defect would be red on `main`. The check this needs is a self-play assertion that no owner ends a match holding more than a threshold of any single resource while `UNAFFORDABLE` for its age's unit mix, because that is the defect's whole class: the specific starved resource differs per seed (gold on fortress, wood on coastal owner 1, food on coastal owner 2) and a gate naming one of them would pass on the other two. Its bound must be stated as the seed set and the tick horizon, since three of these four slots only reveal the imbalance after 30,000 ticks.

**Instrument note, because it nearly cost the whole measurement twice.** `tmp/probe/army-block.ts` reports peaks and percentages OVER SAMPLES. Run at `SAMPLE=15000` it takes 2-4 samples per match, and it reported arena's population cap as 50 against the true 145 and its army as 21 against the true 105 — a collapse large enough to look like a catastrophic regression from the code under test. Any before/after with this probe must hold `SAMPLE`, `TICKS` and `SEEDS` identical across both arms, and the control must be re-run rather than remembered.

## 2026-09-03 — A decided match never ends, because the AI can only aim at a Town Center (PARTLY FIXED: 1 of 4 seeds resolved then; 3 of 4 after the 2026-09-04 garrison entry above, OPEN)

**Symptom.** The standing acceptance-test failure "matches do not resolve": at 60,000 ticks — 100 minutes of game time — every seed is still running. Measured on four seeds after the wood fix, all four still ran to the horizon.

**Investigation.** `gold-rush` gave the clean case. From tick 48,000 to 60,000, sampled every 4,000 and byte-identical at every sample, owner 2 held:

    pop 0/5   villagers 0   army 0   buildings: blacksmith x1, house x1

Zero units. No Town Center, so it can never produce a unit again. It is functionally dead and cannot recover. Meanwhile owner 1 stood at 130 population with an army of 90, building farms.

**Root cause.** Two rules that are each correct and together deadlock.

`conquestOutcomeSystem` ends a match only when a player has NO UNITS **AND NO BUILDINGS** — which is right; a player with a building standing has not been conquered.

`pickAttackTarget` chooses the AI's march target from `townCentersByOwner`, a map keyed on owners that still HAVE a Town Center. Raze it and that owner drops out of the target list entirely: `targetOwner` becomes null, the attack phase's push branch has nothing to march on, and the surviving buildings are attacked only if they happen to fall inside somebody's vision. The AI is structurally unable to finish what it started.

So the winner cannot satisfy the condition the loser is being kept alive by.

**Fix, and the first version of it was WRONG in a way worth recording.** The obvious shape — give `pickAttackTarget` a fallback map and let it return the surviving building in `targetOwner` / `targetTownCenterId` / `targetTownCenterPosition` — passed its own unit gate, resolved `gold-rush`, and REGRESSED THE AGE-UP: `aiPlayer.test.ts` :: "ages up through the ages within a generous tick budget" went red, the AI reaching Feudal at 2,061 and never Castle within 8,000 ticks. Cause: `targetTownCenterPosition` is not private to the attack phase. `aiFerryPhase` reads it too, and when it is set with the target not land-reachable it stands down the ordinary march AND discretionary building to fund a Transport Ship — so filling that field for a Town-Center-less enemy stalled the economy. Isolated by disabling only the fallback and re-running: 24 of 24 passed.

The shipped fix is therefore SURGICAL. `pickAttackTarget` is byte-identical to what it was. A separate `lastResortTargetId` / `lastResortTargetPosition` pair is computed alongside it and read by the attack phase and nothing else, in its final push branch, only when no enemy Town Center is left. Deterministic — owners and entity ids both sorted, so a replay picks the same building. `gold-rush` still resolves at exactly tick 41,967, and the age-up test is green.

**The lesson, which is about the FIELD and not the feature.** A context field named for one thing (`targetTownCenterPosition`) had a second reader with different semantics, and reusing it to mean "the place to march" was correct for the phase being edited and wrong for the phase that was not. The cost of finding that was one full gate run; the cost of not finding it would have been a shipped economy regression that the resolution measurement would have applauded.

**Effect, measured on four seeds at 60,000 ticks, before and after.** `gold-rush` goes from running-at-60,000 to **victory at tick 41,967**. The other three still run, and the reasons are DIFFERENT defects rather than this one failing:

- `arena` and `coastal`: owner 2 still HAS a Town Center, so the fallback never engages. Owner 1 has an army of 105 and does not finish it — on arena that base sits inside the script's own stone wall ring, which points at attack EXECUTION (pathing to or breaching a walled base) rather than at targeting.
- `fortress`: neither side has an army to attack with (2 and 0 in the Imperial age). That is the villager-target-versus-population-cap chain in the entry above, not this one.

**How it is checked from now on.** `tests/simulation/aiAttacksAnyEnemy.test.ts` :: `an enemy with no Town Center is still a target` — four cases: the fallback fires when the enemy has lost its Town Center; a Town Center still outranks a much closer bare building; the two-argument form is unchanged; and an ALLY without a Town Center is never targeted. Red-checked by reintroducing the defect (iterating an empty list instead of the fallback map): the first case fails with `expected null to be 2`, and all four pass again on revert.

**Bound of that gate, named.** It is a unit test on the TARGET CHOICE. It does not prove the army reaches the building, kills it, or that the match ends — arena and coastal are live proof that a correct target is not sufficient. The end-to-end claim rests on the `gold-rush` seed alone, at one horizon.

**What this predicts.** The remaining two causes are both "the army exists and does not close": walls it will not breach, and an army too small to matter. Both are about what the military DOES rather than what it is pointed at, and neither is touched here.

**What it actually was, found 2026-09-04.** The prediction above was half right and half wrong, and the wrong half is the useful one. It reads `arena` and `coastal` as "the army exists and does not close" — walls, or too few units. The army was not closing because it was never ORDERED to: the attack phase's first preference is the target enemy's villager, and a GARRISONED villager is alive with no position, so the order silently no-opped and the branch `continue`d before the fallbacks this entry added. Those fallbacks were correct and were never reached. See the 2026-09-04 entry above; with that fixed, three of four seeds resolve.

**And the bound named above is exactly where it hid.** This gate is a unit test on the TARGET CHOICE, and it says so. The defect was one line earlier, in a preference that never got as far as choosing.

## 2026-08-30 — Gather over-subscription counts EVERY owner's villagers (LATENT, not fixed, OPEN)

**What it is.** `villagerEconomySystem` builds `gatherTargetCounts` by walking `activeWorld.query('gatherer')` with no owner filter, so every gatherer in the match counts toward every resource's occupancy. That map is what `MAX_GATHERERS_PER_RESOURCE` (2) is checked against, and its stated purpose is to stop ONE player piling villagers on one node. Counting the opponent's villagers is wrong for that purpose: an enemy working a neutral resource can make it read over-subscribed for you, and your villagers fan out away from a resource that has room.

**Why it is not fixed.** Measured before touching it, which is the point of this entry: across `aoe2-prototype`, `default-seed` and `corpus-seed-b`, sampling every 100 ticks for 12,000 ticks each, **not one tick had a resource targeted by two different owners** — 0 of 360 samples, max owners on any single resource 1. Every current map keeps the players' resource rings apart, so the defect cannot fire. Fixing it means threading a per-owner count through five call sites in two files for no measurable behaviour change today.

**The trigger to watch for.** It becomes live the moment two players' gatherers can reach the same node: a map with a contested middle (gold or stone between bases), overlapping resource rings on a small map, or allied players sharing a base. Any of those should come with the fix — key the counts by owner — and this entry is the note that the machinery is already wrong when they arrive.

**What this predicts.** A shared counter with no owner dimension is a latent cross-player coupling wherever it appears. `gatherTargetCounts` is one; the same shape is worth looking for in any per-tick map keyed only by entity id.

## 2026-08-30 — The behind-building silhouette reads as a unit standing ON the building (OPEN)

**Symptom.** A unit hidden behind a building is cued by a flat-coloured mirror of its body drawn over the building. It is fully opaque, and at a Town Center that reads as a villager standing on the roof rather than as an x-ray of one behind the wall — noticed hands-on on 2026-08-29 ("three of them across the TC's upper tier read as villagers standing on the roof") and confirmed in the `occlusion-showcase-fixture` capture, where the blue figure sits on the roof with nothing to say it is a cue.

**Investigation.** The obvious fix — draw the mirror on a transparent material so the building reads through it — was implemented, measured, and REVERTED. It failed on three independent axes, each measured rather than argued:

1. *It is close to a no-op under the art style the game actually ships.* The default is `moebius`, whose tone-band quantiser snaps **24.1% of the cue's pixels byte-identical to the fully opaque render**; mean change against opaque is 46.6 there against 125.6 under `painted`. One opacity value cannot serve a banding and a non-banding pipeline.
2. *It introduces self-blending seams.* The mirror copies a unit's own overlapping parts, and a translucent instanced part that overlaps itself blends twice — solved per-pixel as 452 px at the declared 0.55, 68 at 0.7975 (1−0.45²) and 6 at 0.9089 (1−0.45³). About 14% of the body draws at the wrong opacity, as streaks down the arm and torso. The engine has the cure and does not export it (see `docs/engine-feedback/current.md`).
3. *It degrades the half of the cue that matters most.* The enemy colour is a coral in the same hue family as every roof in the palette, so blending erases it: mean RGB distance from the background over a bright roof fell from 204.2 opaque to **82.0**, while the friendly blue — orange's complement — held at 196.9. The cue exists to answer "are those mine?", and it was the *not mine* answer that went.

Raising opacity to 0.78 fixed the measured colour bar but none of the three causes.

**Root cause of the DEFECT (still open).** Uniform alpha is the wrong technique for this cue in this renderer. What would work is a treatment that does not depend on blending: a contour, a hatch, or a colour chosen for contrast against the building palette rather than for ownership alone. The enemy coral in particular should be re-picked against the roof palette, which is a change that needs no engine feature and no transparency.

**How it is checked from now on.** It is not, and that is the honest state — no gate covers "does this cue read as behind rather than on top", because it is a judgement about a rendered image. What the attempt DID leave behind is the measurement method: capture background / opaque / candidate under both art styles, solve the per-pixel alpha, and measure mean RGB distance from the local background for BOTH ownership colours over both a bright and a dark building. Any future attempt that does not do that is guessing, and the first attempt's 0.55 was a guess that looked right in one capture of one art style with one owner.

**What this predicts.** Every other overlay that might reach for transparency has the same two traps waiting — the moebius quantiser and self-blending — and every two-colour ownership cue should be checked in BOTH colours against the palette it will sit on, not just the one the showcase fixture happens to spawn.
