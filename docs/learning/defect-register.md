# Defect register

The standing list of what the gates could not see. One entry per defect that reached a build: the symptom as it presented, what the investigation found, the root cause, and the check that covers the defect's whole CLASS from now on.

Unlike a lesson, an entry stays after it becomes a gate. The register is not a to-do list — it is the record of where defects came from, which is the best available guide to where the next one is.

**What lives here, and what rolled over.** This file holds the 12 most recent CLOSED entries plus every OPEN one, whatever its age, newest first. Everything older and closed is in [`defect-register-past.md`](defect-register-past.md), moved verbatim. An OPEN entry never rolls over — it leaves this file by being closed, not by ageing, and a heading that says the defect is still live is not a closure however it spells it: "(LATENT, not fixed)", "(PARTLY FIXED: ...)" and "(... still unfixed)" all keep the entry here, and each of those three had been archived once before the gate learned to refuse them. The rollover is done by the task whose new entry pushes this file past 12 closed entries, in that task's own commit, the way the devlog archives its detailed file; never by a later sweep. `tests/architecture/defectRegisterRollover.test.ts` holds all of that. An "entry above" or "entry below" written before the split may name an entry that now lives in the archive, and a rollover can strand a pointer in either direction; the archive's header lists the seven that cross today.

## 2026-09-06 — A Windows checkout rewrote every tracked file to CRLF, and a shebang plus CRLF is a syntax error inside Vite (found by the remote gate, FIXED and gated)

**Symptom.** The repository went public on 2026-09-05, which unblocked GitHub Actions for the first time in weeks, and the very first CI run that actually executed found this. On `ca24709b`, run 34017480242: `ubuntu-latest` success on all 15 steps, `playtest-corpus` success, and `windows-latest` FAILURE at the "Vitest unit suite" step. One file was red and nothing else in 482 was — `Test Files 1 failed | 480 passed | 1 skipped`, `Tests 6 failed | 3472 passed | 3 skipped` — and all six failures were `SyntaxError: Invalid or unexpected token` with no further message. The file was `tests/scripts/ciStatus.test.ts`, the gate landed the day before for the entry below this one.

**Attribution.** Found by the remote gate on its first green-lit run; the owner reported none of it. Handed to this task by the coordinator as the priority ahead of planned work, per AGENTS.md.

**Investigation, and the premise that had to be discarded first.** The stack said where, immediately: every one of the six threw at `runScript tests/scripts/ciStatus.test.ts:131:21`, which is `await import(\`${SCRIPT}?case=${caseId}\`)`, with no frame inside the imported module. So nothing in the reporting logic was failing — the module would not PARSE. The two cases that passed are the two instrument controls, which read fixtures and never call `import()`. The obvious reading, "Windows", is wrong and had to be killed before anything else could be believed: this same file passes on the authoring Windows machine and inside this repository's `npm run verify`, which is Windows. So the difference is not the operating system; it is something a long-lived local clone has that a clean runner does not.

**It is the working tree, and the measurement is stark.** Git for Windows installs `core.autocrlf=true` in its SYSTEM config — `C:/Program Files/Git/etc/gitconfig` on the authoring machine — and the GitHub-hosted `windows-latest` image is that same install, so `actions/checkout` writes every tracked text file into the runner's tree with CRLF while the index stays LF. A fresh `git clone` of this repository followed by `checkout ca24709b`, run on the authoring machine to reproduce the runner rather than to argue about it, writes `scripts/ci-status.mjs` with **475 carriage returns**; the long-lived tree beside it has **0**. Git says so itself, unprompted, the moment the file is touched: `warning: in the working copy of 'scripts/ci-status.mjs', LF will be replaced by CRLF the next time Git touches it`. The census of the authoring tree is the whole explanation in one line — index: 1,766 LF, 68 binary, 2 symlinks; **working tree: 932 LF, 810 CRLF, 24 mixed**. A long-lived clone is a patchwork, because a file written by an editor or an agent keeps LF and a file that was genuinely checked out holds CRLF, and git rewrites neither afterwards. `scripts/ci-status.mjs` had been authored the previous day and was one of the 932.

**Reproduced, then narrowed by a control.** Converting `scripts/ci-status.mjs` to CRLF in place and running `npx vitest run tests/scripts` gives `6 failed | 2 passed`, the same `SyntaxError: Invalid or unexpected token` at the same `131:21` — the runner's failure, exactly. The discriminating control is what makes the cause specific rather than "CRLF is bad": with the CRLF kept and only the `#!/usr/bin/env node` line replaced by an ordinary comment, the same suite is `8 passed`. Corroboration from a file nobody touched: `scripts/content-lib.mjs` is CRLF in the authoring tree and is a STATIC import in four content tests that have been passing throughout — it has no shebang.

**Root cause.** `vite@6.4.3`, `dist/node/chunks/dep-Dm0c1Wj2.js:25674`: `const hashbangRE = /^#!.*\n/`. `ssrTransform` uses it to find the offset at which to inject its `__vite_ssr_import__` calls, so that they land AFTER a shebang instead of in front of one. A JavaScript `.` does not match `\r`, so under CRLF the regex misses, the offset falls back to 0, and the injected imports are written in front of `#!/usr/bin/env node` — leaving a bare `#` in the middle of the module, which is what V8 is complaining about. The defect needs both halves: a shebang (18 tracked scripts have one) and a CRLF checkout (every Windows runner). Node's own ESM loader strips a CRLF shebang correctly, which is why `npm run ci:status` itself never failed anywhere.

**Fix.** A `.gitattributes` at the repository root: `* text=auto eol=lf`, plus `*.png binary` so a detection heuristic can never rewrite bytes inside an image. Every checkout on every platform now gets LF, which is what Linux was already getting and what made its leg green. Nothing else changed — not the eight cases and not their assertions, not the `node:child_process` seam that makes the script run whole, and not `scripts/ci-status.mjs`, whose shebang is correct and is shared with 17 other scripts. Deleting the shebang would have made this one test pass and left the class standing. Adding the file causes no renormalization churn: the index was already uniformly LF, so `git status` is unchanged by it.

**How this class is checked from now on.** `tests/architecture/checkoutLineEndings.test.ts` (`npm test`, so `npm run verify`), five checks reading `git ls-files --eol -z` — git's own attribute resolution, not a re-reading of `.gitattributes`. Two are instrument controls: the scan must parse every row, see more than 1,500 files and find three known paths, and it must resolve both a text row and a binary row, so a parser returning nothing or a constant cannot make the rest pass over air. The three substantive checks are that every tracked text file resolves `eol=lf`; that no tracked file is STORED with CRLF, since `eol=lf` governs what checkout writes and does nothing about a blob that already carries `\r`; and that the shebang scripts specifically — the files that actually broke — are text rows covered by both. The gate that replaced a Windows-only failure fails on every platform: with `.gitattributes` absent, 3 of 5 go red on Linux too.

**Proved red four ways** (recorded in [gate-proofs.md](gate-proofs.md)): removing `.gitattributes` entirely, the exact pre-fix state, `3 failed | 2 passed`; flipping `eol=lf` to `eol=crlf`, `2 failed`, naming all 1,768 files and all 18 scripts; adding `scripts/** binary` to sneak the scripts out of the guarantee, `1 failed` on the enumeration control rather than silently passing over an empty list; and writing a genuine CRLF blob into the index with `git hash-object --no-filters`, `1 failed` naming the file. Both files restored to identical SHA-256 afterwards.

**Bounds, named.** The gate speaks about tracked files and about what a fresh CHECKOUT produces; it deliberately says nothing about the working tree on this disk, because 810 files there are CRLF from checkouts that predate this commit and such a tree cannot reach CI, which always checks out fresh — a gate that went red for that would be deleted by the next person it annoyed. It says nothing about Vite's hashbang handling: if a future toolchain mishandles LF instead, it stays green. It cannot see a per-clone override applied outside the repository (`.git/info/attributes`, `core.eol`). And it does not prove the runner is fixed — only the next Windows CI run does that.

## 2026-09-05 — The command that checks the remote gate reported an earlier commit's run as the tip's, so a commit with no run at all read as green (found by the standing loop, FIXED and gated)

**Symptom.** `npm run ci:status` is the first thing AGENTS.md tells a session to run, and it prints one line per watched workflow. Each line describes whichever run is newest in that workflow's run LIST — whatever commit that run belongs to. A commit that produced no run is therefore invisible: the command prints a confident verdict about a different commit and nothing says so. Measured on the recorded fixtures: given a pushed commit whose runs API returns `total_count: 0`, the pre-fix script prints `CI: GREEN — 20+ consecutive, latest "Merge: motion smoothing survives a slow machine (v0.3.192)" at 2026-09-03T04:04:53Z` and **exits 0**. AGENTS.md names the principle in as many words — a gate that cannot tell "passed" from "did not run" reports the second as the first — and the instrument built to stop exactly that (the 2026-08-29 entry: 200 red runs over two months behind green local gates) had the failure inside it.

**Attribution.** Found by the standing loop while pushing; the owner reported none of it.

**Investigation, and a premise that turned out to be wrong.** The trigger was real: `39244310` ("Promote the final acceptance gate") was pushed and `gh api repos/{owner}/{repo}/actions/runs?head_sha=3924431040fab4898add984f16af131de13022c3` returns `{"total_count":0,"workflow_runs":[]}` — no run was ever created — and `ci:status` said nothing about it. The first reading was that GitHub had stopped creating runs. **It had not.** Both watched workflows filter their push trigger: `.github/workflows/ci.yml` runs on a push to main only for `package.json`, `package-lock.json`, `.github/voxel-commit` or `.github/workflows/**`, and `.github/workflows/playtest.yml` adds `playtest-corpus.json`. `39244310` changed one file, `AGENTS.md`. No run was due and GitHub was right not to create one. What was wrong is that `ci:status` could say neither thing — not "this commit was never gated, by design" and not "this commit should have been gated and was not".

A second thing was there to be read and was not being read. Where jobs DO exist and never start, GitHub states the reason on the job's check-run annotations, and today's reason was not the assumed one: the jobs of run 34011049865 carry, at `annotation_level: "failure"`, "The job was not started because recent account payments have failed or your spending limit needs to be increased. Please check the 'Billing & plans' section in your settings". The zero-steps/no-runner inference is sound but generic; "your payment failed" and "you are out of free minutes" call for different actions from the owner.

Sweeping the last 25 commits of main with the fixed classifier found no commit that owed a run and lacked one: 4 have their own run, 12 owed none, and 8 are interior commits of multi-commit pushes whose changes were carried into the run at the tip.

**Root cause.** One line, `const latest = finished[0];` in `scripts/ci-status.mjs` at `b1d0a0ff`. The report was bound to the newest entry of a run LIST instead of to a commit; no call in the whole script mentioned a sha. Nothing distinguished "the newest run" from "the run for the thing you are about to build on".

**Fix.** The report is now per commit — the local HEAD and, when they differ, the pushed tip — via `actions/runs?head_sha=<sha>`. A commit with no run of its own gets one of three answers instead of silence: NEVER ASKED (no run was due; the workflow's `on.push.paths`, read out of the workflow file as of that commit with `git show <sha>:...`, matches nothing that changed since the last gated ancestor — exit 0), CARRIED (a later push gated it at its tip; that run's verdict is reported), or UNGATED (a run was due and none exists — exit 1, in the pre-existing "unknown" bucket; red still means red, and COULD NOT RUN still exits 0). An unparsed workflow trigger or an unreadable file list is reported as UNGATED on purpose, because a filter understood only in part would answer "never asked" for a commit that was in fact never checked. GitHub's own annotation is now printed verbatim beside the never-started verdict.

**How this class is checked from now on.** `tests/scripts/ciStatus.test.ts` (`npm test`, so `npm run verify`), eight cases driven from responses recorded off the live repo with `gh` on 2026-09-05, with `node:child_process` as the only seam so the script runs as a whole rather than through a test-only entry point. Five hold the answers apart — UNGATED (the critical one: a pushed commit that changed `package.json`, runs API empty, must name the sha, say UNGATED, and exit 1), NEVER ASKED, COULD NOT RUN with the billing annotation quoted verbatim, GREEN, and RED with steps and a runner. A sixth is the over-fix guard: an interior commit of a multi-commit push must read CARRIED, not UNGATED, or the command would cry wolf on every commit but the tip. Two are controls on the instrument: the fake `gh`/`git` must throw on any command it has no fixture for (a stub that silently returns "" is how a check reports "did not run" as "passed"), and the recorded zero-run and never-started responses must still have the shape the cases depend on. Proved red by restoring `scripts/ci-status.mjs` to `b1d0a0ff`: 6 of the 8 fail, the UNGATED case on `expected +0 to be 1`.

**Bound of that gate, named. Fixtures are not the API.** Every response was captured from the real repo, but they are the projections the script's own `--jq` asks for, not raw payloads — so the suite proves the reporting logic and the exit codes, and proves nothing about whether GitHub still returns these shapes or whether `gh`'s flags still mean what they meant; a field rename on GitHub's side leaves it green. The only check on that is running `npm run ci:status` against the live repo. Beyond that: the YAML reader understands `on.push.paths` as these two workflows write it and refuses anything with `!`, a character class or a brace group (refusing means UNGATED, which is loud, not silent); `origin/main` is the locally cached ref, so a tip nobody has fetched looks like the tip; the filter is evaluated over the diff since the last gated ancestor, which is a stand-in for the push GitHub actually saw and is wrong for a force-push or a rewritten history; a `skipped` or `cancelled` run with no jobs still reads RED, as it did before; and nothing here watches the third workflow, `playtest-corpus-llm`.

## 2026-09-05 — Right-clicking the empty glass of the command bar sent the selected army to a cell hidden under it (found by the standing loop, FIXED and gated v0.3.209)

**Symptom.** On `aoe2-prototype` at 1280x800: select units, then right-click the empty dark glass of the bottom bar to the right of the training-queue cards — page (700, 700). Every selected unit takes a MOVE order to a cell hidden underneath the bar. Three real right-clicks there gave moves to (31,35), (27,33) and (27,35) on a 60x36 map. Left-clicking the same glass cleared the selection instead, and clicking a training-queue card did nothing but deselect the Town Centre. The bar is painted glass and reads as a control surface; it behaved like a hole in the window.

**Attribution.** Found by the standing loop, playing the game, not reported by the owner. None of this session's play findings were owner-reported.

**Investigation.** No engine tool renders the HUD — `replay:inspect`, `diffBundles`/`forkAt` and the path-queue and occupancy probes all read simulation state back out of a recorded bundle, and the question here is which DOM element the browser hit-tests at a screen point. So the instrument is `document.elementFromPoint`, the browser's own hit test, swept over every painted surface, plus real Playwright clicks recorded by a capture-phase listener on the world canvas. On the unfixed tree at 1280x800 with nothing selected, **1,065 of 3,567** painted points inside `.hud-bar` and `.hud-panel--selection` resolve to `canvas.voxel-world-canvas`; **383 of 1,875** at 800x600; **1,803 of 6,143** and **2,085 of 3,586** with a Town Centre queue, whose cards move the holes about.

**The leak is not the bar's whole box, which is why the fix could not go on the grid row.** `.hud-panel--selection` is `width: auto; justify-self: start` — a 330px slab against a 1,256px `.hud-bottom` row — so the gap beside it is genuine world and must stay clickable. `#hud-tooltip` passes clicks through as well, and correctly: it follows the cursor, so a tooltip that took the pointer would fight the mouse it is chasing.

**Root cause.** `#hud-root` is `pointer-events: none`, so the canvas sees the mouse through the HUD's transparent grid. `.hud-panel--selection` re-stated that gate and then opted eight child selectors back in BY NAME — the command deck, group and list, the build menu, its pages and page tabs, the selection summary, the command buttons. That was sound while the bar was only as big as its content: nearly every pixel it painted belonged to one of the eight. v0.3.207 made it a fixed painted band — 246px above 1120px wide, 236px below — and every pixel no listed child claimed became a hole. **The gate was written on the element that LAYS OUT rather than the one that PAINTS**, so growing the paint silently grew the hole.

**Fix.** `pointer-events: auto` moves onto the painted chassis rule in `hudChrome.css` — `.hud-bar, .hud-panel, .hud-footer`, the rule that sets `background-color` — so a painted surface cannot be added without it. The per-child opt-ins are deleted; the scroll regions keep their events by inheritance instead of by name.

**A test was already aiming through the hole, and it had been RIGHT until the morning of the same day.** `tests/browser/trade-route-reach.spec.ts` centred the camera on the enemy Market's anchor and right-clicked `worldToScreen(market.x + 1, market.y + 1)`, which is (400, 357.6) in the suite's 800x600 viewport. Under today's fixed band that point is 5.6px inside the bar: `elementFromPoint` returns `div.hud-panel.hud-panel--selection` and the canvas receives nothing. **Measured, not inferred**, on a build whose only difference from HEAD is `src/hudCommandPanel.css` restored to its `eb07296b` (v0.3.206) version, with the working tree's pointer-events fix left in place so the hit test reports the painted box honestly: with a Trade Cart selected the v0.3.206 bar was **196px tall with its top edge at y 392**, so the click point sat **34.4px ABOVE it, on open canvas** — `elementFromPoint` returned `canvas.voxel-world-canvas` and a real right-click delivered pointerdown, pointerup and contextmenu to it. The control that proves the swap took effect: under those same v0.3.206 rules the bar is 65px tall with nothing selected against 196px with the cart, where HEAD gives 236px for both, and that 65px matches the v0.3.207 entry's own recorded low end for this viewport. The spec dates from 2026-08-24 (`00c0b4fa`) — twelve days, not two months — and aimed at open canvas for every one of them; **v0.3.207 (`bf5ff47f`, three commits before this one, the same day) grew the bar over its click point**, lifting the top edge from y 392 to y 352, and this defect then hid the consequence, so the spec kept passing. An earlier write-up of this said the spec had been passing for two months on an action no player could perform, and that was wrong in degree and in kind: nothing was passing wrongly for two months, and the spec was not a bad test. A layout change silently invalidated a test's premise, and a second defect concealed it. The spec now centres the camera on the cell it clicks, which puts the click at (400, 319.2) with 32.8px of canvas to spare.

A census of every pointer event the whole browser suite dispatches — 195 tests served from the same `dist/` with a hit-test recorder injected, the instrument proved live against a known-swallowed and a known-good click — found no other spec aiming at a HUD-covered world point; the only rows came from this defect's own gate, which clicks painted HUD glass deliberately.

**How this class is checked from now on.** `tests/browser/hud-opaque-surfaces-swallow-clicks.spec.ts` (`npm run test:browser`, so `npm run verify`). It finds its surfaces at RUN TIME rather than by name: every element under `#hud-root` that is drawn, at least 8x8, with a computed `background-color` at least 50% opaque, and outermost on its branch — five per state. Paused at boot, at 1280x800 and 800x600, in three states (nothing selected; the Town Center with four villagers queued; every villager selected), it holds three things. (1) Every point on an 8px grid inside each rounded border box hit-tests to something inside `#hud-root`. (2) Real right-then-left clicks, at up to eight non-interactive points per surface, reach no listener on the world canvas, leave the selection byte-identical, and leave every selected unit's command unchanged. (3) A right click on open world AND one on the transparent part of the `.hud-bottom` row must both still reach the canvas, before and after each sweep — the over-fix guard, since making the grid row clickable would satisfy (1) and (2) while eating the clicks beside the bar. Red on the unfixed tree in every state at both viewports. The spec refuses a run that sampled too few points, so "no leak" cannot quietly mean "did not run".

**Bound of that gate, named.** Assertion (2)'s world-command half is CORROBORATION, not a reliable detector: it caught villagers retargeted from `move -> 17,18` to `move -> 5,21` in one red run and stayed green in another, because it fires only where the sweep's points resolve to a cell that issues an order, and it is vacuous with a building or nothing selected. Nothing here covers the hidden surfaces (the game menu, the load panel, the match summary, the tech tree, the compendium), `#hud-tooltip` (exempt by design — its `pointer-events: none` is pinned, so the exemption goes red rather than widening), other widths, a deeper production queue, the replay timeline's reserved height, keyboard or wheel input, or whether a swallowed click then does the right thing for the control it landed on. The grid stops one pixel short of each far edge, and a shadow drawn outside the border box is not swept. There is no pixel evidence in the gate: three capture pairs at `TICKS=1` diff at 0.00%, which is the evidence that the behaviour changed and the bar did not.

**Open, and the owner's call rather than a settled thing.** At 800x600 the band now covers the bottom 188px of a 480px canvas — about **39% of the visible world** — and that surface used to leak its clicks through to the map. How much play area the bar should occupy at small windows is a live question, not one this entry answers.

## 2026-09-05 — A villager right-clicked onto an unfinished building walked up to it and stood there (found by the standing loop, FIXED and gated v0.3.208)

**Symptom.** Right-click a villager onto a foundation that already exists — AoE2's way of rescuing an interrupted build and of adding builders to speed one up — and the villager walked to the site and did nothing for the rest of the match. `bridge.issueContextCommand` returned **true** both before and after the fix, so the HUD said the order had taken. A build that stalls looks, from the panel, exactly like a build that is going.

**Attribution, and the honest half.** Found by the standing loop, playing the game; the owner reported none of this session's play findings. **The mouse half of the original observation could NOT be reproduced.** What is proved here is the CELL route, driven through `bridge.issueContextCommand` in simulation. Which of right-click's two routes a given mouse pixel lands in is decided by the entity hit test in `src/input/`, and that was not instrumented — so the original observation is more likely the OTHER defect this session found, where a painted HUD surface swallowed the click entirely (measured and fixed on a branch, not shipped: see the devlog for 2026-09-05). The defect recorded here is real and is fixed; it is simply not certain to be the one that was seen.

**Investigation.** Right-click is routed TWICE. `contextAtEntityRouter` handles a click the entity hit test claims, and it has had a build branch since 0.1.17 (multi-villager construction): it reads the target's construction state, and if the building is incomplete it queues a `build`. That route always worked, and `tests/simulation/multiVillagerConstruction.test.ts` has always covered it. `contextRouter` handles the click on a ground CELL — the route the pointer falls back to whenever the hit test does not claim the click — and it had no build branch at all. The click fell through every branch to a plain move onto a cell the foundation itself blocks, which is why the villager arrived at the site and stopped: it had been told to walk somewhere it cannot stand.

**Root cause.** A rule that belongs to RIGHT-CLICK was implemented on one of right-click's two routes. Nothing in the shape of the code makes the two routes agree, and the entity route's coverage is what kept the gap invisible: the mechanic had a passing test, on the half that worked.

**Fix.** `findOwnedConstructionSiteAtCell` in `selectionFinders.ts` — any cell of the footprint counts, not just the anchor, because that is what the player clicks, and there is no visibility gate, because an owner always knows where its own foundation is (which matches `findOwnedGarrisonBuildingAtCell` beside it). `contextRouter` gains a villager-only branch that must precede the garrison branch, since a foundation cannot be garrisoned. `setUnitBuildCommandDirect` returns false on any precondition miss — non-villager, foreign owner, building missing or already complete — so both routers fall through on a miss instead of swallowing the click.

**How this class is checked from now on.** `tests/simulation/buildExistingFoundation.test.ts` (`npm test`, so `npm run verify`), three cases, every one asserting REAL PROGRESS — `buildProgressTicks` climbing to `totalBuildTicks` — never that a task was assigned, because a task that is assigned and never runs is precisely what this defect looked like. (1) A villager standing adjacent to an orphaned foundation, on three building types (house 2x2, mill 2x2, barracks 3x3), must show progress within 20 ticks: no walk is needed, and the plain move could never satisfy that because it produced no path at all. (2) A villager ordered from the opposite corner walks there and finishes, and is asserted to be standing OUTSIDE the footprint at the end, so it got there under its own steam rather than being teleported onto the site — this is the case a move-only route appears to handle, because the villager does walk, and then never builds. (3) Two runs of one fixture that differ ONLY in whether three more builders are ordered onto the site through the same cell click, with every villager parked against the building in both arms so neither run differs by how far anyone walked: the crew must finish the remainder in under 75% of the solo time, which is the AoE2 crew curve `3*base/(n+2)`.

**Bound of that gate, named.** Only the CELL route is exercised; nothing here says which route a given mouse pixel lands in, and the entity hit test is the browser suite's job. Three building types on the flat all-grass `multi-villager-construction-fixture`, owner 1, AI disabled, Dark Age, no build-rate technology and no Incas or Treadmill multiplier — so it does not cover terrain that blocks the approach, a foundation under fog, an ALLY's foundation, or a non-villager actor. Progress is read from `getEconomyState()`, so it proves the simulation advanced the site, not that the HUD or the renderer showed it. The multi-builder case asserts a RATIO between two runs of the same fixture, not an absolute tick count, so it cannot detect a uniform slowdown.

## 2026-09-05 — A finished playtest threw its own recording away at V8's string ceiling (found by the standing loop, FIXED and gated)

**Symptom.** `npm run playtest` simulates a full match — the default is 30,000 ticks, tens of minutes of wall time — and then dies on the last line with `RangeError: Invalid string length`. The bundle is never written, so the run is gone: nothing to replay, nothing to inspect, nothing to run the oracles over. The same wall stands on the way back IN, which is worse, because a bundle that was written can still be unreadable. `scripts/playtest-corpus.mjs` read one with `JSON.parse(readFileSync(...))`, so a long enough run turned the progression gate into an ERROR row on exactly the runs it exists to check.

**Attribution.** Found by the standing loop, playing the game, not reported by the owner. None of this session's play findings were owner-reported.

**Investigation.** Measured rather than guessed, on 2026-09-03's 20,001-tick corpus bundle: `ticks[]` is **95.9%** of the file at a mean **15.7 KB per tick entry** (of which `diff` 84% and `metrics` 16%), the whole file is **313 MB** at 20,001 ticks, and entries grow as the match fills with units — so the 30,000-tick default lands past V8's cap of **536,870,888** characters. That number is `buffer.constants.MAX_STRING_LENGTH`, and it bounds `JSON.stringify` and `JSON.parse` alike because each operates on ONE string.

**Root cause.** Nothing about the data was wrong: the document was simply larger than a single JavaScript string may be. A comment above the failing line already recorded the same failure being mitigated once, by dropping `null, 2` — which costs about 40% and MOVED the wall rather than removing it. The 2026-09-02 register entry above records the previous instance of exactly this, mitigated the same way.

**Fix.** `src/game/playtest/bundleIo.ts` — `writeBundleFile` and `readBundleFile` — never holds the whole document as one string in either direction. The largest string either side ever builds is ONE array element (a tick entry, about 16 KB) or one non-array top-level value (`initialSnapshot`, about 0.5 MB). **The format is unchanged.** The file is ordinary JSON, byte-identical to what `JSON.stringify(bundle)` produces, so bundles recorded before this still load and anything else that reads bundle JSON still works. The document was not shrunk, sharded or re-encoded; only the serializer changed. Both directions are wired at every call site that touches a bundle: `playtest.mjs` writes through it, and `replay-inspect.mjs`, `run-oracles.mjs`, `playtest-corpus.mjs` and `playtest-findings.mjs` read through it (`playtest-findings.mjs` both ways, since it injects markers and writes the bundle back).

## 2026-09-03 — A decided match never ends, because the AI can only aim at a Town Center (PARTLY FIXED: 1 of 4 seeds resolved then; 3 of 4 after the 2026-09-04 garrison entry above, OPEN)

**Symptom.** The standing acceptance-test failure "matches do not resolve": at 60,000 ticks — 100 minutes of game time — every seed is still running. Measured on four seeds after the wood fix, all four still ran to the horizon.

**Investigation.** `gold-rush` gave the clean case. From tick 48,000 to 60,000, sampled every 4,000 and byte-identical at every sample, owner 2 held:

    pop 0/5   villagers 0   army 0   buildings: blacksmith x1, house x1

Zero units. No Town Center, so it can never produce a unit again. It is functionally dead and cannot recover. Meanwhile owner 1 stood at 130 population with an army of 90, building farms.

**Root cause.** Two rules that are each correct and together deadlock.

`conquestOutcomeSystem` ends a match only when a player has NO UNITS **AND NO BUILDINGS** — which is right; a player with a building standing has not been conquered.

`pickAttackTarget` chooses the AI's march target from `townCentersByOwner`, a map keyed on owners that still HAVE a Town Center. Raze it and that owner drops out of the target list entirely: `targetOwner` becomes null, the attack phase's push branch has nothing to march on, and the surviving buildings are attacked only if they happen to fall inside somebody's vision. The AI is structurally unable to finish what it started.

So the winner cannot satisfy the condition the loser is being kept alive by.

**Fix, and the first version of it was WRONG in a way worth recording.** The obvious shape — give `pickAttackTarget` a fallback map and let it return the surviving building in `targetOwner` / `targetTownCenterId` / `targetTownCenterPosition` — passed its own unit gate, resolved `gold-rush`, and REGRESSED THE AGE-UP: `aiPlayer.test.ts` :: "ages up through the ages within a generous tick budget" went red, the AI reaching Feudal at 2,061 and never Castle within 8,000 ticks. Cause: `targetTownCenterPosition` is not private to the attack phase. `aiFerryPhase` reads it too, and when it is set with the target not land-reachable it stands down the ordinary march AND discretionary building to fund a Transport Ship — so filling that field for a Town-Center-less enemy stalled the economy. Isolated by disabling only the fallback and re-running: 24 of 24 passed.

The shipped fix is therefore SURGICAL. `pickAttackTarget` is byte-identical to what it was. A separate `lastResortTargetId` / `lastResortTargetPosition` pair is computed alongside it and read by the attack phase and nothing else, in its final push branch, only when no enemy Town Center is left. Deterministic — owners and entity ids both sorted, so a replay picks the same building. `gold-rush` still resolves at exactly tick 41,967, and the age-up test is green.

**The lesson, which is about the FIELD and not the feature.** A context field named for one thing (`targetTownCenterPosition`) had a second reader with different semantics, and reusing it to mean "the place to march" was correct for the phase being edited and wrong for the phase that was not. The cost of finding that was one full gate run; the cost of not finding it would have been a shipped economy regression that the resolution measurement would have applauded.

**Effect, measured on four seeds at 60,000 ticks, before and after.** `gold-rush` goes from running-at-60,000 to **victory at tick 41,967**. The other three still run, and the reasons are DIFFERENT defects rather than this one failing:

- `arena` and `coastal`: owner 2 still HAS a Town Center, so the fallback never engages. Owner 1 has an army of 105 and does not finish it — on arena that base sits inside the script's own stone wall ring, which points at attack EXECUTION (pathing to or breaching a walled base) rather than at targeting.
- `fortress`: neither side has an army to attack with (2 and 0 in the Imperial age). That is the villager-target-versus-population-cap chain in the entry above, not this one.

**How it is checked from now on.** `tests/simulation/aiAttacksAnyEnemy.test.ts` :: `an enemy with no Town Center is still a target` — four cases: the fallback fires when the enemy has lost its Town Center; a Town Center still outranks a much closer bare building; the two-argument form is unchanged; and an ALLY without a Town Center is never targeted. Red-checked by reintroducing the defect (iterating an empty list instead of the fallback map): the first case fails with `expected null to be 2`, and all four pass again on revert.

**Bound of that gate, named.** It is a unit test on the TARGET CHOICE. It does not prove the army reaches the building, kills it, or that the match ends — arena and coastal are live proof that a correct target is not sufficient. The end-to-end claim rests on the `gold-rush` seed alone, at one horizon.

**What this predicts.** The remaining two causes are both "the army exists and does not close": walls it will not breach, and an army too small to matter. Both are about what the military DOES rather than what it is pointed at, and neither is touched here.

**What it actually was, found 2026-09-04.** The prediction above was half right and half wrong, and the wrong half is the useful one. It reads `arena` and `coastal` as "the army exists and does not close" — walls, or too few units. **And the bound named above is exactly where it hid.** This gate is a unit test on the TARGET CHOICE, and it says so. The defect was one line earlier, in a preference that never got as far as choosing.

## 2026-08-30 — Gather over-subscription counts EVERY owner's villagers (LATENT, not fixed, OPEN)

Every current map keeps the players' resource rings apart, so the defect cannot fire. Fixing it means threading a per-owner count through five call sites in two files for no measurable behaviour change today.

**The trigger to watch for.** It becomes live the moment two players' gatherers can reach the same node: a map with a contested middle (gold or stone between bases), overlapping resource rings on a small map, or allied players sharing a base. Any of those should come with the fix — key the counts by owner — and this entry is the note that the machinery is already wrong when they arrive.

**What this predicts.** A shared counter with no owner dimension is a latent cross-player coupling wherever it appears. `gatherTargetCounts` is one; the same shape is worth looking for in any per-tick map keyed only by entity id.

## 2026-08-30 — The behind-building silhouette reads as a unit standing ON the building (OPEN)

**Symptom.** A unit hidden behind a building is cued by a flat-coloured mirror of its body drawn over the building. It is fully opaque, and at a Town Center that reads as a villager standing on the roof rather than as an x-ray of one behind the wall — noticed hands-on on 2026-08-29 ("three of them across the TC's upper tier read as villagers standing on the roof") and confirmed in the `occlusion-showcase-fixture` capture, where the blue figure sits on the roof with nothing to say it is a cue.

**Investigation.** The obvious fix — draw the mirror on a transparent material so the building reads through it — was implemented, measured, and REVERTED. It failed on three independent axes, each measured rather than argued:

1. *It is close to a no-op under the art style the game actually ships.* The default is `moebius`, whose tone-band quantiser snaps **24.1% of the cue's pixels byte-identical to the fully opaque render**; mean change against opaque is 46.6 there against 125.6 under `painted`. One opacity value cannot serve a banding and a non-banding pipeline.
2. *It introduces self-blending seams.* The mirror copies a unit's own overlapping parts, and a translucent instanced part that overlaps itself blends twice — solved per-pixel as 452 px at the declared 0.55, 68 at 0.7975 (1−0.45²) and 6 at 0.9089 (1−0.45³). About 14% of the body draws at the wrong opacity, as streaks down the arm and torso. The engine has the cure and does not export it (see `docs/engine-feedback/current.md`).
3. *It degrades the half of the cue that matters most.* The enemy colour is a coral in the same hue family as every roof in the palette, so blending erases it: mean RGB distance from the background over a bright roof fell from 204.2 opaque to **82.0**, while the friendly blue — orange's complement — held at 196.9. The cue exists to answer "are those mine?", and it was the *not mine* answer that went.

Raising opacity to 0.78 fixed the measured colour bar but none of the three causes.

**Root cause of the DEFECT (still open).** Uniform alpha is the wrong technique for this cue in this renderer. What would work is a treatment that does not depend on blending: a contour, a hatch, or a colour chosen for contrast against the building palette rather than for ownership alone. The enemy coral in particular should be re-picked against the roof palette, which is a change that needs no engine feature and no transparency.

**How it is checked from now on.** It is not, and that is the honest state — no gate covers "does this cue read as behind rather than on top", because it is a judgement about a rendered image. What the attempt DID leave behind is the measurement method: capture background / opaque / candidate under both art styles, solve the per-pixel alpha, and measure mean RGB distance from the local background for BOTH ownership colours over both a bright and a dark building. Any future attempt that does not do that is guessing, and the first attempt's 0.55 was a guess that looked right in one capture of one art style with one owner.

**What this predicts.** Every other overlay that might reach for transparency has the same two traps waiting — the moebius quantiser and self-blending — and every two-colour ownership cue should be checked in BOTH colours against the palette it will sit on, not just the one the showcase fixture happens to spawn.
