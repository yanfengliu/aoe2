# 2026-08-23

## Parthian Tactics, and the browser suite that was testing yesterday's build (v0.3.49)

**Timestamp:** 2026-08-23

**Action:** Implemented Parthian Tactics (Archery Range, Imperial) — the cavalry-archer class's own armour technology plus its anti-spearman attack bonus — after re-measuring the technology roster against `design/stats/technologies.csv`.

**The roster count in the roadmap was wrong in the direction that matters.** The headline said "technologies 66/140". Slugifying every CSV name and diffing against the `ResearchableTechnologyType` union says **123 of 140 are in the game and 17 are genuinely missing** — and three of the twenty the naive diff reported were false positives whose implementations simply use a different slug: `plate-barding` (CSV "Plate Barding Armor"), `cannon-galleon-unlock` (CSV "Cannon Galleon"), `bombard-tower-unlock` (CSV "Bombard Tower"). A roster audit that keys on the CSV's display name overstates the remaining work by whatever share of the roster was named for what it UNLOCKS rather than for itself. The real remaining 17: Careening / Dry Dock / Shipwright (Dock), Banking / Caravan / Cartography / Coinage / Guilds (Market — every one of them needs trade or an ally, so none of them does anything in a 1v1 yet), Atheism / Berserkergang / El Dorado / Hoardings / Spies / Treason (Castle; Treason is Regicide-only and out of scope per §2.3), Illumination / Theocracy (Monastery), and Parthian Tactics — shipped here.

**Two halves, two seams, and the reason it is not one.** The armour half (+1 melee / +2 pierce) is per-unit state on the combat state, applied both by the factory for units created later and imperatively by `technologyOps` to the riders already standing — the same path as the Blacksmith armour line, with `parthian-tactics` added to `EXTRA_PIERCE_ARMOR_TECHS` for the asymmetric pierce. The attack half CANNOT go there: the bonus applies only against the spearman armour class, and the attacker's combat state does not know what it is shooting at. So it is derived at the damage site from the owner's researched set (`parthianTechEffects`, the `sappersTechEffects` pattern), which for a cavalry archer means the PROJECTILE IMPACT site — `resolveDueProjectiles` gained a required `technologiesFor(owner)` dep rather than an optional one, so the typechecker names every call site instead of letting a forgotten one silently drop the bonus.

**The class set is wider than `MOUNTED_UNITS` and narrower than the CSV reads.** `CAVALRY_ARCHER_UNITS` covers the Mangudai and War Wagon lines as well as the stock two, because the technology row names the Mangudai explicitly and a War Wagon is the same kind of thing; but the War Wagon takes only the armour, since its own `units.csv` row carries no anti-spearman value and the technology row names only the Cavalry Archer and the Mangudai for the attack. Noted while there: the unique mounted archers are NOT in `MOUNTED_UNITS`, so Husbandry and Bloodlines miss them today — a real parity gap, left alone here because widening that set changes existing units' stats and belongs in its own slice.

**What the reviewer-of-record would have missed: the browser suite tests `dist/`, not the working tree.** `tests/browser/new-tech-reach.spec.ts` failed with "element(s) not found" for `[data-command="research-parthian-tactics"]`, while a simulation probe on the SAME fixture printed `researchOptions` containing `parthian-tactics`. The tempting read — a UI-side filter dropping unknown technologies from the command card — was wrong. `playwright.config.ts` runs `npm run preview`, which serves the last `npm run build`; the captured page context was a faithful screenshot of the code as it stood before the change. Rebuilding made the same spec pass unchanged. **A browser run without a fresh build is a measurement of the previous commit.**

**Verified visually, not just green.** Captured the Archery Range card at 800x600: the button renders with the research glyph as "Research Parthian Tactics", its tooltip reads "Cost: 200 food, 250 gold; takes 65s" (the CSV numbers reaching the player), and the resource chips drop 4000/4000 → 3800 food / 3750 gold on the click. Probed a double click while research is in progress: `queueResearch` returns true both times but the cost is charged ONCE and the second command is a no-op — the panel reads `researching parthian-tactics`. AoE2 greys the button while it is in the queue and this build does not; recorded as UI polish rather than fixed, since it is generic to every technology.

**Result:** 2560 vitest tests + 1 new browser spec green; typecheck, lint and build clean. Spec §10.4 area carries the technology and the two-seam reasoning; the roadmap's technology count is corrected in place.

## Monk faith and rest — the mechanic two technologies were waiting on (v0.3.50)

**Timestamp:** 2026-08-23

**Action:** Implemented the monk FAITH/rest mechanic, then Illumination and Theocracy on top of it, closing the Monastery's technology roster.

**The technologies could not be implemented without first building what they modify.** `technologies.csv` describes Illumination as "Faith regain 50% faster" and Theocracy as "Only one monk needs to rest in a group". Neither had anything to attach to: `bridgeConstants.ts` carried the deferral in writing — "real AoE2 uses per-tick conversion chance plus faith; out-of-scope here" — so a monk in this build could convert an entire army back to back. Shipping either technology without the mechanic would have produced two researchable no-ops, which is worse than not having them.

**The state shape is the interesting decision.** `monkFaithCodec` maps monkId → current faith, and an ABSENT entry means FULL. That single choice removes the migration: a save written before v0.3.50 has no slot at all and loads as every monk rested, the map holds only the monks currently resting (usually none), and the entry is deleted the moment faith tops out. The alternative — a faith field on every monk, defaulted with `?? MONK_FAITH_MAX` — would have needed a migration path in three hydration sites.

**Two seams, chosen for what they buy.** Illumination is a per-tick RATE derived from the owner's researched set, not a duration stamped when the rest begins: researching it mid-rest therefore speeds up the rest already in progress, which is what a player would expect. Theocracy is read at the flip site, where the group is knowable — every monk of that owner whose convert task points at the same target is spent unless the technology says otherwise. A resting monk KEEPS its task and stands there rather than having the order dropped, matching the vision-interrupt shape already in `applyMonkConvert`, and the selection panel reports `Resting` ahead of the task verb so it cannot claim to be converting while nothing happens.

**Three instrument errors, each one command from being believed.**
1. **The fixture killed its own experiment.** With the three convertible villagers spawned on adjacent cells, the villager converted first was standing next to the next target — villagers auto-engage within their vision (3) under the default aggressive stance, so they brawled and the second target was DEAD by tick 160. The "a monk cannot convert again" tests were passing because there was nothing left to convert. Spacing the villagers 6+ cells apart while keeping each inside both monks' action range 4 fixed it, and the real proof was a five-line experiment: comment out the faith gate, watch five of the fifteen tests fail, restore it.
2. **A probe loop that never ran.** `while (bridge.getEconomyState().tick < mark)` exits immediately because `economyState` has no `tick` — so five "snapshots" printed the identical tick-0 state and looked like a frozen simulation.
3. **The browser click that hit nothing.** `clickCell` on the enemy villager produced no order at all. The cells were 700px BELOW the canvas: the camera follows the player's TOWN CENTRE, and this fixture's is at (18,18) while the monks are at (8,7). `__AOE2_TEST__.centerCameraOnWorldPosition` is the hook, and with the camera moved the same real right-click converts.

**A defect I found in the visual sweep and then disproved.** The Monastery card now renders TEN research buttons, spanning x=450..2233 at a 1280px viewport, and the group's own list computes `overflow-x: visible` — which reads exactly like seven technologies (Faith, Redemption, Atonement, Fervor and both new ones among them) that no player can click and that only Playwright's auto-scroll could reach. It is not: the SELECTION BAR is the scrolling ancestor (`hudCommandPanel.css`: `overflow-x: auto`, measured scrollWidth 2220 vs clientWidth 998), and scrolling sideways is the documented design for a selection that needs more room than the screen has. The lesson is the one already in the register — measure the scrolling ANCESTOR, not the element you suspect — and the finding downgrades to a UI-polish item: AoE2's paged icon grid beats a 2200px horizontal scroll.

**Result:** 15 new simulation tests + 3 browser specs (including a mouse-driven conversion that reads `Resting` off the panel), full suite green, and three inventory pins deliberately updated — the Tier-1 codec count 39 → 40, the snapshot slot list, and the Monastery options list. Spec §12 area carries the mechanic and both technologies; the roadmap's technology count moves to 126/140.

## The Dock's three technologies, and a button that never worked (v0.3.51)

**Timestamp:** 2026-08-23

**Action:** Implemented Careening, Dry Dock and Shipwright; found and fixed two silently-dead command-card buttons; added the class gate that covers them.

**Three technologies, three existing seams, one new shape.** Careening's armour is per-unit combat state like every armour technology, but it is the ONLY one with no melee half (technologies.csv "+0/+1"), so it bumps `pierceArmorBonus` directly rather than going through `applyArmorTech`, which always adds +1 melee. Dry Dock is a branch in `movementSpeedPercent`, sitting beside the mounted/infantry/villager branches rather than inside them, because a ship is none of those and would never reach them. Shipwright's cost discount went into `effectiveTrainingCost` - the seam whose own comment says every site that charges or checks a training cost must come through it - which is why the right change was a new parameter on that function (three call sites, all updated by the typechecker) and not a second discount path. Scope everywhere is the water DOMAIN, not a ship list, so a ship added later is covered the day it exists.

**The defect: two tables that must agree, with nothing making them agree.** The browser test would not pass. Clicking `Train Transport Ship` at a Dock produced no unit, no queue entry, no charge, no toast - and the same click on `Train Fishing Ship` charged 75 wood, which is what ruled out the click, the camera, the selection and the pop cap. `trainOptions.ts` (the card) offers `transport-ship` at the Dock from the Feudal Age; `TRAINABLE_UNITS_BY_BUILDING` (what `canTrainAt` consults when the command is validated) never listed it. The UI accepted, the validator refused, and nothing reported the refusal. **The Transport Ship is the only way a land army crosses water, so a whole mechanic has been unusable since the naval slice** - and every naval test passed because fixtures SPAWN transports rather than training them.

**The gate found a second instance immediately.** `tests/simulation/menuMatchesValidator.test.ts` enumerates what the train menu can offer across every building, all four ages, all 30 civilization names and both extremes of the researched set, then asserts the validator accepts each one. First run: `["barracks offers huskarl", "dock offers transport-ship"]`. The Goths' Anarchy is supposed to move the Huskarl into the Barracks; that button was dead the same way. Both fixed by listing them in the validator's superset - the civ-and-technology gate lives in the menu, which the validator consults for eligibility, so listing them opens nothing to anyone else.

**A mirror check that came out clean, which is also information.** The same test asks the reverse for technologies: every technology with a cost must be hosted by some building. I expected the three age advances to be the exception and they are not - they sit on the Town Center's research list as well as having their own command. Zero homeless technologies, so the technology side of the pair was already consistent.

**A test that asserted nothing, caught before it shipped.** The first version of the Dock browser test read `if (transport) { ... }` - and `naval-imperial-fixture` has no transport ship, so the entire capacity assertion was skipped silently while the test reported green. Replaced with training one through the card, which is what turned up the defect above, and the assertions are now unconditional: the wood delta is exactly 100 (125 x 0.8, proving Shipwright reaches the charge) and the panel reads `0 / 20 aboard` (proving Careening and Dry Dock reach the capacity).

**Also on the way:** `technologyOps.ts` reached 514 lines and was split rather than capped - the four owner-wide unit sweeps (line upgrade, armour bonus, Careening's ships, queue rewrite) moved to `technologyUnitSweeps.ts`, which is a coherent module because all four are the same shape: walk this owner's units and mutate.

**Result:** 19 new simulation tests plus 4 in the class gate, 4 browser specs green against a fresh build, full suite green, and the register entry recorded.
