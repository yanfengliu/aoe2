## [2026-04-22 11:30, America/Los_Angeles] - Move-order path caching for selected-unit movement lag

**Action:** Investigated the report that selected units sometimes move in a laggy, sub-60-FPS-feeling way. Read the current devlog + architecture first, then traced the movement path through `src/game/simulation/createSimulationBridge.ts`. The hot path turned out to be the move-command branch re-running `findGridPath(...)` every simulation tick for the same destination via `findMovePlan(...)`, even when the unit was already following a stable route. Added a transient `movePathCache` side map keyed by unit id, new `clearUnitCommand` / `setUnitCommand` helpers so command replacement always invalidates cached routes, and a `resolveMovePlanFromCache(...)` path that reuses the cached path while the next cell is still passable and falls back to a fresh solve only when needed. Added `tests/simulation/movementPathCaching.test.ts` first to lock three gameplay-facing contracts: steady move orders do not re-solve every tick, retargeting drops the old route immediately, and save/load forces a fresh re-plan instead of persisting transient route state. During final review, Codex identified a real regression in the first cache implementation: if the player clicked a blocked cell that later became free, the unit could stop forever at the stale fallback tile. Added a new `move-target-unblocks-fixture` plus a fourth movement-path test, then adjusted the cache logic so reaching a cached fallback destination forces one more re-plan toward the original clicked cell before the command is considered finished.

**Reasoning:** The user-facing symptom looks like "not 60 FPS," but the repo's simulation intentionally runs at `TPS = 10`, so any expensive work in the tick loop is more noticeable than in a 60 Hz sim. The renderer can still draw at 60 FPS, but if the simulation hitches on repeated per-tick pathfinding, selected units appear to advance unevenly. Caching the route for steady move orders is the smallest behavior-preserving fix because move-command passability already ignores other units; that means we can safely reuse the route until the next terrain/building/resource passability check says the immediate next cell is no longer valid.
