### Action

User direction: both lazy redirect on arrival (a) and eager pre-reservation (b) are valid; both should be used depending on the case. Single unit commanded to a crowded place → move to closest available spot. Group commanded together → spots pre-reserved so units don't oscillate. User asked me to enumerate other edge cases.

Added `design/spec-final.md` §12.7 "Movement Targets and Slot Reservation" capturing:

- The dual-strategy rule (lazy redirect vs eager pre-reservation), with the trigger condition for each (single-unit issuance vs N-unit group issuance against a shared destination).

- Enumerated edge cases: target cell flipped to blocker mid-flight; reserved cell taken before arrival; spawn into full cell (treated as instant lazy redirect); wandering / patrol transit (no reservation); combat engage (group move with attack-target ring center); gather clusters (lazy on arrival, hold while gathering); construction (slot adjacent to foundation); mass formations (linear scaling, edge truncation); map-edge fallthrough; naval vs land domain restriction; performance bound.

The renderer is unaffected — it still reads transform position only. All reservation bookkeeping lives in simulation state.

Spec-only change; no multi-CLI review required for this commit. The implementation will go through review per the standard pipeline.

The 30-second TTL on stuck reservations is a guardrail against an entity holding a slot indefinitely because pathfinding can't reach the destination (e.g., the unit got walled in). Without TTL, a small bug in the path-cancellation flow would leak reservations forever.

### Reasoning

Per spec §12.7's dual-strategy rule. Single-unit moves use lazy redirect (shipped 0.1.18) because pre-reserving for one unit is wasteful and breaks the "command target == clicked cell" contract that pathfinding relies on. Group moves use eager pre-reservation because the alternative — N units all arriving at one cell and the latest 16-N falling through to lazy redirect — produces a brief visual pile-up at the destination before redirects spread them out. Spiral allocation pushes the spread to issuance time so each unit's path is direct.

The whole-cell-blocker skip in the allocator is intentional: a group commanded to MOVE to a resource / building cell is logically saying "go stand near here," and surrounding cells are the right destinations. Group commands that mean "gather" or "attack" route through `issueContextCommand`, not `issueMoveCommand`, so they're unaffected.

Determinism is critical for save / load and replay. The spiral uses a fixed neighbor-offset array (E, W, S, N, then four diagonals) walked in BFS order, so the same `(unitIds, targetCenter, world state)` tuple always produces the same `Position[]` output. The save format records each unit's individual move command target (already in the schema), so on load the allocator doesn't re-run — the stored targets are authoritative.

### Notes

The "soft reservation with 30s TTL" wording from spec §12.7 is not yet implemented at the data-structure level. Today's allocator does a one-shot decision at issuance and the result lives in the per-unit move command target. If a third party takes a reserved cell before the unit arrives, the displaced unit's individual `unit.move` command still has the original target; the unit walks there; on arrival the lazy-redirect rule (shipped 0.1.18) finds the cell full and redirects to a neighbor. This achieves the spec's "reserved cell taken before arrival → fall back to lazy redirect" without an explicit reservation registry.

The next outstanding §12.7 follow-ups: widen `findNearestFreeUnitCell` from the 8-cell window to the 16-cell BFS radius the spec calls for; add an explicit reservation lifecycle (release on death / new command / garrison) so AI systems and HUD systems can both observe a unit's "intended slot" rather than just its current target. Both are deferred until a real game scenario surfaces a need.

## 2026-05-08T19:55:00-07:00 - Playtest loop phase 3 (fix-bot wrapper)

### Action

`scripts/propose-fix.mjs` reads `<in>.json` + `<in>.envelope.json` + `<in>-report/REPORT.md`, picks the first high-severity violation (or `--oracle <name>` override), assembles a focused prompt via `src/game/playtest/fixBotPrompt.ts:buildFixPrompt`, and asks `claude` or `codex` (per `--reviewer`) for a unified-diff patch + explanation. Validates with `git apply --check`; writes `output/fix-proposals/<bundle-id>/<oracle>/proposal.diff` + `WHY.md`.

`fixBotPrompt.ts` exports `SOURCE_FILES_BY_ORACLE` — a per-oracle heuristic file list (e.g. `no-pinned-or-oscillating-units` → `src/game/simulation/bridge/systems/playerCommandsSystem.ts`, `worldOccupancy.ts`, `worldOccupancyAllocators.ts`). The wrapper reads each source file, caps at 500 LOC with a `[…truncated]` marker, and embeds the contents in the prompt with the violation summary, envelope, and a 5-tick neighborhood (truncated at structural boundaries to stay under an 8KB budget).

`tests/playtest/fixBotPrompt.test.ts` — 4 tests pinning per-oracle file lists and the prompt structure.

### Code reviewer comments

Multi-CLI review pending; combined with Phase 4 + Phase 5 in the impl-final review.

### Result

`npm run typecheck`, `npm run lint`, `npm test -- --run` green. 4 new tests pass. Smoke-tested with a synthetic violation row (no real CLI invocation).

### Reasoning

The propose-only contract avoids a category of subtle automated-fix bugs: `git apply --check` confirms textual applicability but not type-safety, lint-cleanliness, or test passage. A propose-only loop hands the diff to a human (or to a follow-up gate) before it lands on `main`. Auto-apply with full-gates-on-fail-revert is a Phase-6 follow-up.

`SOURCE_FILES_BY_ORACLE` is a static heuristic, not a dynamic analysis — for each oracle we hand-pick the 1-3 files most likely to contain the relevant logic. The oracle catches the violation; the heuristic narrows the model's focus to the right area; the human reviews the diff before commit. If the heuristic misses, the model still has the bundle/envelope context and can grep via `--allowedTools "Read,Glob,Grep"` (Claude) or codex's read-only sandbox.

### Notes

Prompt content is delivered via stdin (`execFileSync(..., { input: prompt })`) rather than an inline arg. This avoids both shell-escaping issues and Node's argv length limits. The model name `claude-opus-4-7[1m]` selects the 1M-context variant; cmd.exe (Windows, when `shell: true` is set per CVE-2024-27980 mitigation) treats `[]` as literal characters, so the bracketed name is safe through the shell.
