## 2026-05-08T13:00:00-07:00 - Spec rule: unit non-overlap + AGENTS.md spec-persistence meta-rule

### Action

User described a new game rule (units may share a tile via sub-tile slots, but no two units may occupy the exact same point at the same simulation tick) and asked for a meta-rule that future user descriptions of game behavior must be persisted into `design/spec-final.md` as part of the same task. Both changes landed in the same commit.

`design/spec-final.md` gains §12.6 "Unit Spacing and Sub-Tile Occupancy" placed under the existing pathfinding/movement section. The subsection captures: sub-tile occupancy via deterministic slot packing (default 4x4 = 16 slots per tile, alternative patterns allowed if slots are distinct/stable/reproducible); placement / spawn / move / ungarrison / train completion / transport unload / conversion drop / replay-rehydration must resolve to a free slot, with neighbor-tile fallback when the target tile is fully packed; whole-tile blockers (buildings, resources, impassable terrain, out-of-bounds) prevent tile sharing; garrisoned, transported, or otherwise-contained units are exempt while contained; dying units retain their slot through cleanup; renderers may interpolate sub-tile positions independently of simulation slot assignment.

- `pureHelpers.getUnitTargetTransformForCell` and `isUnitTransformAtTarget` accept an optional explicit slot offset (callers without context fall back to the existing `entityId % 4` derivation).

Production wiring was reverted before commit. An earlier draft threaded the allocated slot through `transformOps.syncOccupancyForEntity`, `moveUnitOneSubgridStep`, the train-completion path, and the ungarrison path. Three regressions surfaced under the full test suite: the `createSimulationBridge.unitMovement` test ("renders unit motion on a finer sub-grid") observed exactly 1-tile-per-tick movement instead of <1 because re-snapping the transform on every cell crossing teleported the sprite by the slot delta; `fogMemory` saw the enemy house projected as a memory entity from the first read because the snap shifted the scout's sub-tile position before visibility was first computed; and `aiPlayer` / `imperialUpgrades.castleBlacksmith` / `autoAggression` flaked under the threads pool when the productionQueueSystem double-allocated through `placeFreshSpawnUnit`. The proper fix is at the move-command layer (update target on overflow at arrival, or pre-reserve a slot when the move is issued); that change is deferred to a future iteration that owns the movement system.

The infrastructure stays in `worldOccupancy.ts` so the future iteration can pick it up without re-deriving primitives. Spec §12.6 wording remains aspirational ("the simulation must fall back to a free slot in the nearest available neighbor tile") — that's the goal; today's implementation tracks slots correctly and has the placement helpers, but doesn't consume them in the renderer. The user-visible game behavior is unchanged from 0.1.17.

## 2026-05-08T15:00:00-07:00 - Spec §12.7 Movement Targets and Slot Reservation

### Action

User direction: both lazy redirect on arrival (a) and eager pre-reservation (b) are valid; both should be used depending on the case. Single unit commanded to a crowded place → move to closest available spot. Group commanded together → spots pre-reserved so units don't oscillate. User asked me to enumerate other edge cases.

Added `design/spec-final.md` §12.7 "Movement Targets and Slot Reservation" capturing:

- The dual-strategy rule (lazy redirect vs eager pre-reservation), with the trigger condition for each (single-unit issuance vs N-unit group issuance against a shared destination).
- The lazy-redirect contract: BFS from target with default radius 16 cells, target rewrite to prevent oscillation, last-resort overflow with debug-flag visibility.
- The pre-reservation contract: deterministic spiral-outward slot assignment, single allocation pass at command issuance, no per-tick refresh.
- Reservation lifecycle: arrival → occupation; new command / death / garrison / conversion → released; bounded TTL (30s default) for unreachable destinations.
- Determinism, save / load, replay rules: reservations are simulation state, must serialize, must replay deterministically.
- Enumerated edge cases: target cell flipped to blocker mid-flight; reserved cell taken before arrival; spawn into full cell (treated as instant lazy redirect); wandering / patrol transit (no reservation); combat engage (group move with attack-target ring center); gather clusters (lazy on arrival, hold while gathering); construction (slot adjacent to foundation); mass formations (linear scaling, edge truncation); map-edge fallthrough; naval vs land domain restriction; performance bound.

The renderer is unaffected — it still reads transform position only. All reservation bookkeeping lives in simulation state.

### Code reviewer comments

Spec-only change; no multi-CLI review required for this commit. The implementation will go through review per the standard pipeline.

### Result

`design/spec-final.md` grows from 1346 → 1393 lines (+47). No code change. All four gates remain green from the prior commit.

### Reasoning

User explicitly described the design ("both should probably be used depending on the case"). Per AGENTS.md's Game spec rule: persist user-described rules into `design/spec-final.md` as part of the same task. Edge case enumeration is a small investment that prevents implementation drift later — each case becomes a test the implementation must pass.

The lazy-redirect path is implementable today against the existing `worldOccupancy` infrastructure landed in commit `023c380`. The pre-reservation path requires a new reservation side map plus a deterministic spiral-allocation algorithm; both are tractable. Implementation will follow in subsequent commits, each going through the standard TDD + multi-CLI review pipeline.

### Notes

The pre-reservation algorithm's spiral order is intentionally underspecified at the spec level — implementations may pick row-major, column-major, ring-outward, or any other deterministic walk. The spec only requires that the order be deterministic and that the same inputs produce the same per-unit assignment. This leaves room for a perf-conscious choice when the time comes.

The 30-second TTL on stuck reservations is a guardrail against an entity holding a slot indefinitely because pathfinding can't reach the destination (e.g., the unit got walled in). Without TTL, a small bug in the path-cancellation flow would leak reservations forever.

## 2026-05-08T15:30:00-07:00 - Spec §12.7 lazy-redirect implementation

### Action

First half of the spec §12.7 dual-strategy implementation: the lazy redirect path for single-unit moves arriving at a fully-packed cell. The pre-reservation path for group moves remains queued for a follow-up commit.

Changes:

- `src/game/simulation/worldOccupancy.ts:findNearestFreeUnitCell(entity, requestedPosition): Position | null` walks the engine's closest-first neighborsWithSpace enumeration from the requested cell. Returns the requested cell if it has space (the entity itself is treated as non-blocking — a unit currently in overflow at the cell can re-claim it once another occupant leaves), else returns the closest free neighbor, else null when the immediate 8-cell window is also full.
- `src/game/simulation/bridge/transformOps.ts:resolveArrivalRedirect(unitId, arrivalCell): Position | null` composes `getUnitSlotOffset` + `findNearestFreeUnitCell` to give the move-arrival handler a single yes/no decision: null when no redirect is needed, a target cell when one is.
- `src/game/simulation/bridge/systems/playerCommandsSystem.ts:348` (the move-command arrival handler): before clearing a completed move command, the handler asks `resolveArrivalRedirect` whether the unit ended up in overflow. When yes, the handler rewrites `command.target` to the redirected cell and skips the clear, so the next tick's movement step heads toward the new target. When no, it clears as before.
- 4 new tests in `tests/simulation/worldOccupancyVisualSlots.test.ts` cover the helper: requested cell with space returns the cell; requested cell full returns a neighbor; everything full returns null; entity-itself-in-overflow at the requested cell still sees the cell as free for itself when another occupant has left.

`npm run typecheck`, `npm run lint`, `npm run build`, `npm test` all pass. Full suite: 892 passed + 1 skipped, no failures. Behavior change: a unit commanded to a fully-packed target cell now redirects to a neighbor with a free slot instead of overflowing (visually stacking) at the destination. The 17-units-to-one-cell case is now properly handled in the move path.

### Reasoning

User direction: both lazy redirect and eager pre-reservation are valid. Lazy redirect is the simpler path (no command-issuance changes, no reservation side maps, no save/load schema bump) and covers the most-common single-unit case. The pre-reservation path will follow as a separate commit because (a) it touches command issuance and save/load, raising the surface for regressions; (b) splitting them gives the reviewer two smaller diffs instead of one large one; (c) if pre-reservation introduces issues, the lazy redirect remains shipped.

Implementation gap still open: the visual-overlap-from-entity-id-collisions case (two units with same entityId mod 4 in the same cell drawn at the same screen pixel even when neither cell is full). The renderer still uses `entityId % 4` for sub-tile position via `getUnitCellSlotOffset` rather than the engine-allocated 16-slot offset. Properly closing this requires the renderer to read `worldOccupancy.getUnitSlotOffset` directly, OR the transform to be snapped to the allocated slot in a way that doesn't break in-flight movement (the snap-on-cell-crossing approach broke the unitMovement test in the prior commit). That gap is independent of §12.7 and remains a separate task.

### Notes

`findNearestFreeUnitCell` currently checks only the immediate 8-cell window (via `binding.neighborsWithSpace`); spec §12.7 allows up to a 16-cell BFS radius. The wider radius is a future extension when a real game scenario surfaces a need for it. The current 8-cell window covers the realistic "16 villagers at one tree, 17th villager arrives" case well — gather clusters spread across more than one neighbor cell are rare in practice.

The lazy-redirect path mutates `command.target` directly inside the system loop. This is safe because (a) the unitCommands Map iteration is delete-during-iterate-safe per ECMAScript, and (b) we mark the codec dirty after mutation so the side-map flush sees the change. Mutating in-place beats `setUnitCommand(id, ...)` here because we want to preserve the existing command identity and any internal cache state pointing at it.

Group pre-reservation (the b-path of §12.7) is the next checkpoint. It needs: a reservation side map keyed by entity, deterministic spiral allocation at command issuance, lifecycle hooks (release on death/garrison/new-command), save/load codec, replay determinism. Estimated as a same-day-sized commit if no surprises surface.
