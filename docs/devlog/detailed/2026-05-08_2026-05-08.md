# Devlog: 2026-05-08

## 2026-05-08T13:00:00-07:00 - Spec rule: unit non-overlap + AGENTS.md spec-persistence meta-rule

### Action

User described a new game rule (units may share a tile via sub-tile slots, but no two units may occupy the exact same point at the same simulation tick) and asked for a meta-rule that future user descriptions of game behavior must be persisted into `design/spec-final.md` as part of the same task. Both changes landed in the same commit.

`design/spec-final.md` gains §12.6 "Unit Spacing and Sub-Tile Occupancy" placed under the existing pathfinding/movement section. The subsection captures: sub-tile occupancy via deterministic slot packing (default 4x4 = 16 slots per tile, alternative patterns allowed if slots are distinct/stable/reproducible); placement / spawn / move / ungarrison / train completion / transport unload / conversion drop / replay-rehydration must resolve to a free slot, with neighbor-tile fallback when the target tile is fully packed; whole-tile blockers (buildings, resources, impassable terrain, out-of-bounds) prevent tile sharing; garrisoned, transported, or otherwise-contained units are exempt while contained; dying units retain their slot through cleanup; renderers may interpolate sub-tile positions independently of simulation slot assignment.

`AGENTS.md` gains a new top-level "Game spec" section placed above the existing "Game specific" engine-feedback section. The new section frames `design/spec-final.md` as the authoritative game definition with the explicit goal of enabling autonomous hand-off iteration without per-change intervention. Five operational rules: persist every user-described rule/behavior/mechanic/content/UX/constraint as part of the same task (preparatory, not follow-up); place new content under the topical section that matches; reconcile conflicts so the spec stays internally consistent; keep spec independent of devlog/changelog/architecture pipelines; do not bypass the TDD + multi-CLI review gates for code/tests that follow.

### Reasoning

User stated the goal explicitly: "if the game spec is complete from the beginning you should be able to make the whole game and iterate to completion without my intervention." Persisting normative game rules into the spec immediately (rather than relying on conversational memory) is what makes that hand-off feasible. Adding the meta-rule to AGENTS.md hardcodes the discipline so future sessions follow it without prompting.

Spec rule placement under §12 Pathfinding/Movement matches the topical structure — adjacency to §12.3 Pathfinding ("collision-aware movement") and §12.5 Movement Rates makes the new rule discoverable when a future implementer touches movement code. Meta-rule placement above "Game specific" pairs spec discipline with engine-feedback discipline as the two game-domain operational rules.

### Notes

The current `worldOccupancy.ts` implementation gives each unit a unique sub-tile slot via `OccupancyBinding.occupySubcell` with 16 slots (4x4 grid, lines 26-43), so the spec rule is enforced for the common case. The exception is the overflow path (`addOverflowCrowdedClaim`, lines 173-188) that lets a 17th unit land on the same integer cell with no slot when all 16 are taken. The new spec rule says fall back to a neighboring tile in that case; the current code does not. Whether this manifests as a visible regression in `npm run dev` has not been verified — per the "reproduce bugs in npm run dev first" rule, an overflow fix will only be filed if a real reproduction surfaces. The spec text covers the rule for any future iteration that does encounter the case.

`docs/engine-feedback/current.md` is unchanged. The prior occupancy concerns were closed when the engine shipped `OccupancyBinding`, and the overflow gap (if it manifests) is a game-side fallback decision, not an engine miss.

No version bump or changelog entry. The runtime behavior of the game has not changed; this is rule documentation that future implementations will respect.

## 2026-05-08T14:30:00-07:00 - File-size split + castle-upgrades timeout + visual-non-overlap infrastructure (partial)

### Action

User asked for three follow-ups from the spec-discipline commit and clarified §12.6: visual non-overlap (not just simulation-level slot tracking) is the contract — players see sprites, not slots.

**1. `src/game/simulation/bridge/unitCommandOps.ts` split (file-size budget cleanup).** Extracted `routeMonkContextAtEntityCommandDirect` (~55 lines) plus the `MonkContextRouteOptions` type to a new sibling file `src/game/simulation/bridge/monkContextOps.ts` (108 LOC). `unitCommandOps.ts` is now 486 LOC (under the 500 hard limit). Ungarrison-time monk routing semantics unchanged — the new module is a pure relocation. Closes the post-iter-2 multi-villager-construction regression that the v0.1.17 closeout had missed.

**2. `tests/simulation/castleUpgrades.test.ts` per-test timeouts bumped from 15s to 30s on six entries.** The suite-level default is 30s; this file's explicit caps were too tight for full-suite contention under the threads pool. When isolated, the 15 tests run in ~118s (~8s each); under load they sometimes overrun 15s. Bumping to 30s aligns with the rest of the file's longer cases and the vitest-config default. No simulation behavior change.

**3. Visual non-overlap (spec §12.6) — infrastructure built; production wiring deferred.** The plan was to thread the engine-allocated slot offset (`OccupancyBinding.occupySubcell`'s `placement.offset`) through `getUnitTargetTransformForCell` so unit sprites land at distinct sub-tile positions, and add a spawn-time neighbor-tile fallback for cells that already host 16 units. The slot-tracking and neighbor-search infrastructure landed and is covered by tests (`tests/simulation/worldOccupancyVisualSlots.test.ts`, 9 tests):

- `worldOccupancy.syncUnit` now returns `{ placedAt, slotOffset }` instead of void; existing call sites that ignore the return value compile unchanged.
- `worldOccupancy.placeUnitForSpawn(entity, requestedPosition)` walks `binding.neighborsWithSpace` and redirects to a free slot in a neighboring cell when the requested cell is full.
- `worldOccupancy.getUnitSlotOffset(entity)` exposes the engine-allocated visual offset for renderers and movement code to read.
- `pureHelpers.getUnitTargetTransformForCell` and `isUnitTransformAtTarget` accept an optional explicit slot offset (callers without context fall back to the existing `entityId % 4` derivation).

Production wiring was reverted before commit. An earlier draft threaded the allocated slot through `transformOps.syncOccupancyForEntity`, `moveUnitOneSubgridStep`, the train-completion path, and the ungarrison path. Three regressions surfaced under the full test suite: the `createSimulationBridge.unitMovement` test ("renders unit motion on a finer sub-grid") observed exactly 1-tile-per-tick movement instead of <1 because re-snapping the transform on every cell crossing teleported the sprite by the slot delta; `fogMemory` saw the enemy house projected as a memory entity from the first read because the snap shifted the scout's sub-tile position before visibility was first computed; and `aiPlayer` / `imperialUpgrades.castleBlacksmith` / `autoAggression` flaked under the threads pool when the productionQueueSystem double-allocated through `placeFreshSpawnUnit`. Architectural barrier: a unit mid-move toward a full target cell would have movement re-aim each tick at the same target, syncUnit redirect to a neighbor each cell crossing, and the sprite oscillate at the destination. The proper fix is at the move-command layer (update target on overflow at arrival, or pre-reserve a slot when the move is issued); that change is deferred to a future iteration that owns the movement system.

The infrastructure stays in `worldOccupancy.ts` so the future iteration can pick it up without re-deriving primitives. Spec §12.6 wording remains aspirational ("the simulation must fall back to a free slot in the nearest available neighbor tile") — that's the goal; today's implementation tracks slots correctly and has the placement helpers, but doesn't consume them in the renderer. The user-visible game behavior is unchanged from 0.1.17.
