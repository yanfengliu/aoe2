## 2026-08-30 — Three spec-conformance gaps a completeness audit found

**Timestamp.** 2026-08-30, after the wildlife/scout commit.

**Action.** Closed the three gaps from the tech-completeness audit that were code rather than content: the Dock counting toward Feudal, the "or 1 Castle" alternative for Imperial, and the Incas team bonus.

**Why these three and not the headline.** The audit's biggest finding was that twelve of thirty civilizations have no unique unit and no unique technology — and that one is a DATASET gap, not a code one: `units.csv` and `technologies.csv` have no rows for any of them, and §9.2 already says so. Closing it means authoring roughly 41 CSV rows, which is a different kind of work. These three are code disagreeing with a spec that is already written, which is the cheaper and more embarrassing category.

**The Dock.** §7.2's table says Dark → Feudal takes two of {Barracks, Dock, Lumber Camp, Mill, Mining Camp}. `DARK_AGE_PREREQUISITE_BUILDINGS` held four of the five, on the strength of a sentence in the same section reading "This land-only slice has no Dock". That sentence stopped being true when the naval slice shipped a Dock that §7.3 lists as a Dark Age unlock — so the spec contradicted itself and the code followed the stale half. A water opening of Dock plus Mill is an ordinary AoE2 opening and it could not age up. Both halves fixed: the set, and the sentence.

**The Castle.** §7.2 says "2 qualifying Castle Age buildings **or 1 Castle**". Only the count existed, and a Castle merely counted as one of the two, so a player who had committed to a Castle and nothing else from that tier was locked out of the age the Castle exists to reach. The alternative is the whole point — a Castle costs more than two of anything else in its tier.

**The Incas.** "Farms built 50% faster", and the only unimplemented team bonus not covered by a spec deferral: §9.2.2 names four deferred lines and this was not among them, in neither list, for several versions. The seam existed — `buildRateMultiplier`, shared by Spanish builders and Treadmill Crane — but it took only the builder's civilization, and this bonus is scoped to the BUILDING. It now takes what is under construction.

**Both tests for it, and why there are two.** A unit test on the multiplier, and a second that builds an actual farm in an actual match and compares completion ticks against a Britons control. The second exists because the audit that found this gap found it by looking for table rows whose effect nothing reads — a constant plus a unit test is exactly that shape. Red-checked by stubbing the wiring to `false`: 200 ticks against 200, and the message says the bonus never reached the builder.

**One pinned test had to change.** `prototypeRules.test.ts` asserted the Dark-Age prerequisite list as the land-only four. That pin was the shape of the defect rather than a guard against it, so it now names all five with the reason.

**Gates.** `npm test` 3,053 passed / 3 skipped, typecheck, lint, build, corpus all 0.

### Review of the above

**The fix was half-applied and the missing half was an error message.** `canAdvanceToImperialAge` learned the "or 1 Castle" rule; `researchAvailability` did not, so a Castle-Age player with one University was still told "requires 2 completed Castle Age buildings … you have 1" — advice that is now false, and reaches both the agent snapshot's `researchLocked` reason and the HUD's rejection toast. The canon says an error message must name what would satisfy it. This is exactly the class the test header in this change claimed to be guarding against — "a rule that is right in one table and never reaches the surface that consults it" — one surface further on than I looked.

**Two of my assertions were direction-only where the magnitude was free.** The end-to-end Incas test asserted `incas < britons`; review set the multiplier to 1.01 and watched it pass. The numbers were knowable — a farm is 150 build ticks plus a ~50-tick walk both civs share, so 150/1.5 gives Incas 150 against Britons' 200 — and are now asserted exactly. The new message test was worse: it asserted the reason contained "castle", and the candidate list already ends "…, monastery, or castle", so it passed with the alternative removed. It now asserts the alternative phrase, red-checked.

**Two controls that could not fail.** The Dark-Age exclusion list named houses, farms, walls and the Town Center but not `outpost` or `fish-trap` — the two Dark-Age-buildable non-qualifying buildings, which are precisely what a widened set would sweep up. And the imperial refusal control passed under any implementation that always returned false, so it now carries the positive case alongside it.

**One cost I added on a hot path.** `teamHasCivilization` scans the civilization map and calls `areAllied`; I evaluated it for every builder on every tick regardless of what was being built, one commit after taking tick cost from 15.13 to 5.45 ms/tick. Short-circuited on the building type.

**And a value I took without checking.** `civilizations.csv` says 50%; DE raised it to 100% and later replaced the bonus entirely. The CSV is this repo's stated authority so the number stands, but every neighbouring bonus in §9.2 carries a sourcing note and mine had none — and there is a live lesson in this repo saying a game-rule claim is a hypothesis to check against the wiki. The divergence is now recorded in both the constant and the spec.

**Corrections to documents.** §7.2's other half still said the qualifying sets are "the non-Town-Center buildings introduced in the prior age", which sweeps in walls, gates and towers and had been flagged as wrong by a reviewer on 2026-06-17; a §7.2 conformance pass that rewrote the sentence beside it and left that is the same class it set out to close, so both sets are now named explicitly. A live lesson still described the Dock as "absent in this land-only slice". Two spec citations pointed at §11.11 instead of §9.2.2.

**On CI.** The Windows job went red on the previous commit: `selectionActivity` timed out at 30s. It takes 8s here, and every machine that runs it in CI is slower — the budget had roughly no headroom, and the new tests in that commit competing for cores was enough to cross it. Fixed on both sides: the marginal test has a real budget with the measurement written next to it, and my own tests were re-measured and shortened where the signal allowed (the corner floors run 400 ticks instead of 1,200; the retaliation horizon 300 instead of 1,200, since the wolf is at 1/25 by tick 200). The discriminating corner run keeps its full 1,200 ticks because its signal does not exist below that — 17 cells against the broken build's 19 at 600, with the gap only opening later. An A/B on the scout fix itself put its cost at ~2% of two heavy AI suites, so it is not the cause.

### The behind-building silhouette: attempted, measured, reverted

The cue is opaque and reads as a unit standing ON the building. I made it translucent — its own `occlusion` material, unlit like `ui` but transparent, with the `ui` lane left opaque so the selection outline and drag rectangle stay crisp. The showcase capture looked right, the pixel diff was 0.09% and confined to the silhouette, and the real-map capture showed the wall and window reading through the shape.

Then review measured it properly and it does not survive.

It is close to a no-op under the art style the game ships. The default is `moebius`, and its tone-band quantiser snaps 24.1% of the cue's pixels byte-identical to the opaque render. Every screenshot I judged this by was `painted`.

It introduces seams. A translucent instanced part that overlaps itself blends twice, and the mirror copies a unit's own parts — belt inside tunic, apron coplanar with the tunic face, hair over the crown, arms rolled into shoulders. Solved per-pixel: 452 px at the declared 0.55, 68 at 0.7975 (1−0.45²), 6 at 0.9089 (1−0.45³). Fourteen percent of the body drew at the wrong opacity.

And it broke the half of the cue that matters most. The enemy colour is a coral in the same hue family as every roof in the palette; its mean distance from the background over a bright roof fell from 204.2 to 82.0, while the friendly blue — orange's complement — held. No fixture spawns an enemy-owned occluded unit, so every capture in my evidence set was the blue one. The cue exists to answer "are those mine?", and I degraded the *not mine* answer without seeing it.

Reverted. The engine has the cure for the seams — `markSingleLayerTransparencyInternal`, whose own header describes this exact artefact — and does not export it from `voxel/three`; that is now in `docs/engine-feedback/current.md` as an ask, per the report-don't-modify-engine rule. The defect is registered OPEN with the measurement method the next attempt should use, because the thing that actually went wrong here was not the technique, it was judging a rendered image from one capture, of one art style, with one owner, and calling it verified.

Review also caught a third stale metrics pin I had missed — `voxel-terrain-water.spec.ts` carried the same `materialResources: 7 / instanceBatches: 9` as the two I updated, so the browser suite was red at 1 failed / 134 passed while I had read a piped `tail` status as green. That is the piping lesson again, in a suite I had already been warned about.

### AI self-play audit: what a 40-minute match actually exercises

The standing goal asks for feature completeness "after verifying with AI self-play", and I had never run that audit — the corpus checks age progression and the profiler measures tick cost, but nothing asked what a full match actually touches. So: `aoe2-prototype`, both seats AI, 24,000 ticks (40 minutes of game time), sampling every 250.

    ages first reached   dark 250/250 · feudal 9,250 (owner 2) / 12,500 (owner 1) · castle NEVER
    unit types seen (4)  militia · scout · spearman · villager
    building types (8)   barracks · farm · house · lumber-camp · mill · mining-camp · town-center · watch-tower
    population           t=8,000  11 v 12   →   t=16,000  15 v 29   →   t=24,000  3 v 25
    net losses           71

Two things follow, and the second is the finding.

The match RESOLVES, which is the good news: owner 2 out-economies owner 1 from about tick 12,000 and then destroys it — population 15 down to 3 while the winner holds at 25, with 71 net losses. Combat, targeting, production and the age race all work end to end without a harness propping them up.

But **neither player leaves the Feudal Age in forty minutes**, and the roster the whole match exercises is four unit types and eight building types. No Archery Range, Stable, Blacksmith, Market, Monastery, University or Castle; no archer, no knight, no siege, no monk, no ship. Against a content audit that puts 137 of 138 technologies live with real effects, 93 units trainable and 25 buildings buildable, self-play exercises a small fraction of the game. That is not a claim that the rest is broken — the fixtures and the browser suite reach it — but it is a claim that self-play does NOT currently verify feature completeness, which is what the goal asks it to do. The AI's build order stops at the Dark-Age four (barracks, mill, lumber camp, mining camp) and nothing drives it into the Feudal buildings that gate everything above them.

Recorded rather than fixed: making the AI play a full-length game through Castle and Imperial is its own piece of work, and it is now the largest single gap between "the game has these features" and "playing it exercises them".

One methodological note, because it nearly cost the finding: my first pass read `getEconomyState().playerAges`, which does not exist — the field is `ages` — and printed `undefined` for every sample, which I could easily have read as "the AI never ages up at all". The field name was wrong, not the game. Printing the object rather than a derived boolean is what made it obvious.

### Why AI self-play never leaves Feudal — measured, two fixes tried and reverted

Following the audit above, I went after the largest gap: self-play exercises four unit types and eight buildings against a nearly complete content set, because no match ever reaches Castle Age.

The chain is now measured rather than guessed. On `default-seed` the winning AI ends the match with **food 1571, gold 1140, stone 750 and wood 38, holding no Feudal buildings at all**. Castle needs 800 food and 200 gold — it has both, several times over — plus two qualifying Feudal buildings, and those cost 150–175 wood each. Wood never exceeds ~50 on any seed, either side, at any sample.

I tried the two obvious fixes and neither worked, which is worth more than the attempts:

*More wood villagers* — Feudal split `{food:7, wood:4, …}` to `{food:7, wood:6, …}`, roughly 7 wood villagers to 9. No seed reached Castle; variety unchanged. So wood INCOME is not the constraint.

*Unblocking the farm gate* — `pickNextBuildTarget` returns `farm` on essentially every decision tick, so I held farms to the floor while the age-up prerequisites were missing. It made `aoe2-prototype` slightly worse (eight building types to seven) and changed nothing elsewhere. The reason is instructive: a farm is CONSUMED, so the owned count falls back below even a floor of two and the branch re-fires regardless of what the floor is.

What is left is wood SPEND. Every point goes to houses for a growing population and to replacing eaten farms, and the first 150-wood Blacksmith never gets funded. And the age-up reserve makes the state stable rather than transient: `ageUpReserveCost` is empty until the owner already QUALIFIES, so an AI that cannot qualify has nothing protecting a stockpile it also cannot spend — food and gold pile up unspendably while the one resource that would unblock it sits at zero. Forty minutes changes nothing because nothing in the loop pushes back.

Both experiments are reverted; the tree is unchanged. The defect is registered with the acceptance metric a fix must use — what a match EXERCISES across at least three seeds, not Feudal timing, which both failed hypotheses left untouched while changing nothing that matters.

### A fourth attempt at the Feudal wall, and an instrument flaw

The asymmetry looked like the answer: `ageUpReserveCost` protects the age-up RESEARCH, but only once the owner already qualifies, so nothing protects the cost of BECOMING qualified. The AI defends a purchase it cannot yet make and spends the money for the one it can. So I made the farm wait unless the wood also covered the next qualifying building — six unit tests including a red-check, wired through the caller so it was not a table nothing reads.

Measured across the three seeds: `aoe2-prototype` gained a Blacksmith, `default-seed` lost a building, `corpus-seed-b` lost its farms entirely. Reserving for every still-needed prerequisite instead of just the next one moved `default-seed` to ten building types and cost the other two seeds their farms. No seed reached Castle under either variant. Starving the food economy to fund a hall is not a trade worth making. Reverted, tests included.

Four hypotheses now, four failures, each measured: more wood villagers, relaxing the farm gate, reserving for the next prerequisite, reserving for all of them. The consistent shape is that every lever I have pulled moves wood between two things that both need it, and none of them creates any.

And I nearly drew a false conclusion from my own instrument. The exercise metric counts distinct building types across the MATCH, which unions both owners — so a run reporting a Blacksmith and an Archery Range does not show that either owner had two. I had started writing "it qualifies and still will not advance, so the blocker is elsewhere", which that measurement cannot support. Anything about qualification has to be per-owner. The union metric is still right for what it claims and understates the problem if anything, but it is not the metric for the next question, and the next attempt should build the per-owner one first.
