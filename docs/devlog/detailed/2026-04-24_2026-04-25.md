## Auto-aggression: idle military pursues, idle villagers defend (canonical AoE2)

**Timestamp:** 2026-04-24 (evening)

**Action:** Added a new simulation system `prototypeAutoAggression` so
idle military units engage visible enemies on their own (Aggressive
Stance) and idle villagers swing back at adjacent attackers (Defensive
Stance), matching canonical AoE2 default behavior. Until this commit,
every owned unit was fully passive — an idle Knight standing next to an
enemy Archer just took arrows in silence.

**Spec:** `docs/superpowers/specs/2026-04-24-aggressive-military-design.md`.

**Implementation:**

- New simulation system `prototypeAutoAggression` in
  `src/game/simulation/createSimulationBridge.ts`. Runs after
  `prototypeAi` and before `prototypePlayerCommands` so AI-issued
  commands take precedence and auto-issued attack-commands get
  processed in the same tick. Iterates every owned unit, skips:
  garrisoned, dead, monks (own task pipeline), units with any
  `unitCommands` entry (player order honored), and players whose AI
  is disabled (test-only). Computes a per-unit aggro radius:
  villagers always 1 (melee attack range = Defensive-Stance canon),
  every other unit reads its live `visionSource.radius` so tech
  upgrades and fixture overrides flow through unchanged. Picks the
  highest-priority enemy unit in radius via the existing
  `targetPriority` table; falls back to the highest-priority enemy
  building (military-only — villagers never auto-pursue buildings).
  Issues the same shape of attack-command as a player right-click.
- Two new helpers in `src/game/simulation/bridge/targetFindingOps.ts`:
  `findPreferredEnemyUnitInRadius` and
  `findPreferredEnemyBuildingInRadius`. Both use `world.queryInRadius`
  + Manhattan distance + the existing priority tables. Personal LOS,
  not player visibility — Aggressive Stance triggers off the unit's
  own sight, not the player's fog state.
- New `disableAi: boolean` flag on `PlayerStartSpec`. Skips
  `ensureAiState` for that owner; my passive-player gate (`unit.owner
  !== HUMAN_PLAYER_ID && !aiStates.has(unit.owner)`) reuses the same
  signal so the planner AND auto-aggression both stay off.

**Test contract:** new `tests/simulation/autoAggression.test.ts` with 8
cases — pursue-in-vision, ignore-out-of-vision, archer-pursuit-then-
fire, player-order-overrides, villager-adjacent-defense, villager-no-
pursuit, sequential-targets-after-kill, save/load mid-engagement.
Seven new fixtures live in `src/game/simulation/fixtures/combatMatchups
/autoAggression.ts` (registered through the existing
`combatMatchups` barrel and the `prototypeScenario.ts` dispatcher).

**Regressions caught and fixed:**

1. `tests/simulation/createSimulationBridge.unitMovement.test.ts`
   "renders wandering enemy scouts on a sub-grid…" — broke because
   the wandering enemy scout in `moving-enemy-attack-fixture` saw the
   player militia in its personal LOS on the first tick and
   auto-aggressed, replacing the wander order with an attack order.
   Fixed by adding `disableAi: true` to player 2 in that fixture so
   the wander system stays in charge until the human issues an
   explicit command.
2. `tests/simulation/siegeWorkshop.test.ts` and
   `tests/simulation/imperialSiege.test.ts` "holds Mangonel/Onager
   fire when the target is inside its minimum range of 3" — broke
   because the player-2 spearman was spawned with `vision: radius
   1` (intentional fixture trick to keep the AI from melee-ing the
   siege unit), but my first auto-aggression read used the canonical
   `unitVisionRadius('spearman') = 3`, so the spearman scanned at
   radius 3 and auto-aggressed the Mangonel/Onager. Fixed by
   switching the auto-aggression radius read to the unit's live
   `visionSource.radius` (with the canonical table as a defensive
   fallback). The visionSource is the authoritative per-unit LOS that
   already drives fog reveal — fixture overrides and tech upgrades
   like Tracking flow through unchanged.

## Selection panel: sheep now appear as icons in multi-selection

**Timestamp:** 2026-04-24 (afternoon)

**Action:** Fixed a HUD bug where owned sheep included in a multi-selection
were silently dropped from the selection panel's icon grid. Root cause:
`renderSelectionIcons` in `src/ui/hud/selectionPanel.ts` only iterated
`economyState.units` when classifying selected entity ids; sheep live in
`economyState.resources`, so every sheep id failed the `unitsById.get(id)`
lookup and got skipped. With four sheep selected the panel showed an empty
icon grid; with mixed villagers + sheep the grid showed only the villager
chip.

The fix is a 4-touch additive change:

1. `src/game/simulation/types.ts` — added `id: number` to the
   `EconomyState.resources` entry shape.
2. `src/game/simulation/createSimulationBridge.ts` — `getEconomyState()`
   now passes the entity id through into the resources payload.
3. `src/game/simulation/bridge/pureHelpers.ts` — `isEconomyResourceEntry`
   type guard updated to include `id` on both sides.
4. `src/ui/hud/selectionPanel.ts` — `renderSelectionIcons` now also
   builds a `sheepById` map from resources (filtered to
   `resourceType === 'sheep'`), classifies each selected id as either a
   `UnitType` or `'sheep'`, and emits the icon chip via
   `formatEntityIcon` / `formatEntityIconAccent` / `formatEntityName`
   (which already support sheep). Single non-unit selections keep using
   the existing entity-icon big chip path so the
   `data-selection-entity-icon="sheep"` contract that the existing
   single-sheep browser test depends on stays intact.

A small infrastructure change (`src/app/bootstrap/browserTestApi.ts`)
exposes `selectUnitsInBox(minX, minY, maxX, maxY)` from the simulation
bridge through `__AOE2_TEST__`. The existing
`selectOwnedUnitsByTypeInRect` only selects a single type at a time, so
without this addition the screenshot-capture script could not reproduce
the mixed villager-plus-sheep selection state from outside the Phaser
mouse stack.

## Default-map narrow-path bug: starting villagers walled in by resource clusters

**Timestamp:** 2026-04-24 (continuing through late morning)

**Action:** Fixed a default-map pathfinding bug where the starting villagers
at (6, 8), (6, 9), and (7, 9) on seed `aoe2-prototype` could be completely
walled into a pocket by the procedural resource-cluster placer. The berry
arc at (5, 7)(6, 6)(7, 5)(8, 5)(9, 5) plus the sheep cluster at
(5, 8)(5, 9)(6, 10) and the west-side water/forest strip sealed the
villagers off from the western half of the map. `findGridPath` correctly
returned null for any move target in the unreachable region; the move
command was silently cleared; the user saw villagers that "seemed stuck."

The fix reserves four guaranteed-clear cardinal exit corridors through
the resource-placement predicate in
`src/game/simulation/mapGeneration/applyStandardPlayerOpening.ts` — a
2-row horizontal corridor aligned with the villager spawn rows
(`y = TC.y` and `y = TC.y + 1`) and a 2-column vertical corridor aligned
with the TC center (`x = TC.x + 1` and `x = TC.x + 2`), each extending
13 cells past the TC center (past the outermost forest ring 12). The
`placeResourceCluster` walker skips corridor cells, so no cluster arc can
wrap all the way around the TC and meet an adjacent cluster to form an
impassable wall.

## civ-engine 0.5.3 migration: in-place renderable mutations need explicit refresh

**Timestamp:** 2026-04-25 (evening)

**Action:** `civ-engine` rolled forward today from where this repo previously sat (last touched while v0.3.x was current) to **v0.5.3** in three breaking-change waves (0.4.0, 0.4.1 → 0.5.0 → 0.5.1, 0.5.2, 0.5.3). `node_modules/civ-engine/package.json` already reports 0.5.3, so the breaking changes are live in this build. Audited the aoe2 surface against `../civ-engine/docs/changelog.md` and the corresponding architecture / drift-log entries. Fixed the two real bugs that were biting; confirmed every other breaking change either does not apply or already fits the new contract.

**Breaking changes that DID hit aoe2:**
- **0.5.0 — removed `ComponentStoreOptions.detectInPlaceMutations` + `WorldConfig.detectInPlacePositionMutations` + `World.markPositionDirty`.** Direct in-place mutation of components (`world.getComponent(id, 'renderable').visualVariant = 'complete'`) is no longer detected by the diff machinery, so `RenderAdapter` keeps the pre-mutation projection in `RenderStore` forever. The bridge already has a `markOutOfBandRenderChange()` escape hatch for this exact case at most existing call sites (Monk conversion `bridge/monkTaskOps.ts:440`, sheep claim via the `didChange` return at `createSimulationBridge.ts:5807`); two sites had been silently relying on the old auto-detection: construction-complete in `createSimulationBridge.ts:5239-5243` (fixed earlier today as `d0af9cb` while running the validation gate, before knowing about the civ-engine bump) and tech-upgrade in `bridge/technologyOps.ts:upgradeOwnedUnits`. Both are now bridged.
- **0.5.0 — `world.grid` is now a runtime-immutable read-only delegate.** No aoe2 call site mutates the grid through `(world.grid as any).insert(...)` (verified by grep), so this is a non-event for us.
- **0.5.0 — `EventBus.emit` rejects non-JSON-compatible payloads.** aoe2 doesn't emit events directly (`grep -rn 'world\.emit\|emit(' src/` returns nothing relevant), so no breakage.
- **0.4.0 — fail-fast tick semantics.** `world.step()` now throws `WorldTickFailureError` on tick failure and the world stays poisoned until `world.recover()` is called. The bridge's `step()` at `createSimulationBridge.ts:7212` calls `world.step()` in a loop with no try/catch. **Defensive gap, not an active bug:** tests do not trigger tick failures, and a thrown WorldTickFailureError currently propagates to the Phaser scene's error handler. Deferring active poison/recover handling to a separate sprint — adding it now is preempting a failure mode that doesn't reproduce.
- **0.4.0 — `WorldSnapshot` is now v5.** v4 still loads (per the engine's migration note), and `aoe2`'s `SAVE_SCHEMA_VERSION` is independent of the engine snapshot version. Confirmed by reading `bridge/saveGameOps.ts` — no change needed.

**Breaking changes that didn't apply:**
- **0.4.0 — `getDiff()` / `getEvents()` deep-clone.** aoe2 does not call these directly.
- **0.4.0 — `setMeta` throws on duplicates.** aoe2 does not call `setMeta`.
- **0.4.0 — `destroyEntity` callbacks observe `isAlive(id) === false`.** aoe2's destroy callbacks (in `createSimulationBridge.ts`) read entity state via the side maps, not via `world.isAlive`. No breakage.
- **0.4.0 — `GameLoop.step()` no longer auto-advances.** `GameLoop` is not exported from civ-engine's `src/index.ts`, so aoe2 cannot have been importing it.
- **0.4.0 — failed-tick events emit aborted-handler payloads.** aoe2 does not subscribe to command-execution events.
- **0.5.1 — listener exception fail-fast.** aoe2 does not register any of `commandExecutionListener` / `commandResultListener` / `tickFailureListener`.

**Result:** One commit lands on top of the review-findings batch — `87d4d9f` "Tech upgrade: trigger out-of-band render refresh". Threads `markOutOfBandRenderChange` through the technology-ops dep bag and calls it once at the end of the upgrade loop (single full re-project amortizes across all upgraded units in the same research event). New regression test in `tests/simulation/castleUpgrades.test.ts` ("reflects the upgraded unit type in render state, not just economy state") would have caught the bug — the existing 14 cases in that file all assert on `getEconomyState()` (which reads ECS components directly) rather than `getRenderState()` (which reads through the projector). Validation: `npx tsc --noEmit` clean, `npm run lint` clean, full `npx vitest run` **47/47 files, 393 passed + 1 skipped, 0 failed** (one more passing test than the prior gate run thanks to the new render-state assertion).

**Reasoning:** civ-engine 0.5.0's removal of in-place mutation auto-detection is exactly the correctness-vs-performance trade-off the engine has been progressively tightening (snapshot isolation in 0.4.1, listener fail-fast in 0.5.1, etc.). The net effect on aoe2 was small because the bridge already ran most renderable-affecting transitions through `markOutOfBandRenderChange()`; only two sites were silently relying on the old auto-detection. The earlier `d0af9cb` fix already framed the bug correctly even though it pre-dated my realization of the civ-engine version bump.
