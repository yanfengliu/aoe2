## 2026-09-02 — DE build times, the multi-builder curve, nearest-edge approaches, AI construction crews (v0.3.187)

**Action.** Fixed findings F1-F4 of the 2026-09-02 play test, plus two defects those fixes exposed. Data: `structures.csv` House 30 -> 25 wood (four age rows) and Outpost 10 -> 5 stone, both rows contradicting the aoe2techtree dataset the CSV cites. Runtime: `BUILDING_BUILD_TIME_TICKS` now derived one-for-one from `structures.csv build_time x TPS`; `CONSTRUCTION_COSTS` gained the Watch Tower's missing 25 wood and lost the Wonder's 1000 food. Mechanics: AoE2's multi-builder curve implemented in `builderWorkStep`; approach candidates sorted nearest-first in the new `approachOrdering.ts`; the new `aiBuildCrewPhase` reinforces the AI's in-progress sites.

**What was believed and proved false.** That F3 was four wrong build times. Differentialling the whole column found SIXTEEN — the play test could only see the four a Dark Age opening reaches, and the same sweep over the cost column found three more the play test never touched at all. That the spec's multi-builder formula was implemented: §7 and §16 both state `3 * base_time / (builders + 2)`, and the code added one tick of progress per builder per tick, so five villagers built five times as fast. Measured 5.00 before, 2.33 after.

**That the 37-builder Wonder was an AI bug.** It was, but not first. With `aiBuildCrewPhase` in and 37 villagers holding build commands on the Wonder, the site still gained exactly 1.00 progress per tick — because `findMovementPathToCandidates` returns the FIRST candidate cell it can reach and they were all queued for the one cell the footprint enumeration named first. F2's one-line root cause and the crew cap were the same defect. Fixing the order fixed both, and the crew phase then measured 13.0/tick.

**A fix that was too broad, caught by the suite.** Sorting candidates nearest-first inside `findMovementPathToCandidates` broke 99 tests: a plain MOVE's candidate list is arrival SLOTS, and the caller's order IS the allocation. Scoped to the two approach planners: 5 failures. The ordering now lives in `approachOrdering.ts` and the generic search takes no new parameter — the caller orders its own list, which is also what got `movementPlanOps.ts` back under the 500-line cap (496 -> 524 -> 497).

**Two gate re-anchors, both measured rather than assumed.** `aiReachesCastleAge` read `report[2]` and reported "walled into Feudal". Measured: the boot map's self-play WINNER FLIPPED. Owner 1 now takes it — Castle 29,500, qualified 27,750, peak army 40 (trained 51, lost 11), 8 building types, 7 unit types — and owner 2 is off the map by 30,000 (no Castle, peak army 3, zero villagers). Baseline was owner 2 at Castle 25,250 with peak army 20, so the army doubled. The gate now reads whichever slot reaches Castle first and prints both. `movementTrafficReliefBootMap` measured 0 relief admissions where 229 were the baseline. The CONTROL mattered: with `orderApproachCandidates` disabled by an env flag the boot map still gave 0, which is how the changed MATCH (owner 2 wiped out, too few units to contest a passage) was established as the cause instead of the pathing. A guard granting zero admissions asserts nothing about phantoms either, so the file moved to `default-seed` and was renamed `movementTrafficReliefSelfPlay.test.ts` — 181 admissions across 10 units, first at tick 18,006, phantom 0.

**A test premise that improved into falsehood.** `fogMemoryFixturePremise` asserted the scout WANDERS off and lets the enemy house fall to memory within 8 ticks; its own failure message said "the scout no longer wanders off — the browser spec may be able to pin the premise directly again". It does not wander now: a unit already in range of what it is attacking picks its own cell and does not walk, so the house stays in live vision for at least 300 ticks. The test now pins the stable premise, which is a stronger guarantee for the browser spec that consumes it.

**A test that failed on a movement change while measuring an arrow cap.** `fu3DefensiveFire`'s two garrisoned-archer cases garrisoned five archers and then stepped a fixed 15 ticks. The fifth archer now arrives at tick 12, so the volley landed outside the window and a test about the ARROW CAP failed on approach ordering. Both cases now wait for two events — everyone inside, then the first volley — and refuse to measure if the Castle fires before the crew is in, which would make the count wrong rather than late.

**Tick budgets are the recurring cost of a pacing change.** Eleven fixed `for (let i = 0; i < N; i += 1) bridge.step(100)` loops and three browser `advanceTicks(N)` calls broke at once, each on a number that was right when written. Converted to condition waits behind two new helpers — `stepUntilBuildingComplete` (simulation) and `advanceUntilBuildingComplete` (browser). The browser one has a trap worth naming: it returned instantly for the second-Town-Center spec because the fixture ALREADY has a complete Town Center, and the failure surfaced three assertions later as "food 200, expected 150" (a foundation selects, and trains nothing). It takes an optional position for exactly that case.

**A fixture that measured opening arithmetic, not behaviour.** `ai-rush-fixture` is bare grass with no gatherable resource at all, so the AI ran the whole rush off its 200 starting food. At DE build times it spent that food on villagers while the Barracks went up and could never afford the 60-food Militia — zero militia in 12,000 ticks, against a villager kill at tick 741 on the old build time. Four sheep near the AI's Town Center (clear of its 4x4 footprint — the seed validator's error message named the overlap precisely) restored the rush: kill at tick 1,371, and the AI's food economy keeps running instead of pinning at 0.

**Result.** 3137 unit tests, 145 browser tests, typecheck, lint, build all green. Play test measured through the real mouse and HUD: walk 2.5 s (was 22.0) + build 24.8 s (was 11.9, DE is 25.0), now ASSERTED in `play-opening.spec.ts` rather than annotated.

**Notes.** F5 and F6 (both HUD) are untouched here and are being done separately. `structures.csv` is CRLF, which cost time: a throwaway probe's regex failed on every row because `(.*)$` will not cross the `

## 2026-09-02 — The corpus gate caught two defects a green local gate could not (v0.3.188)

**Action.** Fixed the two failures `playtest-corpus` reported on v0.3.187's first push. The fog-memory slot no longer re-serialises whole every tick; nearest-first approach ordering is confined to the walk to a construction site; the corpus horizon moved to 20,000 ticks; `aiReachesCastleAge`'s bars were re-derived.

**What was believed and proved false — three times, and controls did all three killings.** That the bundle overflow was a size problem to be worked around. It was a CONTENT problem: `lastSeenTick` is written for every visible entity every tick and read nowhere, and a codec slot diffs whole, so a field with no consumer was two thirds of a 537 MB replay. That DE build times had slowed the AI past the corpus horizon — reproduced with the old times restored behind an env flag, so not the data. That the town bell was latching on an enemy that had stopped wandering; that reads convincingly, a shelter cap was built for it, and it moved the measurement by exactly nothing (stockpile delta 162 before and after, Feudal at 14,100/13,800 with the cap and with it disabled). It was reverted. Two of the three would have survived any amount of re-reading the code.

**What actually found it.** Tracing POSITIONS rather than reasoning about state: all nine of owner 2's villagers stood on one cell (51,28), motionless across a 60-tick trace, every one latched in `to-resource`. That is the signature, and it named the cause immediately — a whole workforce converging on one nearest cell.

**A fix narrowed twice, by two different instruments.** Nearest-first went into `findMovementPathToCandidates`, where every caller inherited it: 99 unit-test failures, because a plain move's candidates are arrival SLOTS and the caller's order is the allocation. Narrowing to "approach plans" cut that to 5 — and still covered the resource and drop-off walks, which only self-play could see. The final scope is one boolean passed from `playerCommandsSystem` for a `build` command on an in-progress site, carried in the plan cache key. The lesson is in `approachOrdering.ts`'s header, where the next person to widen it will read it.

**A gate whose window stopped before the end of the GAME — and a defect I filed that does not exist.** Re-calibrating `aiFeudalStone` I widened its measurement window and it failed. The economy on `ai-feudal-stone-fixture` goes byte-identical at about tick 15,000 and stays that way to 24,000, with the day's ordering change both on and off — 26 villagers stationary across a 60-tick trace, not one moving even a sub-cell, 13 of them in `to-dropoff`. I filed it as an open deadlock. It is not one: the MATCH ENDS at 15,000 by conquest (owner 1 wiped out, scores 1:70 2:1492), and a finished match stops. One `getMatchState()` call would have said so, and I made it only after writing the register entry. The entry is now a retraction, kept because the mistake is the useful part: a still world reads identically whether it is deadlocked or decided, and I had just fixed a REAL deadlock with the same signature an hour earlier, which is exactly what made the second reading feel confirmed.

**A bar lowered, and why that is not the forbidden move.** `aiReachesCastleAge`'s peak-army bar went 19 -> 8. Measured at its 45,000 horizon the first slot to Castle now shows peak 9 where the old baseline showed 20 — but run to 90,000 and owner 1 reaches peak 45, more than double that baseline, with the match still unresolved. DE build times make construction 2-2.5x longer, so the army arrives LATER rather than smaller, and 45,000 stopped being past this map's conquest at 39,890. The horizon stays at 45,000 for runtime; the cost — that the gate can no longer see an army regression between 9 and 19 — is recorded in the defect register rather than absorbed.

**Two tests from v0.3.187 were REVERTED with the change that motivated them.** `fogMemoryFixturePremise` had been rewritten to assert the scout HOLDS its ground (true while every approach sorted nearest-first); with the narrowing it wanders again, so the original premise is the true one and was restored verbatim. `fu3DefensiveFire`'s two arrow-count cases had been rewritten to wait on events instead of a fixed 15-tick window; restored, with a KNOWN WEAKNESS now recorded in the file — measured while rewriting, the Castle fires at tick 10 with only FOUR archers in, which already yields the capped five arrows (1 base + 4), so the 50 damage that test reads cannot tell "five garrisoned, capped at five" from "four garrisoned, five arrows". It excludes 1 + 5 = 6 and nothing more. Measuring the NEXT volley does not fix it: the Champion is at 20 HP by then and dies to it, so the damage is clamped by its remaining health. A stronger form needs a target that survives two volleys.

**Two more tick budgets moved on measurement, not on guesswork.** `gatherDomain`'s villager-growth wait went 14,000 -> 20,000: the AI reaches 15 villagers at tick 16,000 now (measured 10 at 5,000 and 10,000, 14 at 15,000), where 14,000 was ample before. `aiFeudalStone`'s window stayed at 14,000 for the reason above.

**Result.** Corpus green by EXIT CODE (not by reading its summary). 3,140 unit tests, 145 browser tests, typecheck, lint, build. Bundle 537 MB -> 181 MB. Fog memory verified by capture on `fog-memory-fixture`: remembered terrain and the remembered enemy house both still render.

**Notes.** The `visibility` slot is 66 MB of the remaining 181 and has the same shape as `lastSeenStatic` — the next bundle blow-up if recorded state grows another 3x. Nothing fails until a bundle crosses the ceiling, so that limit is still unguarded.

## 2026-09-02 — The command deck: DE's two build pages, icon tiles, and the bar that stopped clipping itself (v0.3.189)

**Timestamp.** 2026-09-02, worktree `agent-a9e594cb8a8fe13ef`, from the owner's request to split the build menu into DE's pages, replace the labelled command boxes with icons, and fix play-test findings F5 and F6 with them.

**Action.** DE's two build pages (`selectionPanel/buildPages.ts`, `buildPalette.ts`), square icon tiles for Orders/Stance/Formation and the build cards (`icons/commandGlyphs.ts` — eight new hand-authored 24x24 `currentColor` glyphs plus two page-tab glyphs), a rebuilt bar geometry that fits its content at 800x600, and a tooltip-ownership rule that lets a clicked card keep focus without keeping its tooltip.

**Measured before, 800x600, villager selected.** Panel 204px tall, `overflow-y: hidden`, content 396px. The BUILD group's box was y 647-767 against a panel clipped at 588: six of its ten cards entirely off-panel, four of the eight stance/formation buttons cut, and the stat rows gone. No wheel reached any of it — `.hud-panel--selection` is `pointer-events: none` and neither the panel nor `.hud-build-menu` was in the allowlist — and the existing suite only ever reached the cards because Playwright's `locator.click()` scrolls hidden overflow. **After:** zero clipped elements and `scrollHeight == clientHeight` at 800x600, 1280x720 and 1920x1080, for a villager on both pages, a scout and a Town Centre. Panel heights after: 227 / 186 / 186 (villager), 196 / 213 / 213 (scout), 187 / 243 / 243 (Town Centre). Ceilings `min(36vh, 268px)` unwrapped and `min(42vh, 252px)` wrapped — the second is set by the CAMERA rather than by the content: at 800x600 a 276px bar's top edge is y 312 and everything the game centres lands at y≈300-320, which is how a Dock's newly trained Transport Ship ended up behind the bar in `new-tech-reach.spec.ts` (the third test the bar's height moved, after the Watch Tower fixture and the opening play test). Gated: `leaves the centre of the canvas clear, whatever is selected`.

**What was believed and proved false.** Three things. (1) That F5 was a narrow-viewport defect. It was not: at 1280x720 and 1920x1080 the selection summary's own 186px `overflow-y: auto` box put Faction, Civ and Inventory OUTSIDE the panel (y 708-769 against a panel ending at 708) — the same defect at every width, never reported, and invisible to a check that only looks at `[data-command-group]`. The gate now measures every stat chip too. (2) That `:focus-visible` was the right primitive for F6. It is the browser's own answer, and it is wrong HERE: a synthetic `focusin` — the shape of every unit test of this controller — focuses nothing, so `matches(':focus-visible')` answers "not keyboard" for every test and "keyboard" for none; three tooltip suites went red before the try/catch fallback was even reached, because jsdom implements the selector rather than throwing on it. The rule is a pointer-down flag instead, sticky until the next keystroke because the panel re-renders and restores focus a frame after the click. (3) That a taller bar was free. It is not, and two tests measured the cost before any critic did: the Watch Tower fixture's preferred placement anchors are chosen by "is this cell reachable by the mouse", so the bar growing 204 -> 227px pushed the tower to a cell 6.3 cells from the enemy Scout (line of sight 6) and it never fired; and the play test's Town Centre click landed on the bar. Both were fixed as what they are — the fixture leads with anchors high on the isometric screen and gets a tick budget with headroom (520 was a knife edge: the build finishes at ~400 and the Scout dies at ~600), and the play test scrolls the view with the arrow keys first, as a player would.

**What the numbers paid for.** Icon tiles driven by one token pair (`--hud-command-tile` 44px, 34px below 1120px) so a narrow window shrinks the whole deck at once; the selection summary laid out ACROSS the bar (portrait beside the name, stat chips wrapping inside what is left) instead of down a 264px column that was 300px tall; the portrait's redundant name caption dropped below 1120px, which bought a whole row of stat chips; a ceiling of `min(36vh, 268px)` wide and `min(46vh, 276px)` wrapped; and the panel sized to its content rather than stretched — at 1920x1080 the stretched bar was ~800px of empty glass beside a five-tile card.

**Build pages.** `Record<BuildableBuildingType, BuildPageId>` makes a page-less building a typecheck error, and `tests/ui/buildPages.test.ts` walks the union parsed out of `types.ts` for the runtime half (dropping `outpost` turns 3 of its 5 tests red). The shorter page is padded with inert empty slots so both pages fill the same number of rows — the toggle sits above the palette, and a palette that changed height would move the control that had just been clicked. The palette follows a placement in progress onto its own page, so the "Placing: …" pill in the Build heading is always above the highlighted card.

**Result.** `npm test` 0 (450 files, 3,140 tests), typecheck 0, lint 0, build 0, `npm run test:browser` 0. BLOCKING 2: F5 was not fixed as a CLASS — the critic swept ten shipped fixtures and every owned entity type (47 selections) and found 16 still clipped at 800x600, a Blacksmith's research row running to x 1724 against a panel ending at 588, `research-loom` off screen on a Castle-Age Town Centre — all pre-existing, all made smaller and none removed by my fix, while the spec I wrote in the same commit asserted they were gone. MAJOR findings applied: the page toggle was a dead control during placement and recorded the press anyway, so the palette flipped pages when placement was cancelled (a choice now outranks placement); the toggle MOVED 113px when placement started, because the container query hides the title and count around it (it now LEADS the heading row, where nothing can move it); `watch-tower` and `bombard-tower` rendered byte-identical glyphs, which was survivable while a card carried its name and is not now (new Bombard Tower glyph, and the distinctness assertion the author had written for stance/formation — where no collision existed — extended over every buildable building). NOT applied: an empty page's tab stays `disabled` and so leaves the tab order — making it focusable-but-inert would let a player switch to a page that renders nothing, and the tooltip is on the tab either way.
