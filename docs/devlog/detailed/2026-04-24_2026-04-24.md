## Selection panel: sheep now appear as icons in multi-selection

**Timestamp:** 2026-04-24 (afternoon)

**Action:** Fixed a HUD bug where owned sheep included in a multi-selection
were silently dropped from the selection panel's icon grid. Root cause:
`renderSelectionIcons` in `src/ui/hud/selectionPanel.ts` only iterated
`economyState.units` when classifying selected entity ids; sheep live in
`economyState.resources`, so every sheep id failed the `unitsById.get(id)`
lookup and got skipped. With four sheep selected the panel showed an empty
icon grid; with mixed villagers + sheep the grid showed only the villager
chip.

The fix is a 4-touch additive change:

1. `src/game/simulation/types.ts` — added `id: number` to the
   `EconomyState.resources` entry shape.
2. `src/game/simulation/createSimulationBridge.ts` — `getEconomyState()`
   now passes the entity id through into the resources payload.
3. `src/game/simulation/bridge/pureHelpers.ts` — `isEconomyResourceEntry`
   type guard updated to include `id` on both sides.
4. `src/ui/hud/selectionPanel.ts` — `renderSelectionIcons` now also
   builds a `sheepById` map from resources (filtered to
   `resourceType === 'sheep'`), classifies each selected id as either a
   `UnitType` or `'sheep'`, and emits the icon chip via
   `formatEntityIcon` / `formatEntityIconAccent` / `formatEntityName`
   (which already support sheep). Single non-unit selections keep using
   the existing entity-icon big chip path so the
   `data-selection-entity-icon="sheep"` contract that the existing
   single-sheep browser test depends on stays intact.

A small infrastructure change (`src/app/bootstrap/browserTestApi.ts`)
exposes `selectUnitsInBox(minX, minY, maxX, maxY)` from the simulation
bridge through `__AOE2_TEST__`. The existing
`selectOwnedUnitsByTypeInRect` only selects a single type at a time, so
without this addition the screenshot-capture script could not reproduce
the mixed villager-plus-sheep selection state from outside the Phaser
mouse stack.

**Reasoning:** The repo's selection model intentionally treats owned
sheep as commandable siblings of units (the bridge's existing
`selectUnitsInBox` already pulls them in alongside `selectUnitIdsInRect`),
so the HUD icon contract should reflect that. Adding `id` to the
resources payload is the smallest schema change that lets the HUD look
up sheep by selected entity id — the alternative (a separate sheep
field on `SelectionState`, or a position-keyed lookup) would either
duplicate the unit-style contract or rely on `(x, y)` coincidences that
are not stable for moving sheep. Keeping the single-sheep selection on
the existing `data-selection-entity-icon` path preserves the current
browser-test contract for that case.

## Default-map narrow-path bug: starting villagers walled in by resource clusters

**Timestamp:** 2026-04-24 (continuing through late morning)

**Action:** Fixed a default-map pathfinding bug where the starting villagers
at (6, 8), (6, 9), and (7, 9) on seed `aoe2-prototype` could be completely
walled into a pocket by the procedural resource-cluster placer. The berry
arc at (5, 7)(6, 6)(7, 5)(8, 5)(9, 5) plus the sheep cluster at
(5, 8)(5, 9)(6, 10) and the west-side water/forest strip sealed the
villagers off from the western half of the map. `findGridPath` correctly
returned null for any move target in the unreachable region; the move
command was silently cleared; the user saw villagers that "seemed stuck."

The fix reserves four guaranteed-clear cardinal exit corridors through
the resource-placement predicate in
`src/game/simulation/mapGeneration/applyStandardPlayerOpening.ts` — a
2-row horizontal corridor aligned with the villager spawn rows
(`y = TC.y` and `y = TC.y + 1`) and a 2-column vertical corridor aligned
with the TC center (`x = TC.x + 1` and `x = TC.x + 2`), each extending
13 cells past the TC center (past the outermost forest ring 12). The
`placeResourceCluster` walker skips corridor cells, so no cluster arc can
wrap all the way around the TC and meet an adjacent cluster to form an
impassable wall.

**Reviewer comments:**
- Not circulated to Codex / Gemini / Claude CLI reviewers on this pass.
  The change is bounded: one predicate in one helper, no architectural
  shift, and the new regression test (`defaultMapNarrowPath.test.ts`)
  plus the full 43-file vitest suite (`373 passed + 1 skipped`) lock in
  both the fix and the "units do not block narrow corridors" contract.

**Result:**
- Simulation test `tests/simulation/defaultMapNarrowPath.test.ts` added:
  4 cases, each ordering all three starting villagers to a cardinal
  near-base target (west `(2, 8)`, north `(8, 2)`, south `(8, 14)`,
  east-beyond-TC `(14, 8)`) and asserting every villager arrives within
  3 Manhattan cells. Before the fix, the west and north cases timed out
  with stuck villagers; after the fix, all 4 pass in under 1.3 s.
- Separate regression file `tests/simulation/narrowCorridorMovement.test.ts`
  (added earlier in the same session before the root cause shifted to

  corridor" scenario: a single mover walks past neighbors, a stationary
  friendly in the corridor does not block the mover, a plugged-entrance
  case still lets a mover reach the far side, and a full cluster ordered
  through a 1-cell-wide corridor advances past the entrance. All 4 pass.
- Full validation: `npx tsc --noEmit` clean, `npx vitest run` 43/43 files
  373 passed + 1 skipped (the 6 `[vitest-worker] onTaskUpdate` unhandled
  errors are the pre-existing Windows-only warnings), `npx vite build`

  `src/game/simulation/fixtures/economyBasics.ts` and is wired through

**Reasoning:** `civ-engine`'s grid pathfinder and `OccupancyBinding` both
behave as documented: units stay out of the `blockedBy` list (they only
crowd, per the design lesson at `docs/learning/lessons.md:29-31`), so
narrow corridors populated by friendlies are correctly passable. The
synthetic-corridor regression confirmed that. The only scenario that
actually failed was the procedural default map's specific seed where the
cluster placer wrapped resources all the way around the TC. A
corridor-reservation rule in the placement predicate is the minimum
change that fixes it: it does not touch the cluster-walk logic itself
(still places each cluster's count by ring expansion), does not require
post-generation rework of placed resources, and does not remove any
resources — it only forbids a small cross-shaped band from holding
resources so the ring walker is forced to leave a walkable gap.
