## 2026-09-05 — A finished playtest no longer throws its own recording away

**Action.** `npm run playtest` simulated a whole match — the default is 30,000 ticks, tens of minutes of wall time — and then died on its last line with `RangeError: Invalid string length`, so the bundle was never written and the run was gone: nothing to replay, nothing to inspect, nothing to run the oracles over. `src/game/playtest/bundleIo.ts` and its test were produced by a worker, inspected and accepted by the coordinator, and ship unmodified; the register entry, the devlog and the correction below were written here.

**The ceiling is V8's, and the fix streams rather than shrinks.** `buffer.constants.MAX_STRING_LENGTH` is 536,870,888 characters on Node 24, and it bounds `JSON.stringify` and `JSON.parse` alike because each works on ONE string. Measured on 2026-09-03's 20,001-tick corpus bundle: `ticks[]` is 95.9% of the file at a mean 15.7 KB per tick entry (its `diff` 84%, `metrics` 16%), the whole file is 313 MB, and entries grow as the match fills with units — so the 30,000-tick default lands past the cap. `writeBundleFile` and `readBundleFile` never hold the whole document as one string in either direction; the largest string either side builds is ONE array element (a tick entry, ~16 KB) or one non-array top-level value (`initialSnapshot`, ~0.5 MB). **The format is untouched.** The file is ordinary JSON, byte-identical to what `JSON.stringify(bundle)` produces, which is why bundles recorded before this still load and every other reader of bundle JSON still works. Nothing was sharded, re-encoded or thinned — that distinction is the whole point, because the previous mitigation was thinning: dropping `null, 2` in v0.2.x cost about 40% and MOVED the wall.

**The read side is the half that would have been missed.** A bundle that was written can still be unreadable, and four scripts read one with `JSON.parse(readFileSync(path, 'utf8'))`: `replay-inspect.mjs`, `run-oracles.mjs`, `playtest-corpus.mjs` and `playtest-findings.mjs`. The corpus one is the sharpest — it read the bundle to check age progression, so a long enough run turned the progression gate into an ERROR row on exactly the runs that gate exists to check. All five call sites now go through the pair; `playtest-findings.mjs` goes through it BOTH ways, since it injects agent markers and writes the bundle back through a temp file and a rename.

**The gate refuses to report "did not run" as "passed", which is the part worth copying.** `tests/playtest/bundleIo.test.ts` sizes its oversized payload from `buffer.constants.MAX_STRING_LENGTH` at RUN TIME rather than from a baked-in number, so it keeps crossing the cap if a future Node moves it, and builds it from one shared 8 MB string referenced many times — 8 MB of heap, still past the cap when serialized. Three controls then run before the claim: the written file's size must exceed the cap, `JSON.stringify` on the same payload must throw `Invalid string length`, and `readFileSync(path, 'utf8')` on the written file must throw. A payload that quietly shrank under the cap fails there instead of passing everywhere. A sixth case binds the CALL SITE by reading the text of `scripts/playtest.mjs` and requiring `writeBundleFile(...)` and the absence of `JSON.stringify(result.bundle)`, because the module can be correct while the CLI still calls the old thing — which is exactly how the run was lost.

**Bound, and it is a real one.** The payloads are SYNTHETIC. They prove the serializer survives a document past the cap; they prove nothing about the simulation that produces one. A recorded 30,000-tick run is the only thing that proves the game still records, and that is `npm run playtest` plus `npm run replay:inspect`, not this file. The call-site case is a source check that names one script; the four readers are wired but not pinned that way.
