## Engine "sim-throughput regression" investigated → NOT-A-REGRESSION; caps ratcheted back; engine benchmark blind-spot closed

**Timestamp:** 2026-06-30

**Action.** Investigated the standing `docs/engine-feedback/current.md` claim of a "+50-75% civ-engine sim-throughput regression (0.8.24→1.0.1)" that had caused aoe2 to double per-test timeout caps in 9 simulation fixture files (`x2 2026-06-12`). Proved the regression does NOT exist in engine code, ratcheted the caps back to data-driven values, and (co-evolving the engine) added a benchmark scenario that closes the detection gap that let such a claim stand. Full debug write-up: `docs/debugging/2026-06-30-engine-throughput-regression.md`.

**What was found (ground-truth, not narration).**
- **Static audit:** `git log a53efc2..8a10966` over the per-tick hot-path files (`world-tick`, `world-queries`, `component-store`, `entity-manager`, `world-systems`, `query-cache`) is EMPTY — byte-identical across the whole 0.8.23→1.0.2 window. The only per-tick change is v1.0.0's strict-by-default flip (`world-core.ts`). The named suspects were wrong: v1.0.0's `world.ts` edits are serialize/deserialize-only; v0.8.25's `player-observer.ts` change was an optimization (hoisted `getRegistrationManifest()` out of a loop); the strict guard `assertWritable` is O(1)/allocation-free.
- **Direct A/B on the real fixture:** aoe2 doesn't pass `strict`, so v1.0.0 flipped its worlds false→true. Timing `createSimulationBridge.ageUp` isolated/single-thread: strict-on 42.71s vs strict-off 43.24s — within run-to-run noise. Strict's per-tick cost is ~0 here.
- **Isolated vs contended:** ageUp is ~43s/file (~7s/test) isolated; the +50-75% only appears under the full-suite `threads` pool (CPU saturation). Root cause = contention, not engine cost.

**Cap ratchet (the requested "ratchet back down").** Measured worst-case *contended* per-test times by running all 9 heavy sim files together under the default pool (maximal CPU saturation): worst per-test was 30.5s (ageUp) / 29.8s (blacksmith); the other 7 files ≤14.9s. Set a uniform per-file cap at ~3× the file's worst contended time: **90_000** (ageUp, blacksmithProgression), **45_000** (castleNewUnits, imperialUpgrades.archeryBarracks, createSimulationBridge.production, castleUpgrades, createSimulationBridge.utility, createSimulationBridge.darkAge), **30_000** (autoAggression). Replaced all 67 `x2 2026-06-12: engine-1.0.x sim-throughput regression` annotations with a truthful comment (`contention headroom (full-suite thread pool; NOT an engine regression — see docs/debugging/2026-06-30-engine-throughput-regression.md)`). Removed the absurd 120-180s ceilings. Verified: all 9 files pass under the reduced caps even in the worst-case all-heavy-parallel run.

**Engine co-evolution (civ-engine, script-only, no version bump).** Added a `commands` scenario to the civ-engine benchmark gate (`scripts/rts-benchmark.mjs` + `benchmarks/baseline.json`): a STRICT world driven by per-tick validated commands (accept + reject branches), in-tick emitting handlers/systems, and 14 systems (12 querying across all five phases + movement writer + combat emitter) over 60 ticks on 800 entities. Deterministic tier-1 counters (queryCalls 1560, commandsAccepted/Rejected 3840/960, commandsProcessed 8640, moveHandlerRuns 3840, eventsHandled 17400). This is the aoe2-shape load the gate's occupancy/churn scenarios under-weighted — the gap that let a (hypothetical) per-tick regression go undetected. `benchmark:check` green.

## M6 villager repair — buildings (v0.1.51)

**Timestamp:** 2026-07-01

**Action.** Villagers can now repair a friendly, complete, damaged building (spec §8.1). Right-clicking one routes (`routeUnitContextAtEntityCommandDirect`) to `setUnitRepairCommandDirect`, which — after charging the repair cost up front (`repairCost(buildingType, missingHp, maxHp) = ceil(0.5 × buildCost × missingHp/maxHp)` per resource, gated by `canAfford`/`spendResources`) — queues a distinct `'repair'` `UnitCommand`. The build-command loop branches on `command.type`: `'repair'` restores HP over time at the build rate (`maxHp / buildingBuildTimeTicks`) until full; `'build'` runs construction and clears on complete. Reuses the walk-adjacent flow; multiple villagers repair faster; no per-tick charge. The `startHp` spawn field seeds a damaged building for the fixture.

**Refactor (both for the 500-LOC cap, enforced by `tests/architecture/fileSizeBudget.test.ts`).** The construction-COMPLETE block was extracted from playerCommandsSystem into `bridge/finalizeBuildingConstruction.ts` (behaviour-preserving; 494→490). ## M6 score-timer victory (v0.1.52)

**Timestamp:** 2026-07-01

**Action.** Matches can now end on a timer with the highest score winning (spec §4.3), so games that would otherwise stalemate forever have a definite conclusion. A scenario opts in via a new `gameLength` tick count on `PrototypeScenario` (unset ⇒ map runs indefinitely on conquest/wonder/relic, the AoE2 default). New `bridge/systems/scoreTimerSystem.ts` (`registerScoreTimerSystem`): registered LAST in postUpdate, `after: ['prototypeConquestOutcome']`, and a no-op — not even registered — when `gameLength` is undefined. On the first tick where `world.tick >= gameLength` it compares every player's `computePlayerScore(owner)` in a single order-independent max/count pass and calls `finalizeMatchEnd(outcome, 'score', summary)`: victory when the human is the sole top scorer, draw when tied for top, defeat otherwise. The `!isMatchRunning()` guard means an earlier conquest/wonder/relic resolution on the same tick wins (verified: relicCountdown → winConditionResolver → conquestOutcome → scoreTimer chain).

**Threading + save.** The `WinCondition` union gained a `'score'` member, threaded through `types.ts`, `saveSchema.ts`, `saveGameOps.ts`, `registerAllSystemsTypes.ts`, `conquestOutcomeSystem.ts`, `winConditionResolverSystem.ts`, `matchEndOps.ts`. `gameLength` flows wireBridgeOps (`scenario?.gameLength`) → registerBridgeSystems → registerAllSystems → the system; `computePlayerScore` (already on `MatchEndOps`) flows via the existing `...matchEndOps` spread. Save widening is additive/back-compatible: `winCondition` is a plain passthrough with no runtime whitelist, and old saves only ever carry `conquest|wonder|relic|null`. Slice-1 limitation: `gameLength` is a live-scenario field only — the saved-game load path passes `scenario=null`, so a loaded save resumes with the timer disabled. The post-game card gained a `'score' → "Score Victory"` label (`postGameSummary.ts`). `wireBridgeOps` ratcheted 605→604 (one-line comment trim absorbs the `gameLength` line under the 500-LOC-legacy budget).

**TDD.** `tests/simulation/scoreTimerVictory.test.ts` (4 tests over three fixtures built by a shared `buildScenario`: `score-timer-victory` P1 sole-top 180 vs 50 ⇒ victory, `score-timer-draw` 180==180 ⇒ draw, 3-player `score-timer-defeat` P1 50 < P3 100 < P2 180 ⇒ defeat — exact score assertions confirm the formula) + an EXACT boundary test (still running through step 30, resolves on step 31). `tests/ui/postGameSummary.test.ts` (all four labels + the null-omission case). Full suite green (1503 passed).
