## Self-healing units, and the technology that was waiting on them (v0.3.65)

**Timestamp:** 2026-08-24, continuing the same session as v0.3.60–v0.3.64.

**Action:** shipped unit regeneration (the Vikings' Berserk line, 1 HP every 3 seconds) and Berserkergang, the Imperial Castle technology that doubles it. Fixed two pre-existing defects found on the way: a red lint gate on main, and a spec table that had drifted from the code.

**What was believed and proved false.**

*That a technology whose effect is a RATE can keep that effect outside the technology table.* The first version put `BERSERKERGANG_REGEN_MULTIPLIER = 2` in `unitRegeneration.ts` and gave the `UNIQUE_TECHNOLOGIES` entry no effect field at all, with a comment explaining why. `uniqueTechnologies.test.ts`'s "gives every technology an effect of some kind" guard rejected it — correctly, because that guard exists to stop a technology costing 850 food and doing nothing, and it cannot tell "effect lives elsewhere" from "no effect". The fix was to move the number onto the entry as `regenMultiplier: 2` and have `regenPerTick` read the table, so the technology's whole effect is visible in one place and the guard stayed strict. Widening the guard would have been one line and would have blinded it.

*That a passing simulation test means the player can see the effect.* Four simulation tests proved the Berserk healed at the right rate, in a real match, from a real save blob. The browser test — the health bar, read off the render — showed **zero** change across 300 ticks. `step()` opens with `flushOutOfBandRenderChange()`, so the projection refreshes only when a mutation marks it; damage sites call `markRender`, the technology sweeps call `markOutOfBandRenderChange`, and the new system called neither. The state was right and the screen was wrong, which is the exact failure mode a numbers-only test cannot see. Swept the class afterwards: every other `currentHp` writer (projectiles, blast, monk heal, repair, Loom/Sanctity/Bloodlines) already marks.

*That a fight would supply the wound the browser test needed.* The first fixture stood an enemy militia next to the Berserk to wound it. The probe showed the militia at `idle` while it was beaten to death, and the Berserk at 55/55 — `autoAggressionSystem` skips owners with `disableAi: true` by design, so a passive enemy really is passive. `ScenarioSpawnSpec.startHp` exists for exactly this and made the fixture three lines shorter.

**What a check caught that the author missed.**

`npm run lint` had been failing on `main` since e576d00 (the Petard) and 656e2b3 (Hoardings and El Dorado): a prose comment sitting as the only content of a `case` label reads to ESLint as a fall-through. It survived two commits because the gate was being run as `npm run lint 2>&1 | tail -1` and eslint's last line is blank — filtered output that looks exactly like success. Recorded as a lesson (read a gate's exit code, unpiped) and fixed by moving each comment into the body it explains.

Then, while adding the Vikings row to §9.2.2, the table turned out to have 17 rows against 18 implemented technologies: El Dorado has been researchable since v0.3.57 and the spec never learned. The sentence above the table still said "Sixteen of the nineteen". Both halves are now read by `tests/architecture/specUniqueTechnologyTable.test.ts`, which compares the table's `(civilization, technology, age)` rows to `UNIQUE_TECHNOLOGIES`, checks the count sentence, and checks that every deferred id is named in the paragraph below. Red-checked by deleting the El Dorado row.

**What number moved and from what.** Berserk regeneration: 0 → 1 HP per 3 seconds (1/30 per tick), doubled to 2 by Berserkergang — measured on `vikings-regeneration-fixture` as 10.0 → 23.3 → 30.0 → 40.0 HP at ticks 0/100/300/600, which is exactly 1 per 30 ticks. Deferred unique technologies: 2 → 1 (`atheism` alone). Implemented: 17 → 18 of 19. Tests: 2681 → 2692 passing — eight for the mechanic and the technology, three for the spec-table gate.

**Notes for later.** Atheism is the last deferred unique technology and needs three things this build lacks: Wonder and Relic victory timers to change, and a Spies/Treason cost to halve. It is honest where it is until then.

## §4's size ladder: the map becomes a per-match value (v0.3.66)

**Timestamp:** 2026-08-24, same session as v0.3.65.

**Action:** grew the standard map with the player count (§4's size ladder) and opened all eight of spec §4.2's seats. Seven rungs from 60x36 to 116x72, land per seat held near the two-player map's own 1080 tiles.

**What was believed and proved false.**

*That seating more players was a map-generation change.* It is a change to what "the map" IS. `MAP_WIDTH`/`MAP_HEIGHT` were read in 78 places across 17 files — the engine world's grid, the fog map's constructor, the projected frame's cell indices, the occupancy grid, the unit-transform clamps, the projectile aim clamp and its projection bounds check, the attack feed's validity check, the camera's pan bounds, the pointer's cell resolution, and the drag box. Every one of them is a silent failure on a bigger map: they answer 59 for any cell past the two-player right edge and never throw. Making `isInBounds` take a size turned the whole set into a typechecker worklist, which is the only reason this was one sitting rather than a hunt.

*That a cell index is just a key.* Replacing `toCellIndex`'s `y * MAP_WIDTH + x` with a fixed 1024 stride looked like a strict improvement — no map dependency at all. It broke the fog: `visibleCells` is decoded by the engine's projector using the frame's own `mapWidth`, so the encoding is a contract, not an implementation detail. Caught by `losTechs.test.ts` and `monastery.relic.test.ts` within one full-suite run; nothing about the change looked wrong at the site.

*That a fake world in a test is a stub of the world.* Four `as unknown as GameWorld` fakes across three test files had no `grid`, so the moment production code asked the world how big it was, `undefined.width` threw — after a clean typecheck, because the cast erases exactly that. The fakes now carry a grid.

**What the browser caught that the simulation could not.** The clamp defect is invisible to a simulation test, which passes cell coordinates in directly. The proof is a Playwright spec that opens `?players=8`, centres the camera at (90,50), enters placement mode and moves the mouse there: the preview must report cell (90,50). With the old clamp restored it reports **(59,50)** — a build 31 cells from the pointer, with nothing in the console.

**A defect that had nothing to do with the ladder.** The default map stands a house and a scout for player 2 near the middle, a landmark for the human to find in a 1v1. `createDefaultMap` added it unconditionally, so since v0.3.61 a three- or four-player match gave exactly one opponent a free building and a free unit. Now gated to two seats, and a test asserts every seat's opening is identical from three players up.

**What number moved and from what.** Seats: 4 → 8. Map: 60x36 → up to 116x72 (2160 → 8352 tiles). Land per seat across the ladder: 1030–1080, a 1.05 spread. An eight-player free-for-all at 12000 ticks: all eight owners alive, four in Castle Age, p8 at 26 villagers and 30 units. Tests: 2692 → 2717.

**Notes for later.** `createPrototypeScenario` is now called once in `createSimulationBridge` and handed to `createWorld`, because the fog map and the world have to be the same map — generating the seed twice would be two maps that merely look alike. Fixtures still name `MAP_WIDTH`/`MAP_HEIGHT` deliberately: those constants now mean "the two-player map", which is what every fixture is built on.

## Tribute, and the two technologies that price it (v0.3.67)

**Timestamp:** 2026-08-24, same session as v0.3.65–66.

**A python slip worth remembering:** an edit script used `x if False else None` mid-chain and crashed AFTER claiming partial work; the recovery was to re-read the file and re-apply cleanly. Scripted edits must be idempotent or atomic — this one was neither and cost a round trip.

## Resources, victory, speed: match options at three layers (v0.3.74)

**Timestamp:** 2026-08-24, same session as v0.3.65-73.

**Action:** shipped §4.1 resource presets, §4.3's Conquest Only victory option, and §4.5 game speed — each implemented at the layer its semantics demand.

**Three options, three layers.** RESOURCES are a boot-time seed: the preset fills every seat the scenario does not pin, and the save carries the resulting stockpiles, so the option is rightly ignored on load. VICTORY is match STATE: a conquest-only match must stay conquest-only through a save, so it became the first entry in `matchSettingsCodec` — a record-shaped singleton slot, absent in every older save (no migration), read by both countdown systems as one flag. SPEED is PRESENTATION: the view multiplies each frame's simulation delta before stepping, so nothing in the simulation, saves, or replays knows speed exists. Putting any of the three at the wrong layer (speed in the sim, victory in a closure, resources on the load path) would have broken determinism, save-fidelity, or load semantics respectively.

**The spec edit that fidelity forced.** §4.3 said "Default setup should be Conquest only" — but AoE2's own Standard victory mode INCLUDES Wonder and Relic victories, and the standing rule is that DE behaviour is authoritative. The line now names the AoE2 Standard set as the default and Conquest Only as the option, which also matches what this build has always done.

**Gates that fired, as designed.** The Tier-1 codec count (41 → 42), the slot-inventory pin, and the Map-vs-record shape check all went red on the new singleton — three pins that exist precisely to make "you added a persisted slot" a conscious act. The file-size gate caught `AoeVoxelGameView.ts` at 505 (no legacy entry): the speed field was paid for by compressing the class's own doc block.

**What number moved and from what.** §4.6 setup options configurable: 5 → 8 of 9 (population cap remains; its `deriveCap` seam is noted in bridgeConstants). Tier-1 codecs: 41 → 42. Tests: 2756 → 2759.
