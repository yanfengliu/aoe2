## A Windows CHECKOUT is not a Windows MACHINE, and that is the whole defect

**Timestamp:** 2026-09-06 00:15–01:05

**Action:** Diagnosed the `windows-latest` failure of CI run 34017480242 on `ca24709b`, added `.gitattributes` (`* text=auto eol=lf`, `*.png binary`), and added `tests/architecture/checkoutLineEndings.test.ts` as the gate for the class. `tests/scripts/ciStatus.test.ts` and `scripts/ci-status.mjs` were not touched.

**Result:** The runner reported `Test Files 1 failed | 480 passed | 1 skipped (482)` and `Tests 6 failed | 3472 passed | 3 skipped (3481)`, with all six failures reading only `SyntaxError: Invalid or unexpected token`. `gh run view 34017480242 --log-failed` puts every one of them at `runScript tests/scripts/ciStatus.test.ts:131:21` — the `await import()` — with no frame inside the imported module, so nothing in the reporting logic was failing; the module would not parse. The two cases that passed are the instrument controls, which read fixtures and never call `import()`.

**What actually differs between the local Windows machine and the Windows runner.** This is the reusable part. Git for Windows installs `core.autocrlf=true` in its SYSTEM config — `C:/Program Files/Git/etc/gitconfig` here — and the GitHub-hosted `windows-latest` image is that same install, so `actions/checkout` writes every tracked text file into the runner's working tree with CRLF while the index stays LF. A long-lived local clone does not look like that, because git converts on CHECKOUT and never afterwards: a file written by an editor or an agent keeps its LF, and only a file that was genuinely checked out holds CRLF. Measured here on the morning of the fix — index 1,766 LF, 68 binary, 2 symlinks; **working tree 932 LF, 810 CRLF, 24 mixed**. A patchwork. `scripts/ci-status.mjs` had been authored the previous day and was one of the 932, so the suite that is red on every clean Windows runner is green at home. A fresh `git clone` plus `checkout ca24709b`, done on this machine to reproduce the runner rather than to argue about it, writes that file with **475 carriage returns** against 0 in the tree beside it. Git says so itself the moment the file is touched: `warning: in the working copy of 'scripts/ci-status.mjs', LF will be replaced by CRLF the next time Git touches it`.

**Root cause, in a dependency.** `vite@6.4.3`, `dist/node/chunks/dep-Dm0c1Wj2.js:25674`: `const hashbangRE = /^#!.*\n/`. `ssrTransform` uses it to find the offset at which to inject its `__vite_ssr_import__` calls, precisely so that they land after a shebang instead of in front of one. A JavaScript `.` does not match `\r`, so under CRLF the regex misses, the offset falls back to 0, and the injected imports are written in front of `#!/usr/bin/env node`, leaving a bare `#` in the middle of the module. The defect needs both halves — a shebang and a CRLF checkout — which is why only one file of 482 was red. Node's own ESM loader strips a CRLF shebang correctly, so `npm run ci:status` itself never failed anywhere.

**Reasoning — why the fix is `.gitattributes` and not any of the three easier things.** Deleting the shebang from `scripts/ci-status.mjs` would have turned the leg green and left the class standing: 18 tracked scripts start with `#!`, and the next one a test imports fails identically. Skipping the file on Windows, or dropping the `import()` seam for a test-only entry point, would have kept the red away by removing the coverage that found it — and that seam is deliberate, so the script runs whole. Normalising line endings at the repository level fixes what every one of those works around, costs one file, and changes no test. It also causes no churn: the index was already uniformly LF, so `git status` is unchanged by adding it.

**Validation.** Reproduced before fixing: `scripts/ci-status.mjs` converted to CRLF in place gives `npx vitest run tests/scripts` -> `6 failed | 2 passed`, `SyntaxError: Invalid or unexpected token` at `tests/scripts/ciStatus.test.ts:131:21` — the runner's failure exactly, on the machine where it passes. Then narrowed by a control, which is what turns "CRLF is bad" into a named mechanism: the same CRLF file with only its `#!` line replaced by an ordinary comment gives `8 passed`. Corroboration nobody had to build: `scripts/content-lib.mjs` is CRLF in this working tree and is a STATIC import in four content tests that have been passing throughout — it has no shebang. The gate was proved red four ways, all recorded in `docs/learning/gate-proofs.md`: `.gitattributes` removed (the exact pre-fix state) 3 of 5 red; `eol=lf` flipped to `eol=crlf` 2 of 5, naming all 1,768 text files and all 18 scripts; `scripts/** binary` appended to smuggle them out of the guarantee, 1 of 5 red on the enumeration control rather than passing over an empty list; and a genuine CRLF blob written into the index with `git hash-object --no-filters`, 1 of 5. `.gitattributes` restored to an identical SHA-256 afterwards.

**What the proof does not reach.** The gate asserts what a fresh CHECKOUT produces and deliberately says nothing about the working tree on this disk — 810 files here are CRLF from checkouts that predate the fix, and a stale tree cannot reach CI, which always clones fresh. A check that went red for that would be deleted by the first person it annoyed. It says nothing about Vite's hashbang handling; a future toolchain that mishandles LF leaves it green. And a green local run does not prove the runner is fixed — only a Windows CI run does that.

**A methodological note worth keeping.** The engine's debug harness answers nothing here: `replay:inspect`, `diffBundles`/`forkAt` and the path-queue and occupancy probes all read simulation state out of a recorded bundle, and this question is about what bytes a checkout writes and how a bundler parses them. The instruments that did answer it are `gh run view --log-failed` for the real stack, `git ls-files --eol` for what git will do on checkout, and a throwaway `git clone` for what the runner sees. Naming that before probing is the rule; it is recorded here because "no engine tool applies" is itself the answer on a toolchain defect and it should not have to be rediscovered.

## The key was safe for three reasons and not one of them was in the file

**What was actually exposed.** The repository went public on 2026-09-05. `playtest-llm.yml` triggered on `pull_request: types: [opened, labeled, synchronize]`, checked out the merge ref, and ran `npm ci` and `npm run playtest:corpus-llm` — a contributor's own install scripts and package script — with `ANTHROPIC_API_KEY` in the step environment. Nothing about the file changed on the day the meaning of its trigger did: a private repository takes pull requests only from people who can already push.

**The finding worth carrying out of this, and it is not the fix.** The path never ran once: of 120 workflow runs, 119 are `schedule`, 1 is `push`, and `pull_request` appears zero times. THREE things were holding the key back and NOT ONE was visible in the file as a protection — GitHub's platform default for a fork's pull request, a human applying the `llm-playtest` label, and the job's `if:` requiring `vars.ANTHROPIC_KEY_AVAILABLE == 'true'`, where this repository has NO Actions variables at all, so that half was false for every event that ever reached it. **A condition that reads a name nobody has defined is not a gate.** Setting that variable to `true` — the obvious move for anyone who wants LLM playtests on pull requests — re-arms the whole path in one click from the web UI with no commit and no review. And the label was never a code gate: `synchronize` sat in the trigger list, so labelling approved the code once and the key-bearing job re-ran on every commit the contributor pushed afterwards. The shape to hunt for in the next audit is a protection whose evidence lives outside the file.

**Reasoning — why the trigger and not the `if:`.** Hardening the condition (requiring the label AND a maintainer association AND a variable) leaves the arrangement exactly as fragile as the one that just failed: it would still be a gate whose truth is decided outside the repository, and it would still be re-armable from a settings page. Deleting the trigger makes the file itself the evidence, which is also the only thing a test can read. The `if:` was then dead weight — it evaluated true for every schedule and dispatch run — so removing it changes the behaviour of neither remaining trigger. `ci.yml`'s new `permissions: contents: read` is a floor, not a fix: the repository's `default_workflow_permissions` is already `read`, so nothing was open; it is written down so that a later change to that default cannot quietly widen a workflow that runs a stranger's code.

**Validation.** The gate was proven red three ways on an otherwise untouched tree — `pull_request` re-added to `playtest-llm.yml`, `pull_request_target` added to the secret-free `playtest.yml`, and the secret detector stubbed out (the six in-file fixtures catch that one; without them the real-file checks pass vacuously) — and proven green once with a comment naming both banned things added to `ci.yml`. That last case is the point of parsing rather than scanning: `ci.yml` really does contain the text `secrets.` in a comment saying it uses none, and `playtest-llm.yml` really does contain `pull_request_target` in a comment forbidding it, so a raw-text checker paints a genuinely safe workflow red on day one and gets deleted by the next person it annoys.

**Left open, deliberately.** All three workflows fetch `civ-engine.tgz` from a rolling release tag whose asset is replaced on every engine push, so what CI installs is whatever was uploaded last. Fixing it properly needs `civ-engine` to publish a per-commit artifact, and AGENTS.md forbids modifying that repository. A sha256 pin on the mutable URL was considered and rejected: it reddens all three workflows on every engine publish, and this project has already lost two months to a red streak nobody was watching. **The one edit made during integration.** `js-yaml` was declared in `devDependencies` at `^4.3.1`, the version already resolved in `node_modules`. Until now it reached the gate only as a transitive dependency of eslint, so a lint upgrade could have removed it — the gate throws by name rather than skipping if that happens, which is the right failure, but the dependency should be declared. The lockfile needed one line for `npm ci` to stay in sync; rather than regenerating it, the pair was hand-edited and then checked against what npm itself writes (`npm install --package-lock-only` on a copy in a scratch directory produced the same single insertion, in the same alphabetical position), and `npm ci --dry-run` on that copy exits 0 with `add js-yaml 4.3.1`. ## The playtest bundle streams on every path, not just the cheap one

**Timestamp:** 2026-09-06 (integrated 07:30)

**Action:** Removed the four remaining whole-bundle strings that yesterday's `bundleIo` change missed, split `scripts/playtest-llm.mjs` by role, and replaced the gate's one-script call-site check with a scan of every `scripts/*.mjs` against four forbidden shapes. Files: `scripts/playtest-llm.mjs`, `scripts/playtest-llm-host.mjs` (new), `scripts/playtest-self-improve.mjs`, `tests/playtest/bundleIo.test.ts`, `tests/architecture/fileSizeBudget.test.ts`.

**Result:** The largest string anywhere on the bundle path is 4 MiB against V8's 536,870,888-character cap. `LEGACY_VIOLATIONS` in the file-size gate is down to one entry.

**Yesterday's entry claimed every call site was wired, and that was false.** The 2026-09-05 register entry ends its Fix paragraph with "Both directions are wired at every call site that touches a bundle", naming five scripts. Two more were not on that list, and between them they held four more ceilings. The entry has been corrected in place rather than quietly superseded: the false sentence is flagged where it stands and a dated `CORRECTED` block at the end of the entry says plainly what was missed and why.

**Three of the four were on the expensive path.** `scripts/playtest-llm.mjs` spends model calls for tens of minutes and then exports, so each of these threw only after the run had been paid for. (1) The page-side `window.__AOE2_PLAYTEST_BUNDLE_TEXT__ = JSON.stringify(bundle)` built the whole document inside the browser's heap. (2) `JSON.parse(parts.join(''))` rebuilt it in Node. (3) `writeFileSync(\`${args.out}.json\`, JSON.stringify(result.bundle))` — the same line, verbatim, that yesterday's fix had removed from `playtest.mjs`. The instructive part is (1) against (2): the 4 MiB chunking reads exactly like a fix for this problem, and is not one. It bounded the JSON-RPC transport between Node and the page, never the document, and the page had already built the full string before the first chunk was requested. A mitigation that looks like the fix is worse than no mitigation, because it stops anyone looking.

**The fourth explains how a review and a gate both missed it.** `scripts/playtest-self-improve.mjs` read the bundle as `const bundle = readJson(\`${prefix}.json\`)`. `readJson` is a generic three-line `JSON.parse(readFileSync(path, 'utf8'))` used four times in that file, and the other three artifacts are small. Nothing at the call site put the word "bundle" next to a `JSON.parse`, so a source-check gate looking for the shapes it had been shown could not see it — a wrapper is precisely the shape it had not been shown. This one is a READ ceiling as well: the bundle wrote correctly and was then unreadable, which is the worse failure of the two, because the artifact exists and the run looks recorded.

**What the page emits now.** `beginPageExport` stashes a cursor over the bundle's top-level entries; `nextPageExportPiece` hands back one structural piece at a time — a non-array top-level value stringified alone, or a batch of individually-stringified array elements. Node reassembles element by element rather than by spreading a batch, because a spread pushes the whole batch as one argument list and overflows the call stack on exactly the runs this exists for. The batch bound is checked before appending, so a batch can overshoot the 4 MiB target by at most one element.

**The gate no longer names a file.** `tests/playtest/bundleIo.test.ts` scans all 34 `scripts/*.mjs` against four patterns: the whole-bundle stringify, the whole-bundle `readFileSync` parse, the wrapper shape `const bundle = <anything but readBundleFile>(` added for the fourth ceiling, and the chunk rejoin. Each carries the sentence the reader needs. Proven red against this repository's own pre-fix `playtest-llm.mjs`, naming all three of its ceilings by line number. It carries a control case — five verbatim historical lines that must match, five correct shapes that must not — so a pattern that stopped matching anything fails there instead of passing everywhere, and a positive half asserts the two writers do call `writeBundleFile`.

**The 500-line cap was resolved by splitting, which is why an exemption could be deleted.** The Playwright host adapter moved to `scripts/playtest-llm-host.mjs` (195 lines), leaving `playtest-llm.mjs` at 425 against its old 531. Shuffling a line would have kept the exemption; splitting by role earned its deletion. One entry remains, `scripts/content-lib.mjs` at 633.

**Notes — two wrong sentences left in the source deliberately.** The gate's own header says "the three shapes below" while `FORBIDDEN` holds four; the code is right and the prose undercounts it by exactly the newest entry. And `scripts/playtest-llm-host.mjs` and `src/game/playtest/bundleIo.ts` both call 4 MiB "three orders of magnitude under" the cap when it is 128x, about 2.1 orders. Both are recorded in the register rather than edited, because this integrator writes documentation and does not touch source or test files that were inspected and accepted; the numbers in both files are correct and only the ratio is overstated. Whoever next touches either file should fix the sentence there.

## The browser suite runs on CI, on a config that could never have run there

**Timestamp:** 2026-09-06 (integrated 07:30)

**Action:** Added a `browser` job to `.github/workflows/ci.yml`, made `playwright.config.ts` pick its npm binary at run time, added `.gitattributes` to both workflows' push filters, and gave `tests/scripts/ciStatus.test.ts` two cases that bind the workflow fixtures to the workflows they copy.

**Result:** `npm run verify`'s sixth stage has a CI leg for the first time. Whether it passes is unknown — see the reasoning below, and the register entry is OPEN for that reason.

**The gap.** `npm run verify` is `content:validate && test && typecheck && test:browser && lint && build`. CI ran five of those six. Nothing installed a browser, so the 44 spec files under `tests/browser/` — 43 of which execute, since `_captureSelectionPanel.spec.ts` is excluded by `testIgnore` — were only ever evidence that one developer machine had run them. That is the same machine whose unrepresentative line endings let a defect ship the day before, which is what made the gap worth closing now rather than later.

**And adding the job alone would have proved nothing, which is the substance.** `playwright.config.ts` started its preview server with `` `npm.cmd run preview -- ...` ``. `npm.cmd` was hardcoded on 2026-04-11, when Windows was the only platform running the suite: `002b7280` ("Add browser gameplay test harness") introduced it as `npm.cmd run dev`, and `cf774cd4` the same day changed `dev` to `preview`. There is no `npm.cmd` on Linux. An ubuntu job on that config would have started no server, and all 43 specs would have died together on the 120-second `webServer` timeout with nothing in the output naming npm — the exact failure shape that gets read as "the browser suite is broken" rather than "the command is wrong", and then discounted. The config's new comment credits the hardcoding to `cf774cd4`, which is the `dev`→`preview` commit; the date holds but the hash is wrong for that claim.

**The job.** `ubuntu-latest`, no `needs:` so it runs beside `gates` instead of behind it, 45-minute timeout, Playwright's browser restored from `actions/cache` keyed on the installed Playwright version — full `playwright install --with-deps chromium` on a miss, `install-deps chromium` on a hit, because the apt libraries live outside the cached directory and a cache hit would otherwise leave them missing. `test-results/` is uploaded on failure for seven days, which is the only way a remote browser failure is diagnosable at all.

**Two omissions, both argued.** No Windows leg: it costs 30 to 40 extra billable minutes at double rate, and Windows is the one platform this suite is not unproven on, because it is the platform that has been running it. And `.nvmrc` was deliberately kept out of both push filters, because both workflows pin their Node version as a literal — `'20'` in `ci.yml`, `'22'` in `playtest.yml` — and neither reads that file, so a push triggered by `.nvmrc` would run on a version the file does not name and report green. For whoever wires `node-version-file:` later: `.nvmrc` contains **24**, which matches neither pin, so that wiring is a Node 20 → 24 move for CI and a change in its own right rather than a tidy-up. `.gitattributes` WAS added to both filters, because the commit that fixed the Windows line-ending defect could not trigger its own proof.

**The fixtures were copies nobody compared.** `tests/scripts/fixtures/workflow--*.yml` were captured at `ca24709b`; `52546080` then edited two of the originals and the fixtures sat a day behind with nothing red. Each fixture's parsed push trigger must now equal the real workflow's, with the controls asserted first — the real file parsed at all, and has a readable `name:` — so a match cannot mean "neither parsed"; plus a completeness case requiring a fixture for every `.yml` in the directory. Bound, stated in the test: parsed push trigger ONLY. A fixture may differ from its workflow in a comment, a step or a `permissions:` block and this stays green.

**Notes.** The register entry is marked OPEN, and the heading says so, because the `browser` job has never run anywhere. Everything above is a claim about what the first push will do, not an observation, and an unrun CI job is exactly the thing this entry exists because nobody had. An OPEN entry does not count against the twelve-closed cap, so marking it honestly costs nothing.
