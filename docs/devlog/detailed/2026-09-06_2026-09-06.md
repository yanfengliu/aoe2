## A Windows CHECKOUT is not a Windows MACHINE, and that is the whole defect

**Timestamp:** 2026-09-06 00:15–01:05

**Action:** Diagnosed the `windows-latest` failure of CI run 34017480242 on `ca24709b`, added `.gitattributes` (`* text=auto eol=lf`, `*.png binary`), and added `tests/architecture/checkoutLineEndings.test.ts` as the gate for the class. `tests/scripts/ciStatus.test.ts` and `scripts/ci-status.mjs` were not touched.

**Result:** The runner reported `Test Files 1 failed | 480 passed | 1 skipped (482)` and `Tests 6 failed | 3472 passed | 3 skipped (3481)`, with all six failures reading only `SyntaxError: Invalid or unexpected token`. `gh run view 34017480242 --log-failed` puts every one of them at `runScript tests/scripts/ciStatus.test.ts:131:21` — the `await import()` — with no frame inside the imported module, so nothing in the reporting logic was failing; the module would not parse. The two cases that passed are the instrument controls, which read fixtures and never call `import()`.

**What actually differs between the local Windows machine and the Windows runner.** This is the reusable part. Git for Windows installs `core.autocrlf=true` in its SYSTEM config — `C:/Program Files/Git/etc/gitconfig` here — and the GitHub-hosted `windows-latest` image is that same install, so `actions/checkout` writes every tracked text file into the runner's working tree with CRLF while the index stays LF. A long-lived local clone does not look like that, because git converts on CHECKOUT and never afterwards: a file written by an editor or an agent keeps its LF, and only a file that was genuinely checked out holds CRLF. Measured here on the morning of the fix — index 1,766 LF, 68 binary, 2 symlinks; **working tree 932 LF, 810 CRLF, 24 mixed**. A patchwork. `scripts/ci-status.mjs` had been authored the previous day and was one of the 932, so the suite that is red on every clean Windows runner is green at home. A fresh `git clone` plus `checkout ca24709b`, done on this machine to reproduce the runner rather than to argue about it, writes that file with **475 carriage returns** against 0 in the tree beside it. Git says so itself the moment the file is touched: `warning: in the working copy of 'scripts/ci-status.mjs', LF will be replaced by CRLF the next time Git touches it`.

**Root cause, in a dependency.** `vite@6.4.3`, `dist/node/chunks/dep-Dm0c1Wj2.js:25674`: `const hashbangRE = /^#!.*\n/`. `ssrTransform` uses it to find the offset at which to inject its `__vite_ssr_import__` calls, precisely so that they land after a shebang instead of in front of one. A JavaScript `.` does not match `\r`, so under CRLF the regex misses, the offset falls back to 0, and the injected imports are written in front of `#!/usr/bin/env node`, leaving a bare `#` in the middle of the module. The defect needs both halves — a shebang and a CRLF checkout — which is why only one file of 482 was red. Node's own ESM loader strips a CRLF shebang correctly, so `npm run ci:status` itself never failed anywhere.

**Reasoning — why the fix is `.gitattributes` and not any of the three easier things.** Deleting the shebang from `scripts/ci-status.mjs` would have turned the leg green and left the class standing: 18 tracked scripts start with `#!`, and the next one a test imports fails identically. Skipping the file on Windows, or dropping the `import()` seam for a test-only entry point, would have kept the red away by removing the coverage that found it — and that seam is deliberate, so the script runs whole. Normalising line endings at the repository level fixes what every one of those works around, costs one file, and changes no test. It also causes no churn: the index was already uniformly LF, so `git status` is unchanged by adding it.

**Validation.** Reproduced before fixing: `scripts/ci-status.mjs` converted to CRLF in place gives `npx vitest run tests/scripts` -> `6 failed | 2 passed`, `SyntaxError: Invalid or unexpected token` at `tests/scripts/ciStatus.test.ts:131:21` — the runner's failure exactly, on the machine where it passes. Then narrowed by a control, which is what turns "CRLF is bad" into a named mechanism: the same CRLF file with only its `#!` line replaced by an ordinary comment gives `8 passed`. Corroboration nobody had to build: `scripts/content-lib.mjs` is CRLF in this working tree and is a STATIC import in four content tests that have been passing throughout — it has no shebang. The gate was proved red four ways, all recorded in `docs/learning/gate-proofs.md`: `.gitattributes` removed (the exact pre-fix state) 3 of 5 red; `eol=lf` flipped to `eol=crlf` 2 of 5, naming all 1,768 text files and all 18 scripts; `scripts/** binary` appended to smuggle them out of the guarantee, 1 of 5 red on the enumeration control rather than passing over an empty list; and a genuine CRLF blob written into the index with `git hash-object --no-filters`, 1 of 5. `.gitattributes` restored to an identical SHA-256 afterwards.

**What the proof does not reach.** The gate asserts what a fresh CHECKOUT produces and deliberately says nothing about the working tree on this disk — 810 files here are CRLF from checkouts that predate the fix, and a stale tree cannot reach CI, which always clones fresh. A check that went red for that would be deleted by the first person it annoyed. It says nothing about Vite's hashbang handling; a future toolchain that mishandles LF leaves it green. And a green local run does not prove the runner is fixed — only a Windows CI run does that.

**A methodological note worth keeping.** The engine's debug harness answers nothing here: `replay:inspect`, `diffBundles`/`forkAt` and the path-queue and occupancy probes all read simulation state out of a recorded bundle, and this question is about what bytes a checkout writes and how a bundler parses them. The instruments that did answer it are `gh run view --log-failed` for the real stack, `git ls-files --eol` for what git will do on checkout, and a throwaway `git clone` for what the runner sees. Naming that before probing is the rule; it is recorded here because "no engine tool applies" is itself the answer on a toolchain defect and it should not have to be rediscovered.

## The key was safe for three reasons and not one of them was in the file

**Timestamp:** 2026-09-06 01:15–02:10

**Result:** A workflow that references a secret can no longer carry any `pull_request*` trigger, and no workflow at all may carry `pull_request_target`, with a test that fails the build if either changes. `playtest-llm.yml` now triggers only on `schedule` and `workflow_dispatch`, both of which run code that is already on a branch of this repository.

**What was actually exposed.** The repository went public on 2026-09-05. `playtest-llm.yml` triggered on `pull_request: types: [opened, labeled, synchronize]`, checked out the merge ref, and ran `npm ci` and `npm run playtest:corpus-llm` — a contributor's own install scripts and package script — with `ANTHROPIC_API_KEY` in the step environment. Nothing about the file changed on the day the meaning of its trigger did: a private repository takes pull requests only from people who can already push.

**The finding worth carrying out of this, and it is not the fix.** The path never ran once: of 120 workflow runs, 119 are `schedule`, 1 is `push`, and `pull_request` appears zero times. THREE things were holding the key back and NOT ONE was visible in the file as a protection — GitHub's platform default for a fork's pull request, a human applying the `llm-playtest` label, and the job's `if:` requiring `vars.ANTHROPIC_KEY_AVAILABLE == 'true'`, where this repository has NO Actions variables at all, so that half was false for every event that ever reached it. **A condition that reads a name nobody has defined is not a gate.** Setting that variable to `true` — the obvious move for anyone who wants LLM playtests on pull requests — re-arms the whole path in one click from the web UI with no commit and no review. And the label was never a code gate: `synchronize` sat in the trigger list, so labelling approved the code once and the key-bearing job re-ran on every commit the contributor pushed afterwards. The shape to hunt for in the next audit is a protection whose evidence lives outside the file.

**Reasoning — why the trigger and not the `if:`.** Hardening the condition (requiring the label AND a maintainer association AND a variable) leaves the arrangement exactly as fragile as the one that just failed: it would still be a gate whose truth is decided outside the repository, and it would still be re-armable from a settings page. Deleting the trigger makes the file itself the evidence, which is also the only thing a test can read. The `if:` was then dead weight — it evaluated true for every schedule and dispatch run — so removing it changes the behaviour of neither remaining trigger. `ci.yml`'s new `permissions: contents: read` is a floor, not a fix: the repository's `default_workflow_permissions` is already `read`, so nothing was open; it is written down so that a later change to that default cannot quietly widen a workflow that runs a stranger's code.

**Validation.** The gate was proven red three ways on an otherwise untouched tree — `pull_request` re-added to `playtest-llm.yml`, `pull_request_target` added to the secret-free `playtest.yml`, and the secret detector stubbed out (the six in-file fixtures catch that one; without them the real-file checks pass vacuously) — and proven green once with a comment naming both banned things added to `ci.yml`. That last case is the point of parsing rather than scanning: `ci.yml` really does contain the text `secrets.` in a comment saying it uses none, and `playtest-llm.yml` really does contain `pull_request_target` in a comment forbidding it, so a raw-text checker paints a genuinely safe workflow red on day one and gets deleted by the next person it annoys.

**Left open, deliberately.** All three workflows fetch `civ-engine.tgz` from a rolling release tag whose asset is replaced on every engine push, so what CI installs is whatever was uploaded last. Fixing it properly needs `civ-engine` to publish a per-commit artifact, and AGENTS.md forbids modifying that repository. **The one edit made during integration.** `js-yaml` was declared in `devDependencies` at `^4.3.1`, the version already resolved in `node_modules`. Until now it reached the gate only as a transitive dependency of eslint, so a lint upgrade could have removed it — the gate throws by name rather than skipping if that happens, which is the right failure, but the dependency should be declared. ## A simulation step that refuses to run now says why

**Timestamp:** 2026-09-06 (integrated 09:40)

**Action:** Added `src/game/simulation/bridge/stepReport.ts` and the `StepRefusal` / `StepReport` types in `simulationBridgeTypes.ts`; `createSimulationBridge.step()` and `makeReplayBridge.step()` now return a report instead of `void`; `browserTestApi.advanceTicks` returns the run tally it summed from those reports. Gate: `tests/app/stepRefusalIsReported.test.ts`.

**Result:** `step()` returns `{ ticks, refusedBecause }`, where `refusedBecause` is one of `'paused'`, `'halted'`, `'match-over'`, `'replay'`, or `null`. `advanceTicks` returns `stepsRequested` / `stepsRun` / `ticksAdvanced` / `refusedBecause` and warns once per reason for callers that discard the value. Confirmed against the live defect at v0.3.213: menu-paused, `advanceTicks(3000, 100)` delivered 0 ticks, threw nothing, and left `matchState.outcome === 'running'` with `engineHalted === null`.

**The cost was not the missing ticks; it was two sessions reasoning from a false model.** A play session, reading nothing but a tick delta of zero, wrote down a hazard about the test seam in two forms — that `advanceTicks(n)` throws the engine's re-entrancy `EngineError`, and that it "silently under-advances when the simulation is not paused" — and both were repeated in worker assignments as established fact. A later session measured them at `d65f84aa` and refuted both: running and unpaused, 3,000 requested gave 3,000 advanced with no throw; paused through the test API, the same; and `advanceTicks` is a plain loop called from outside any tick, so it cannot reach the engine's re-entrancy guard at all. A tick delta of zero is compatible with every explanation, so the sessions that had one picked wrong ones. That is the whole argument for the return value.

**A production caller was already paying for the same silence.** `src/game/playtest/llmRunner.ts` maps `advanced <= 0` to `stopReason = 'engineHalt'` under a comment that asserts the inference is safe: "Reached only when the match is still 'running' ... so no progress here IS a genuine halt." A world paused by anything other than the test API is still `running` and still advances nothing, so that branch would report a pause as an engine crash. It is latent only because the LLM host unpauses around each call — a property of the host, not of the runner, and nothing in the runner knows it.

**Reasoning — the two designs that were rejected.** THROWING loses: the playtest runner polls a finishing match, and a resolved match is an ordinary end there rather than an exception, so the common path would become an exception path. Fixing only the TEST SEAM — having `advanceTicks` diff tick counters and report the shortfall — also loses, and this is the sharper one: it would have made the reproduction green while leaving `step()` exactly as silent for the frame loop and for `runPlaytest`, and the production silence was the defect. The report is separated into `ticks` and `refusedBecause` for the same reason: a `deltaMs` shorter than one tick (100 ms at TPS 10) legitimately runs zero ticks, so a short step is not a fault and `ticks === 0` is not the fault signal.

**Cost, since this path is taken every frame.** A halted, paused or finished match refuses on EVERY frame for the rest of the session — a steady state, not an anomaly — so the refusal values are frozen module constants, one object each for the life of the process: no `Error`, no stack capture, no string building. Only a step that actually ran ticks allocates, and it allocates one small literal.

**Validation.** `tests/app/stepRefusalIsReported.test.ts`, 13 cases, exercising all four reasons on the REAL objects (`paused`, `halted`, `match-over` on a real `createSimulationBridge`; `replay` on a real `makeReplayBridge`), asserting the four are DISTINCT values — a signal that cannot tell them apart is the same defect in a new costume — with a control in the opposite direction (a running unpaused bridge reports no refusal, so the gate cannot pass by refusing everything) and the seam driven end to end through the real `installBrowserTestApi`. ## Two browser specs measured the host instead of the game

**Timestamp:** 2026-09-06 (integrated 09:40)

**Action:** Rewrote the clock step of `tests/browser/play-opening.spec.ts` to poll for the world to advance; rewrote the stack-point search in `tests/browser/game-selection-click.spec.ts` to aim at the middle of the qualifying region and measure its margin; reordered the spawns in `src/game/simulation/fixtures/selection.ts` so the militia and the sheep share a draw slot.

Both failures were tests measuring their host rather than the game. Recorded as ONE register entry, not two, because that is what they are: the first run of a suite off the machine that had always run it.

**The first failure was an assertion about how fast the host is.** The step read the tick, waited for the HUD clock to leave `00:00`, and read the tick again. The clock had already left `00:00` before that wait started, so it resolved on its first poll — 14 ms — and waited for nothing at all. What remained was an assertion that at least one tick fits in the 25 ms between two round trips. On `ubuntu-latest`, two cores and software rendering, exactly zero fitted: it read 20 → 20. The new form polls for the tick to pass the one it read, with a message naming what it was waiting for. Nothing else moves the tick, so it cannot pass on a dead simulation, and it cannot pass by accident on a fast one.

**The falsifiability proof is the durable half of that.** The first attempt to prove the new form red PASSED when it should have failed: the mutation froze the world at tick 11 rather than at zero, so the poll succeeded for the wrong reason — it was racing the very condition it was meant to disprove. A mutation that races what it is trying to disprove proves nothing, and its green is indistinguishable from the green of a working gate. Only a mutation that freezes the world before the first tick actually falsifies this one.

**The second failure had 0.30 screen pixels of room, and the cause was the fixture.** The spec searches `tile-selection-cycle-fixture` for a point where a militia, a house and a sheep all answer one click, then cycles the selection there. Of the **625** world offsets the old scan probed, exactly **four** qualified, in a ribbon one sample wide — and raster order reaches a region at its TIP, so the point it took had the least room of any point in it. The presented hit polygons are evaluated at the renderer's animation clock, so a host that reaches a different tick before the scan freezes the world reads the bodies at a different phase and the ribbon's edge moves by about half a pixel. Underneath that: co-located bodies are drawn at their cell plus one of four slots (`UNIT_CELL_SLOT_OFFSETS[entityId % 4]`, and a sheep carries a unit transform so it takes one too), the slots are half a cell apart, and the militia's body is 0.25 cells across against the sheep's 0.231 — a **0.019-cell** gap. Two bodies on this lattice are either exactly coincident or they never touch, and these two never touched; the only qualifying points were where the two rendered voxel silhouettes happened to graze. Ids are handed out one per spawn in list order, so the two share a slot exactly when their list positions differ by a multiple of four. The fix is a spawn REORDER — militia first, sheep fifth — so they coincide as the fixture always intended, with the constraint written into the fixture beside the list.

**And the scan now measures what it found.** It walks up the militia's body, takes the middle of the longest run that cycles, grows an eight-point compass around that middle until one direction stops cycling, and fails BY NAME on the fixture below two screen pixels. Margin went **0.30 px to 6.00 px** at default zoom, held across five animation phases. No existing assertion was changed or weakened; one was added. The margin is in iso pixels before the camera zoom (≥ 1), so the real on-screen margin is at least the number asserted.

**Two findings that outlive this fix.** (1) Fixture spawns and live play use DIFFERENT lattices: half-cell slots for fixture spawns, quarter-cell through the occupancy allocator in play. A fixture pile is therefore spread twice as far as a real one and its bodies never touch. That is the real root cause and it needs its own task; the reorder works around it for one fixture. (2) There is NO player-facing defect. Three units genuinely on one cell were ordered correctly in the running game, are separately clickable, and repeated clicks cycle whichever bodies cover the point — the spec's own contract, and more than the real game does.

**The OPEN entry about the browser job is amended, not closed.** Its first run being RED on a real defect is exactly what the job existed to make possible, and the platform claims in it are now observations rather than predictions: `npm` resolves on Linux, the preview comes up, the specs execute. It stays OPEN because what it is waiting for is a GREEN run, and a red run is not one.
