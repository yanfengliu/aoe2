## Select the whole army, order it across the map, and nothing happens at all (v0.3.219)

**Timestamp:** 2026-09-06 22:10–23:55

**Result:** A walk order that cannot be carried out now walks the unit as far toward the ordered cell as it can get and puts a sentence on the rejection queue the HUD already drains into a toast. On the gate fixture the sealed unit used to go from (2,2) to (2,2); it now moves. Reachable orders are unchanged — same destination, same path length, verified per call rather than argued.

**The reported symptom.** A 93-minute Black Forest match at Castle Age, 58 units all reporting idle. `issueAttackMoveCommand` returned `true` and over 9,200 ticks the army's centre moved from (14.0, 10.0) to (15.0, 9.7) and then never changed again. No movement, no message, no console error. Short orders worked; long ones did nothing. Nobody reported it — the standing loop found it by playing, which is the entry point the local rules name.

**The finding that nearly ended the investigation, and why it was not the answer.** An independent 4-connected flood — over terrain plus building and resource footprints, deliberately never over the pathfinder under test — established that on `black-forest` the map SEALS ITSELF with the buildings a normal match puts up: the human's own component falls from 368 cells to 205 by tick 20,000 and enemy units reachable from it from 4/4 to 0/26. That is a real and separate defect, and it would have been easy to stop there and call the movement correct. It is filed OPEN in its own register entry rather than inside the fixed one, because an OPEN entry never rolls over and the finding is too important to let the rollover carry away.

**The search bug hiding behind it.** The fallback for "the ordered cell cannot be reached" scanned `getNearestMoveCandidates(target)` — every cell within `max(mapWidth, mapHeight)` manhattan cells of the target — and ran a full A* per candidate. On a 60x36 map that radius is 60 and the greatest cell-to-cell distance is 94, so a unit sealed far from the ordered cell had NO candidate it could reach: the resolver returned null and `playerCommandsSystem`'s `if (!movePlan) clearUnitCommand(id)` dropped the order in silence. A larger radius fixes the instance and not the class, because the scan's cost is quadratic in the radius and is paid entirely in failing A* searches. Flooding out of the unit's own cell has no radius to run out of.

**Reasoning — the compatibility constraint drove the design more than the cost did.** The flood picks the reachable cell with the smallest `(manhattan-to-target, y, x)`, which is deliberately the ring scan's own ordering: rings by manhattan distance, row-major within a ring, first reachable wins. That is what makes this a fix rather than a behaviour change. It was verified by MEASUREMENT, both arms in one process against one bridge so the tree could not move between them: identical destination and identical path length in every case, and 0.89 ms → 0.02 ms on a reachable order, 162.91 ms → 1.09 ms on one sealed across a wall. The old cost was one unit for one replan; 58 units in that state would have frozen the game.

**The second half is the one a player feels.** `clearUnitCommand` on a null plan was the whole of the old behaviour — an order accepted and then dropped, with no way for the player to learn anything was wrong. This is the same class the placement validator and the command-availability work closed, one layer out. The barrier is named from the STUCK unit's frontier and not the target's: seeded at the target, the frontier picked out the player's own town centre on the far side of the map and reported that as the wall.

**Falsifiability.** Proven red on the unfixed tree with the two control cases green, then proven again by two TARGETED mutations that bind each half to its own mechanism — silencing only the message reddens exactly the two message cases, restoring only the give-up fallback reddens exactly the movement case with the same `(2,2) to (2,2)` text. A single mutation that reddened everything would not have distinguished the two.

**Notes.** Bound, stated in the gate's own header: one map size, one sealed shape (a 6x6 pocket inside a ring of trees), land units only, move and attack-move only. A unit standing on a cell that became blocked UNDERNEATH it still cannot move at all — the flood returns null, the command is still cleared, and only the toast covers it. That is the spawn-egress class and it is untouched.

## A building's health bar read FULL while it was still a foundation (v0.3.220)

**Timestamp:** 2026-09-06 22:10–23:55

**Action:** Added `src/game/simulation/bridge/constructionHealth.ts` (63 LOC) and rewired `systems/builderWorkStep.ts` to move health from it; `entityCreateOps.ts` now reads the 10% foundation floor out of `constructionStartHp` instead of repeating `Math.max(1, Math.floor(fullHp * 0.1))`. Added `tests/simulation/constructionHealthMeansComplete.test.ts` (10 cases).

**Result:** While a site is unfinished its health is strictly below full, and it tracks real build progress within 2%. A full bar now means a finished building and can mean nothing else.

**Symptom as reported.** A Mill reading `currentHp: 1000, maxHp: 1000` — a full bar, and 1000 is exactly the Mill's `hit_points` in `structures.csv` — while still drawn as a foundation, still refusing to work, and still counting 0 toward the Feudal advance, for more than 11,600 ticks. Found by the standing loop playing; the owner reported none of it.

**Root cause, arithmetic rather than anecdote.** `builderWorkStep` credited progress on the crew curve and health on a flat rate, in the same block, from the same tick. `builderProgressShare` is `1` for the first builder credited on a site that tick and `1/3` for each of the rest, telescoping to `(n + 2) / 3` for a crew of n. Health added `(maxHp − startHp) / totalBuildTicks` once **per builder**, so `n` per tick. The ratio is `3n / (n + 2)`: 1.8x at three builders, 2.7x at eighteen, and health therefore saturated at `(n + 2) / 3n` of the build — 56% at three, 37% at eighteen, 100% only for the single builder that never showed the defect. After that `Math.min(maxHp, …)` clamped it and the bar said nothing for the rest of the job.

**Reasoning — what this did and did not cause, because the difference matters.** It stalled nothing. Completion is decided by progress alone (`playerCommandsSystem.ts`, `if (advanced.buildProgressTicks >= advanced.totalBuildTicks)`), so a site with a crew on it still finished on the curve. What it destroyed was the player's only reading: a site being built, a site nobody was working any more, and a finished building became three states with one appearance, while `countCompletedAgePrerequisites` counts `isComplete` and told the player they owned none of the buildings they were looking at. The reported match is the middle state — a foundation everyone had walked away from — and the gate's third case is exactly it.

**The design point worth keeping.** Health is derived TWICE and both rules are needed. The CEILING is `constructionEarnedHp(progress)`, which makes health a pure function of progress so the two can never disagree. The STEP is the same tick's `progressDelta` in hit points, and it exists for the one case the ceiling alone gets wrong: a foundation an enemy has chipped sits below the curve, and under the ceiling alone the next builder tick would snap it back to full-for-its-progress — a damaged site healing free the instant a villager touched it. In the undamaged case the two coincide exactly, which is why the composition is unconditional rather than branching on damage state this module does not have.

**Notes.** Bound, in the gate's own header: one flat fixture, owner 1, AI disabled, Dark Age, Britons, no build-rate technology or civ multiplier; four building types over two footprints; crew sizes 1 and 5, so the ratio is measured at its SMALLEST — eighteen builders, the size the reported match used, is not reachable on this fixture. Health is read from `getRenderState()`, so no pixel is proved drawn; the invariant is sampled once per tick; damage during construction, save/load and an age that raises `maxHp` mid-build are all uncovered. Crew 1 is the CONTROL: health and progress advanced in lockstep for a single builder, so a crew-1 arm going red would have meant the sweep was measuring the fixture rather than the crew. The test recomputes the 10% floor from its own literal instead of importing `constructionStartHp`, so it is not the code agreeing with itself.

**Two corrections made at integration, both in the lane's own text.** Its code comment said a crew of three saw full health on a "57%-built" foundation; `(n + 2) / 3n` at n = 3 is 5/9, so it is 56%, and the comment now states the formula rather than a pair of numbers. A test comment read "for an hance and a half".

## A camera test that was really a frame-rate test, and a duration budget the measurement refused

**Timestamp:** 2026-09-06 22:10–23:55

**Action:** Fixed six browser specs that asserted on ground covered inside a fixed `waitForTimeout` and three that could not tell "held still" from "never rendered"; added `waitForRenderedFrames` to `tests/browser/helpers/gameTestHelpers/camera.ts` and `tests/browser/helpers/durationBudgetReporter.ts`, wired into `playwright.config.ts` as a second reporter beside `line`. Deleted the duration-budget rule from `docs/learning/lessons.md` and wrote its substance into `docs/policies/local-rules.md`. No version bump and no changelog line: nothing a player can see changed.

**Result:** The specs measure the game rather than the host. `npm run test:browser` gains four lines of output and no new way to go red.

**Root cause is arithmetic, not flakiness.** `game-hud-and-camera-camera.spec.ts:5` held D for 250 ms and required `scrollX` to grow by more than 40; CI read −333.33 → −298.33, exactly 35. Keyboard pan is `deltaMs / 1000 × 420 / zoom` (`KEYBOARD_SCROLL_SPEED_PX_PER_SECOND` = 420) and `AoeVoxelGameView.frame` clamps `cameraDeltaMs` to `MAX_CAMERA_FRAME_DELTA_MS` = 100, so one rendered frame contributes at most `100/1000 × 420 / 1.2` = 35.00 px at boot zoom — the CI number to the last digit, one clamped frame. Requiring more than 40 required TWO frames inside 250 ms. It was an eight-frames-per-second requirement written as a camera assertion. The fix holds the key WHILE the poll runs and releases it in a `finally`.

**The rejected instrument is the more useful half.** The first control tried was CPU throttling at 20x, and it would have "proved the defect absent": throttling also delays CDP input handling, so the keyup lands late, the key stays down far longer than the spec intends, and the OLD form covered 175 px and PASSED. The control that actually reproduced CI was frame starvation — `requestAnimationFrame` replaced with a 300 ms `setTimeout` shim, which starves rendering without touching input timing. An instrument that changes two variables answers about neither.

**Reasoning — the queued lesson asked for a gate, and the measurement refused it.** The per-spec duration budget was built, wired in and proven to fire. Then two full-suite runs on the same machine and the same bundle, nothing else changed, gave 95/59/46/40/39 and 48/47/44/41/38 percent of budget for the five specs closest to their timeouts; one test went 28.4 s → 14.3 s and another moved the OTHER way. It is not one load factor scaling everything — it is per-test and it points in both directions, so a threshold above the worst observation lands past 100% (the timeout that already exists) and anything below it goes red because somebody was compiling. The budget therefore ships as a REPORT, with `BROWSER_DURATION_BUDGET=0.8` to opt into failing.

**What that did to the lessons queue, which is the part with a rule behind it.** The constitution says an entry that can name no workable gate is not a lesson, and repo-only knowledge goes to the local rules. The queue's only entry named this gate, so the entry is deleted and the rule — with its numbers, its instrument, and the CPU-throttling trap — is now a local rule. `docs/learning/gate-proofs.md` is deliberately NOT touched: no gate landed, and recording a refutation in the proofs file would misrepresent it as one. `lessons.md` is empty again and says why.

**Notes.** Bound: two runs on ONE machine, so the CI runner's distribution is unmeasured and may be tighter or looser; the report names the top five only. `patrol-interaction.spec.ts:49` cannot be fixed inside the 30 s timeout without raising it and was deliberately LEFT rather than quietly given more room; `game-combat-and-meta-meta.spec.ts:5` sits at 95% of its budget and was deliberately not chunked, because a coarser break check would change what it asserts. Neither open thread in `docs/threads/current/` was advanced by this batch, so neither gained a status line; both are well inside the 30-day staleness limit.

## Worktrees are made and removed by one script, because removing one can delete a sibling repo

**Timestamp:** 2026-09-22 (the infrastructure lane's work), integrated 2026-09-23

**Action:** Added `scripts/controlWorktree.mjs` — `create <name> [<base>]`, `remove <name-or-path>`, `delete-branch <branch>`, with `--dry-run` and `--discard-changes` — and `tests/scripts/controlWorktree.test.ts`, 11 cases on sandboxed trees. Replaced the local rule "A/B control builds: never `ln -s` node_modules into a worktree" with "Worktrees are the default, and only `scripts/controlWorktree.mjs` makes or removes one", and amended three sections the synced canon now contradicts ("Take a lane", "Several workers in one checkout", "Half one"). Amended the archived 2026-09-05 register entry, whose last sentence said the script "is not written yet". No version bump and no changelog line: tooling only.

**What was believed and proved false.** That `--force` was the hazard. Measured in a temp directory with git 2.42.0.windows.2: a PLAIN `git worktree remove` of a CLEAN worktree whose `node_modules` is a junction exits 0 and deletes the canary behind the junction; with the junction removed first, the canary survives. git's delete of the admin directory `.git/worktrees/<id>` follows a junction the same way. Git for Windows' lstat calls a junction a directory, so any recursive delete by git walks into one. The script therefore unlinks every link in the tree on its own with `rmdirSync`/`unlinkSync`, which cannot recurse, scans again, refuses if a link is left or if the admin directory holds one, and only then lets git delete.

**What the brief got wrong, found by the worker.** "The tips are in main, so removing them loses no work": two A/B arms, `aoe2-177-after` and `aoe2-177-before`, held STAGED content (21 and 4 files), and 10 and 1 of those blobs appear nowhere in `main`'s history. They were saved first as `git diff --cached --binary --full-index` patches under the ignored `tmp/probes/worktree-staged/`, proven to rebuild each index byte-for-byte, and only then removed with `--discard-changes`. `git branch -d` would have refused `shadow-silhouette`, because it judges a branch that has an upstream against the upstream rather than `main`; the script deletes a branch with `git update-ref -d` after `git merge-base --is-ancestor` against `main`. And `.claude/worktrees/voxel` is itself a junction to `../voxel` (dated 2026-07-14), so a recursive delete of `.claude/worktrees/` would walk into the voxel repo.

**Mutations, on the final bytes (script `882b9ac9`).** Cut the unlink step: the fresh scan refuses, git never runs, both canaries survive. Cut the unlink step AND the fresh scan: git deletes both canaries through the junctions, and the script's own after-check says STOP. Cut the admin-directory check: git deletes the canary behind a junction planted in `.git/worktrees/<id>`. The first two are also in the suite as mutants built by exact-once text cuts; the second runs only where a load-time measurement finds git deleting through a junction, so on Linux it is skipped, not passed.

**The cleanup it did.** Thirteen stale worktrees removed one at a time with the script, with `../civ-engine`, `../voxel` and this checkout's `node_modules` re-counted unchanged after each; nine branches went with them, and `deposit-walk-field` went by `delete-branch`. The four scratchpad worktrees were skeletons — every file deleted and every directory kept, apparently by a temp cleaner — which is one reason worktrees now live at `../aoe2-worktrees/<name>`.

**Notes.** Bound: Linux and Node 20, which both CI legs use for `npm test`, were reasoned, not run, before this integration; real symlinks cannot be made on this machine (EPERM), so only junctions are exercised on Windows; `create` had run only in sandboxes; the harness's own worktree deletes (`isolation: "worktree"`, `ExitWorktree`) were not measured, which is why the rule forbids them rather than trusting them; and a junction made by another process between the last scan and git's delete defeats the script, as its header says.

## The capture script draws on the GPU on request (no version bump)

**Timestamp:** 2026-09-24 (the de-terrain lane, worktree `de-terrain` from `ced7f6da`; the first milestone of step 2 of `docs/threads/current/de-look/PLAN.md`)

**Action:** `scripts/captureMapScreenshot.mjs` takes `RASTERISER=swiftshader|gpu`. `swiftshader`, the CPU rasteriser CI's browser suite draws with, stays the default, so every earlier capture and every command that does not name it is unchanged. `gpu` launches Chromium with ANGLE's Direct3D 11 backend, which exists only on Windows. After boot the script asks the game canvas's own WebGL context which renderer drew it and refuses a frame from any other, because Chromium falls back to SwiftShader on its own when its GPU process fails and Direct3D falls back to WARP. It also refuses a renderer it cannot name. The rules live in `scripts/captureRasteriser.mjs`.

**Why:** step 2 of the plan is a terrain shader, and the plan's section 10 lists GPU rendering as unchecked: every capture it took was SwiftShader. The two rasterisers can differ in float precision, derivatives and texture filtering, so a shader has to be looked at on both.

**Checked:** captures of the control build (`ced7f6da`, default view, 800x600, `TICKS=1`): `gpu` was drawn by "ANGLE (NVIDIA, NVIDIA GeForce RTX 4090 (0x00002684) Direct3D11 vs_5_0 ps_5_0, D3D11)", and `swiftshader` and an unset value by SwiftShader. The unset and `swiftshader` frames differ on 0 of 480,000 pixels; `swiftshader` and `gpu` differ on 86,379 (18.00%). `RASTERISER=bogus` exits 1 naming both values.

**Gate:** `tests/scripts/captureRasteriser.test.ts`, nine cases. Four mutations, each restored after, each red on the case meant to see it: WARP no longer counted as a CPU rasteriser, `gpu` launching SwiftShader, an unnamed renderer accepted, and `gpu` accepted off Windows.

**Not checked:** Linux and macOS were not run. The test does not launch Chromium, so that the script calls the refusal is held by reading its source, and was seen working only in the captures above.
