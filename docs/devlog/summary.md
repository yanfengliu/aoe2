It generalizes because it reads only depth, normals and luminance, and because `ThreeRenderRuntime` has exactly one `renderer.render(scene, camera)` call shared by every frame path *and* the capture path, so a stylized screenshot cannot disagree with the canvas. What deliberately did not port is the sea: `WATER_TONE_RANGE = 0.55..0.88` is one game's measurement of its own water, so it ships as a generic background lane defaulting to the scene lane. The first render proved the preset is not a tuning: `normalEdgeScale: 2.4` cost **23% of the frame's brightness** (L 90.1 → 69.8), because voxel geometry has no creases to find — every face junction is exactly 90°, so the turn is exactly 1.0 at every cube edge and any scale ≥1 inks all of them. The obvious suspect was the linear/sRGB round trip; a pass-through capture reproduced the baseline at **L=90.2 vs 90.1** and ruled it out in one measurement. Silhouettes alone still landed *below* baseline (L=86.8) because flattening tone does nothing to chroma, so gamut-safe `saturation`/`brightness` were added to the pass — final **L=96.9**, brighter than the original despite the ink. Painted remains selectable and is the absence of the pass, not a configured-off pass. Style is a display preference: persisted per player, never in a save, falling back to the default when a stored id no longer exists. Multi-CLI review then found seventeen defects (Codex out of quota; a second Claude carried its lens), four of them real: an unrestored render target on a throw, metrics collapsing to the resolve quad, an inert shadow-map suppression, and **ink blended in the wrong colour space** — which means this game's look had been tuned against an accidentally darker line than it asked for. Fixing that moved the shipped frame to **L=100.8**; re-inspected at 3x and `inkStrength` left alone. Also fixed here: `setArtStyle` recorded its id before the swap that can throw, and the menu row had no tests at all. The browser gate then caught two things no unit test could: a focus-trap assertion that hardcoded whichever button sat last, and a **real layout regression** — the menu panel had no height ceiling, so one extra row pushed the load form's Cancel button off a 390x560 viewport where it was neither visible nor clickable. The panel scrolls now. Evidence: before/after/diff artifacts, HUD panel interiors pixel-identical (worst channel-sum delta 3 of 3444 px; selection panel exactly 0).
