## Ground depth-only prepass: reject as redundant in current C

The proposed premise needs correction: current ground is **renderOrder 0**, not 2. `aoeDeGround.ts:143–157` creates a default MeshLambertMaterial and Mesh without assigning renderOrder. `aoeVoxelWorldRenderer.ts:120–141,169–174` constructs that ground before creating the runtime. The rejected experiment record explicitly says candidate order1 moved ground LAST and changed pixels (`primary/docs/work/133_branch-completion/snapshots/ground-experiment.md:7–21`); it must not be retried.

Actual installed Three bytes establish the current order: `node_modules/three/build/three.core.js:12062` defaults Object3D.renderOrder to0; `:20518` monotonically assigns material.id. `three.module.js:8112–8137` sorts opaque objects by groupOrder, renderOrder, then material.id, before z. All current runtime Groups/meshes retain order0 (`node_modules/voxel/dist/three/runtimePresentationSurface.js:63–71`; `instanceBatchPresenter.js:238–252`). Presenter materials are constructed later on reconcile (`materialPresenter.js:2–27,59`; `runtimePresentationSurface.js:92–101`); this repo's only directly constructed Three material is the earlier ground Lambert material. Therefore the ground colour/depth draw already precedes opaque voxel materials in the current Natural path. This is a source-order deduction, not a newly captured draw trace.

Natural selects no resolve pass (`src/rendering/artStyles.ts:181–188`). The public runtime takes one direct renderer.render (`node_modules/voxel/dist/three/runtimeStylizedResolve.js:54–60`; `ThreeRenderRuntime.js:839–843`). Three draws opaque before transparent (`three.module.js:17943–17958`), so a same-scene ground depth twin would duplicate an existing early ground depth write; it would not make ground depth available any earlier to opaque voxel fragments. A separate renderer.render before the runtime draw would also face the renderer's default autoClearDepth=true (`three/src/renderers/WebGLRenderer.js:198–216`) and must not silently add a different clear/pass lifecycle.

The ground's coverage is uncomplicated: five quads, ten triangles, top y=0 plus four slab sides y=-1..0, CCW outward, same geometry bounds (`aoeDeGround.ts:41–69`). Its splice only exports world position/normal after the unchanged built-in position projection and later multiplies diffuseColor.rgb; it never changes gl_Position, opacity, gl_FragDepth or discard (`aoeDeGroundShader.ts:40–48,270–275,300–315`). Even unexplored black ground is opaque and writes depth. MeshLambertMaterial inherits FrontSide, LessEqualDepth, depthTest/write=true, alphaTest=0, no clipping planes, polygonOffset=false and stencilWrite=false (`three/src/materials/Material.js:87,123,210–230,298–331,374,476`). The current renderer requests ordinary depth with no reverse-depth option; its clipping planes default empty. The unused log-depth chunk is conditional, not proof that ground writes a custom depth.

An identical-depth clone could in principle preserve final colour: use exactly the same positions/model-view/projection/front-side/coverage, write depth only, retain original ground colour ordering and LessEqualDepth. Strictly behind fragments are already hidden; equal-depth opaque fragments still pass and their existing colour order must be retained. EqualDepth or LessDepth substitutions, a y bias/polygon offset, changed culling/clipping/MSAA, different vertex arithmetic, omitted slab sides, or treating black ground as a discard would invalidate that equivalence. A cheaper material is not automatically bit-identical in depth across shader programs. These are real correctness hazards, but solving them still leaves **zero additional opaque occlusion** under C's existing early ground draw.

Expected useful work removed by the proposed ground-only prepass: none established; it adds one mesh submission/ten triangles and another raster/depth coverage pass. It does not reduce ground colour texture work behind later opaque objects, because its own depth is equal rather than the nearer objects' depth. Reordering the colour pass or adding an all-opaque prepass is a different mechanism and outside this bounded route. Cheapest honest discriminator has already been met by tracing actual material construction and installed sort rules; no performance experiment is justified for this redundant ground prepass. A future host override that changes ordering would require a fresh source/draw-order audit rather than inheriting this conclusion.

## One simpler local alternative: FrontSide-only shadow material

**Conditionally plausible exact candidate; performance unproved and probably a small saving.** The sole proposed local change would be the shadow resource's `doubleSided:true` to false (`src/rendering/voxel/aoeVoxelResources.ts:81–86`). It is already unlit/transparent with opacity0.22. The existing public resource maps this to Three MeshBasicMaterial and FrontSide/DoubleSide (`node_modules/voxel/dist/three/materialPresenter.js:2–27`), so no runtime feature or sibling edit is needed. Nothing is implemented here.

Current Three actually renders transparent DoubleSide with forceSinglePass=false in **two submissions**, BackSide then FrontSide (`three.module.js:18127–18141`; `three/src/materials/Material.js:430`). One shadow wedge has exactly one indexed flat triangle, not a prism (`aoeVoxelShadowWedge.ts:27–43`). Thus the late baseline's1260 shadow slots contribute2520 submitted triangles, not1260 distinct translucent faces. This matches the measured triangle reduction arithmetic above. A FrontSide resource retains the existing FrontSide program/pass and omits its BackSide predecessor; instance order, shadow heights and depth comparisons need not change.

Winding proof from production sources: `silhouetteTriangles` defines wx,wz unit length (fallback1,0), ux=-wz, uz=wx, so the (u,w)->(x,z) basis determinant is-1 (`aoeVoxelShadowTiling.ts:171–180`). Strips have ascending u with u1-u0>=1e-9 (`:227–233`) and hi>=lo, including clamped clip endpoints (`:274–290`). Its two triangle forms `[a,b,c]` and `[a,c,d]` have strictly positive signed area in (u,w) when emitted; zero-height ends are skipped (`:316–326`). Therefore signed area in world(x,z) is negative and the world 3D cross product points **upward**. `shadowTrianglePart` sets axes Q-P,R-P and center(Q+R)/2 without reversing vertices (`aoeVoxelCastShadows.ts:230–260`); `matrixForPart` directly uses those axes (`aoeVoxelRecipeTypes.ts:219–227`). The local downward wedge winding is flipped by that instance basis, yielding exactly the upward world triangle.

All production shadow-surface creation comes through this tiling path; no other source creates shadow parts. The shadow lane explicitly removes animation (`aoeVoxelLaneBatches.ts:228–234`), unit/wildlife pose paths skip shadow parts, and overlap repair only raises their y (`aoeVoxelCastShadows.ts:145–199`). Runtime roots remain identity Groups. Three chooses front-face reversal from object.matrixWorld only, not from the per-instance determinant (`three.module.js:17182`); the actual transformed upward winding is therefore what culling sees. The game's camera conversion fixes center.y=0 (`aoeCameraSync.ts:18–23`), and installed `orthographicView.js:78–98` sets a positive30-degree pitch from32/64 with a downward view direction. Pan/positive zoom do not turn the camera under the triangles. Under those current contracts, the BackSide submission has no covered fragments and its removal should leave the existing FrontSide draw's exact colour/depth/blending order intact.

Important disqualifiers: arbitrary reversed triangles passed directly to the exported helper are not covered by the production tiling proof; neither are a tilted/rotated/negative-scale runtime root, below-plane/borrowed camera, future non-flat geometry, animated shadow matrix, mixed winding or Float32/clip precision that actually flips a nondegenerate rasterized triangle. Normals [0,1,0] alone do not prove winding. FrontSide correctness must be checked after actual Float32 transforms and camera projection. Moebius uses a normal override pass (`node_modules/voxel/dist/three/stylizedResolvePass.js:237,346–373`), so a product resource change would require both styles' maintained picture checks rather than extrapolating Natural. No exact-pixel claim is made from this algebra alone.

Expected saving if the winding proof survives: for visible shadow batch, one culled-side submission and its vertex/state/program work—774 submitted triangles at opening base and1260 at late base, reducing13->12 and14->13 draw calls respectively. At late base that is5.58% of22582 submitted triangles, and the removed pass already shades no visible fragments. Ground, opaque, animated119, front-facing shadow fragments, memory, instance capacities and adapter/simulation work remain. The empty-corner shadow batch is already frustum-culled, so it cannot gain this submission saving. The source and current counters do **not** support claiming the roughly17% late live-frame improvement needed by the original software target, nor a20% static win. Avoid spending on host lifecycle machinery for this simple material question.
