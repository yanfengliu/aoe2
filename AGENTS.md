# AGENTS.md — aoe2

## What this is

An AoE2-style RTS in TypeScript, built on the sibling `civ-engine` repo. Spec-driven: `design/spec-final.md` plus `design/stats/` is the authoritative game definition — kept complete enough that an agent can implement and iterate the whole game from it without further user clarification.

This repo's own rules live in [docs/policies/local-rules.md](docs/policies/local-rules.md). They add repository constraints consistent with the Fleet Orchestration Policy below.

### Fleet Orchestration Policy

Deliver the requested outcome with verified correctness, coherent architecture and minimal necessary complexity. Optimize useful progress, not agent count, code volume or maximum reasoning. Adapt rigor to risk. This policy grants no new permissions or capabilities. [R1]

**Roles.** Only an explicitly designated agent coordinates; each scope has one accountable integration owner. The coordinator owns planning, dependencies, shared interfaces, architectural consistency, integration and acceptance. It reads only what assignments, acceptance or its own trivial change need, accepts or rejects inspected handoffs, and delegates all but trivial changes that cost more to delegate (owner directive, 2026-09-23, superseding 2026-09-05). Trivial means at most about 20 changed lines of docs, config or an integration fix, no R10 high-risk change, product logic, migration, security or trust-boundary code; the same gates, review and worktree rules apply. [R2]

Workers own bounded outcomes and local implementation decisions. Each worker, reviewers included, chooses and dispatches its subagents within budget: none for a small task, while remaining accountable for their work (owner directive, 2026-09-23). Threads follow deliverables, not permanent departments; no recursive manager hierarchies. [R3]

**Plan and delegate.** Inspect instructions, code, docs, tree state and active tasks; set outcome, non-goals, acceptance criteria, dependencies and verification; settle ambiguity with evidence and reversible defaults. Use the simplest delegation: subagents for bounded investigation, independent judgment or localized changes, separate threads for substantial independent changes. Agree shared contracts before parallel work; no duplicate or blocked work. Assignments name owner, outcome, context, dependencies, contracts, base revision, workspace, scope and exclusions, verification, resource limits, handoff, and read-only or implementation. Change model and reasoning defaults only through supported controls, on evidence. [R4]

Size the team continuously (owner directive, 2026-09-15): widen when one worker holds the critical path and independent work waits; narrow when workers contend for files, ports or CPU. Account for shared services, databases, ports and compute: serialize same-file edits in one tree, duplicate gates and unshareable resources. Run one expensive gate at a time; choose other work around it. [R5]

**Session size** (owner directives, 2026-09-23 and 2026-10-22). Sessions run long: take new requests as separate assignments in the same session, and never hand off to a successor session to shed context; auto-compaction carries the session. Split tasks expected to exceed about 200k context tokens into milestones within that budget, each committed and merged to main once green. Milestones are task boundaries; harness compaction never justifies wrapping up or handing off. No unattended "don't stop until done" loop without milestone commits. Mechanical subagents use lower effort or a smaller model; reviews and their subagents keep the review runbook's pins. Per-item model calls are one-shot, never full agent sessions. [R6]

**Coordinate safely.** Use available capabilities; assume no visibility into other chats, shared memory, automatic messaging, workspace isolation or persistent monitoring. If spawning is unavailable, work directly or hand off explicitly. Beyond a trivial read, each session or agent defaults to its own worktree to isolate concurrent edits. Serialize overlapping writes only when no worktree is available, and say why. Finish each bounded increment in its session: merge to main, push, then `git worktree remove`. Remove completed task-owned branches and unneeded temporary files; explicitly transfer ownership and locations of still-needed resources. Report any merged worktree left and its location as a defect. Never overwrite or discard another participant's work. Track delegation to completion, cancellation or handoff; release only owned resources without losing work. On resumption, first inspect surviving worktrees, artifacts and task status; recover what exists and preserve unfinished work, assuming no worktree, transcript or shared memory survived until checked. [R7]

**Preserve state and decision boundaries.** Store owners, dependencies, revisions, status, blockers and consequential decisions in the repo or tracker; reuse conventions and keep only useful docs. The coordinator updates canonical todos and progress from workers, revisiting goals, remaining work, dependencies, blockers and acceptance criteria. Periodically spawn a fresh subagent to review the whole effort for fundamental flaws, unnecessary detail, hard problems or loops; reassess from its findings. Propagate contract changes; revalidate stale information. Distinguish requirements from behavior, prepared from dispatched work, observations from assumptions, and implemented, verified, reviewed, integrated and blocked work. At handoff or interruption preserve goals, acceptance criteria, todos, owners, resource locations, outcomes, revisions, checks, results, evidence, risks, blockers, decisions, open issues, next steps and integration needs, excluding secrets and needless private data. A successor maintains canonical todos with status, owners and dependencies and any active goal's objective, status, progress and remaining limits through supported controls; never reset consumed allowances. Workers act autonomously in scope; escalate cross-task interfaces, persistent formats, security boundaries, major dependencies and scope changes to the coordinator for resolution within the approved mandate. Unapproved major architecture or product changes and consequential external actions need human authorization. [R8]

**Implement and verify.** Inspect, implement a coherent increment, check, diagnose, fix, recheck. Preserve architecture; no unrelated rewrites, speculative abstractions or unnecessary dependencies. Implement when requested. Use task-appropriate evidence and baselines; inspect real user flows in interactive products. Check games' and simulations' invariants, save compatibility and realistic-scale performance; prototype uncertain ideas before generalizing. Research cites evidence and separates hypotheses, measurements and conclusions. Never weaken tests or conceal failures to claim success. Docs-only work uses content and version checks; skip runtime tests and CI waits. [R9]

During authorized work, proactively improve products and orchestration and learn from recorded outcomes; follow `../fleet/docs/skills/self-improvement/SKILL.md` within scope and budget. [R33]

Obtain independent, preferably read-only review for substantial or high-risk changes when available. Review the exact revision against acceptance criteria. Report unavailable review; fix justified findings, rerun affected checks, and obtain focused re-review when fixes invalidate earlier review. [R10]

**Integrate, report, and stop.** Reassess after two failures for one reason. Unless another budget is set or the user authorizes more, cap automatic repair at five substantive attempts, then report; explicit overrides hold for their stated scope without asking again. Keep updates brief and decision-relevant. Stop when acceptance criteria and material findings are resolved; invent no follow-up work. [R11]

**Final acceptance gate.** The integration owner integrates in dependency order and on the final integrated revision's actual changes and evidence, not worker summaries, checks every acceptance criterion, runs relevant automated checks and exercises affected end-to-end behavior and cross-task interactions. Substantial or high-risk work gets independent read-only review of the integrated changes, integration fixes included. Confirm the merge to main; report that revision, review status and every failed, skipped or unavailable check and unmet criterion. Nothing is fully verified with an open material finding or required check. [R12]

### Fleet conventions

- Repository rules add local constraints consistent with this policy; they cannot override its permissions, adaptive workflow or stopping limits. [R13]
- Gates pass before any commit touching code; dependency changes rerun the audit gate. The user's standing grant covers committing, merging to main and pushing in every repo they own; force-pushing, rewriting history, deploying and publishing still need authorization. Work is done only once merged to main, regardless of green branch or worktree gates; report unmerged work's location. [R14]
- After executable changes, follow available remote gates to completion; inspect steps and runner before blaming code. Report unavailable verification and local bounds; fix blocking failures within the repair budget and report unrelated ones without expanding scope. [R15]
- For substantial or high-risk changes, use independent review when available. High-risk includes persistence and migrations, security and auth, concurrency, money, supply chain, and executable changes in sibling repos; `../fleet/docs/skills/multi-cli-review.md` provides the review mechanics. [R10]
- Inspect rendered visual work; work without a visual surface runs headlessly. Cover 3D with ample fixed angles and zooms for comparison and randomized angles for exploration; leave room for surprises. Cover 2D and artwork at relevant viewport sizes, scales and states, interactive work through real controls and representative flows over time, static assets from their viewpoints. Use headless when adequate, visible only when needed. Aggregate views establish presence, not correctness: inspect each item at native resolution and bind review to the inspected bytes' digest. Check affected flows and surroundings for material regressions. Direct state-setting does not verify the controls or skipped input path. [R16]
- Record every user-reported defect in `docs/learning/defect-register.md`: the user's symptom, investigation, root cause and how it is checked. Add a check for the whole defect class; retain the entry after its gate lands. [R17]
- Read `docs/learning/lessons.md` at session start. Record lessons there the session learned; each names its retiring gate and is deleted in the commit landing it. A gate counts only after going red with the defect reintroduced, following `../fleet/docs/lessons-template.md`. [R18]
- Gates prove nothing beyond their bounds: name the bound in the header and pin every reproducing input. Distinguish passed from did-not-run; a check built from its checked symbol proves only self-agreement. [R19]
- Verify outcomes beyond exit status, red or green, and return values: read the artifact that should have changed. Retest inherited blockers before repeating them. [R20]
- Verify instruments before trusting measurements: flags took effect, the denominator is intended, the control reproduces and relied-on claims remain true. Hold the tree still between A/B arms. Ask the repo's debugging instrument first; the first probe names it or explains why none answers. Enforce applicable rules when writing a probe. [R21]
- Identify and fix slowness on the critical path (owner directive, 2026-09-15). Keep only slowness the verdict requires: the expensive gate the team is sized around. [R22]
- Keep task-run evidence only under ignored paths; delete it when no active task, unresolved issue or handoff needs it. It enters Git only after review promotes it to a repository input. Tracked docs retain plans, authored reviews, conclusions and provenance. Promoted blobs over 256 KiB need a stated reason; over 512 KiB binary or 1 MiB of anything never enter ordinary Git. Asset stores or LFS need user approval. [R23]
- Keep plans and every authored review round in permanent `docs/work/<id>_<theme>/` folders (`../fleet/docs/work-docs.md`). Record history, not status: a dated devlog line per behaviour-changing session in `docs/devlog/summary.md` (`../fleet/docs/devlog-template.md`). [R24]
- Use common words with the same meaning in chat, docs, commits, PRs, comments and errors. One idea per sentence unless a rule needs more. Cut length, not facts: keep exact terms, numbers and evidence. Quotes and pastes are exempt; do not copy this canon's style. One line per paragraph, no hard wrapping. When expanding skills, agent instructions or rules, merge overlaps, tighten wording, set a line budget and actively seek cuts; consider one-in, one-out. Justify necessary growth. [R25]
- Check error messages across the affected class and adjacent paths. Each names what happened, which input caused it and what would satisfy it, never bare `Validation failed`. [R26]
- When blocked, immediately hand over the redacted artifact with the named blocker, before analysis; continue safe independent work. [R27]
- Repos choose their language and toolchain (Node, Python and Rust run here), pin versions where tooling reads them and name them in Gates. Node baseline is 24; older majors need a CI job proving them. [R28]
- Runtime model calls, vision included, are authorized and paid for. Reviewer model pins live only in `../fleet/docs/skills/multi-cli-review.md`; every model a product calls is pinned in its calling repo. No model IDs are hardcoded elsewhere. [R29]
- Standing loops source tasks by running the artifact as its user does, with its default entry point and real configuration, never by reading code for improvements. No runnable entry point means no standing loop. [R30]
- Directions that outlive a task land that session in `../fleet/FLEET.md` if fleet-wide, otherwise the repo's `docs/policies/local-rules.md`; report where. [R31]
- When a hard problem blocks progress, run the search in `../fleet/docs/skills/hard-problem.md`. [R32]

## Gates

`npm run verify` is THE gate: `content:validate && test && typecheck && test:browser && lint && build`, chained with `&&` between `node scripts/verify-receipt.mjs start` and `write`. Its EXIT CODE says whether every stage exited 0 and both test suites reported a whole, passing run; a landing reads `node scripts/verify-receipt.mjs check` instead, because a run cut short through WMI exits 0 (register, 2026-10-11). Run it before every code commit. Reading a summary line out of a piped run is not running the gate — `npm test | tail` reports zero while the suite is red, and a look-alike summary has twice been quoted as green over a failing run. Only affected tests while iterating. Dependency audit gate: `npm audit --audit-level=high` (full tree and `--omit=dev`).

## Session start

Run `npm run ci:status` FIRST — it prints main's remote CI and playtest-corpus conclusions and exits non-zero when either is red, or when a red attempt or run on the tip is followed by a re-run or a later run, finished or still going (it names the job and step that failed first). A red remote gate is the next task, ahead of whatever was planned. (This is a command because the intention was not enough: main's CI ran red for 200 consecutive runs over two months behind green local gates — see the 2026-08-29 defect-register entry.) Then read `docs/learning/lessons.md` (short by construction — every entry names the gate that will retire it), `docs/devlog/summary.md` and `docs/architecture/ARCHITECTURE.md` before starting work.

## Invariants & boundaries

- `design/spec-final.md` is authoritative. Persist every user-described rule, mechanic, content change, UX expectation, or constraint into it as part of the same task — a task is not done until the spec reflects the rule, and the spec must stay internally consistent (edit conflicting language rather than letting two rules coexist). (Established 2026-05-08 — a complete spec is what enables autonomous iteration.)
- Do not modify the `civ-engine` repo. If a missing engine feature blocks the task, report the blocker and continue safe independent work within scope.
- Record engine weaknesses in `docs/engine-feedback/current.md` as you work (history in `docs/engine-feedback/past.md`); before writing, audit the current file's freshness and prune stale or already-addressed items.
- Stay current with civ-engine: when the engine ships an update, check `../civ-engine/docs/changelog.md`, keep the CI engine-dist chain green (it fetches civ-engine's prebuilt tarball — engine must be green and pushed first), adapt call sites, and re-run the gates before other work. Convenience trigger: the repo-scoped `check-engine` command.
- The playtest LLM model policy — one model for every harness call, the current pin, and the wholesale-swap procedure — is governed by `design/spec-final.md` §15.7; never bump the playtest pin anywhere else.
- File size: 500 LOC cap per file, enforced by `tests/architecture/fileSizeBudget.test.ts` (legacy violators grandfathered there with shrink-only caps; split by lifecycle/role and delete the entry).
- TDD for behavior changes: tests first, testing the contract (app experience and mechanisms), not the code.
- A visual change is not verified until a before screenshot, the change, an after screenshot, and a pixel diff exist alongside the normal gates, and the diff shows the delta confined to the region the change was meant to touch. `scripts/captureMapScreenshot.mjs` + `scripts/diffMapScreenshots.mjs` are the maintained pair (`SEED`/`LABEL` env vars reach any scenario); one-off capture scripts are not.
- Playtest runs and observation tools report; they never generate or apply product fixes or touch Git. The manually invoked `playtest:canary` developer drill is a retained exception: it temporarily applies a checked-in seeded bug and restores its clean baseline. It measures oracle sensitivity, never selects or ships a fix. (The automated fix arm was removed 2026-08-01 — see `docs/architecture/decisions.md`.)

## Conventions

- Devlog: `docs/devlog/summary.md` (one line per task; compact past 50 lines — no cheating with mega-lines) + `docs/devlog/detailed/START_DATE_END_DATE.md` (per-task entry: timestamp, action, reviewer findings by provider/theme, result, reasoning, notes; archive via `git mv` when the active file passes 500 lines, starting a new file dated today).
- Changelog `docs/changelog.md` + `package.json` version: user-visible changes only (external audience; migration focus). Bump `c` per non-breaking change, `b` (reset `c`) per breaking change, `a` only when the user says so; one bump per coherent shipped change; pure refactors/doc sweeps bump nothing.
- Architecture: structural changes update `docs/architecture/ARCHITECTURE.md` and append a row to `docs/architecture/drift-log.md`; non-obvious tradeoffs append to `docs/architecture/decisions.md` (append-only — supersede, never delete). Non-structural fixes touch none of these.
- Debugging: one file per session, copied from `docs/debugging/template.md`, which owns the copy-and-cleanup mechanics; when a later session invalidates an old conclusion, update that old doc rather than leaving it to mislead. An existing instrument comes FIRST, before any probe of your own — the rule stands, and the three tools this bullet used to name were each wrong in a different way, so they are corrected below rather than repeated. What exists, and the question each answers: `bundleHotspots(bundle)` — which ticks are worth looking at (tick failures, execution failures, duration outliers, markers); it is pure and builds no world, so it goes first in a triage. `snapshotAtTick(bundle, tick)` — world state at any recorded tick, folded from the nearest snapshot with ZERO World construction and no game code; the cheapest ground truth there is. `npm run replay:inspect -- <bundle> --ticks a,b,c` — THIS repo's own script (`scripts/replay-inspect.mjs`), not an engine capability: it wraps `SessionReplayer` with an aoe2 world factory to print aoe2-shaped per-owner rows (record a bundle with `npm run playtest -- --all-ai --max-ticks N`). `diffBundles` and `SessionReplayer.forkAt` — two recorded runs compared structurally, which is what an A/B is. `SessionReplayer.selfCheck()` — whether the recording is deterministic, asked BEFORE trusting anything read off it. `WorldHistoryRecorder` with `summarizeWorldHistoryRange` — records and folds a LIVE world with no bundle at all, so "no bundle exists for this configuration" is not a reason to hand-roll a probe. `createVisibilityDebugProbe(key, visibility)` on `WorldDebugger` — takes a `VisibilityMap`, which this repo does build (`simulation/createSimulationBridge.ts:84`), so unlike the two probes below it is type-compatible and will attach; the map is a local in the bridge factory with no accessor on the bridge, so reaching it costs a one-line export, not a redesign. `npm run ai:tick-ab -- <scenario> <treeA> <treeB>` answers whether equal simulated work costs more in one tree, interleaving both in one process with digests and foreign load; `scripts/profile-selfplay.mjs --config castle|lab` reports self/inclusive CPU shares on the gate's match, with `--players`, `--save` and `--load` for equal-world comparisons. And civ-engine ships a read-only MCP server (`../civ-engine/mcp`, `node mcp/dist/cli.js --corpus <dir>`): 14 tools over a bundle corpus, conversational, constructs no world. Two engine probes do NOT serve this repo and no doc should send you to them again: `createOccupancyDebugProbe` takes an `OccupancyGrid`, and this repo holds an `OccupancyBinding` whose grid is `private` with no accessor, so it does not attach — and its payload is eight scalars (a width, a height, a version and five counts), so even attached it counts cells and names no cell and no entity; `createPathQueueDebugProbe` wants a `getStats(): PathRequestQueueStats`, and movement here is synchronous `findGridPath` plus a local cache with no queue anywhere, so it does not apply at all. Who is blocking whom is answered by `bridge.getDebugSnapshot()` — `coarseVsFine` carries every unit's cell and sub-cell position and `unitPaths` its current move target — which is what the freeze investigation actually used. Every scratch probe under `tmp/probes/` carries a `// harness:` line naming the tool that answers its question, or `none` with the reason (a question about which cell a unit chose lives in bridge closure state that a replay re-simulates from a snapshot, so only the live bridge answers it); the hook in `.claude/settings.json` refuses to write or run a probe without that line. The rule was skipped twice as prose alone (2026-06-13, 2026-09-05); the tools it named were audited on 2026-09-06 and the asks that came out of that are in `docs/engine-feedback/current.md`.
- New work records: plans and every authored review round use permanent `docs/work/<id>_<theme>/` folders and the common fleet allocator. `plan.md` owns current status and shipping outcomes. During the bounded September 29 historical migration, active legacy threads retain the closure and freshness rule below; imported active wrappers and their owner threads are updated together. See `docs/policies/local-rules.md` for the verified migration boundary.
- Review threads: syntheses land in `docs/threads/current/<objective>/<date>/<n>/REVIEW.md` (synthesis only — no raw CLI output; temp captures go to gitignored `tmp/review-runs/`); `DESIGN.md`/`PLAN.md` live at the objective root. A thread closes in the commit that ships or drops its objective, never in a later sweep: `git mv` it to `docs/threads/done/`, add a closure line under the title (`Closed YYYY-MM-DD: <version or decision>`), fix every pointer to the old path, and give each leftover a home (the lessons queue, the register, or an explicit drop with its reason). Every task ends with a look at `docs/threads/current`: a thread the task advanced gets a dated status line (what moved, what is still open); one whose objective has shipped or been dropped is moved. `tests/architecture/threadHygiene.test.ts` fails on a stale thread pointer in code, tests, scripts, the spec and the architecture, policy and learning docs, on a `Closed YYYY-MM-DD:` line still under `current/`, and on a current thread with no date in the last 30 days of commit time — the last of those is a tail, not the rule: a thread closed without its closure line is caught only after 30 days. The rule and its evidence are in `docs/policies/local-rules.md`. Archived threads carry synthesis only — strip any `raw/` when moving to `done/` (raw has zero downstream reuse; the `REVIEW.md` is the durable, cited record).
- Canonical doc surfaces are README, ARCHITECTURE + decisions + drift-log, devlogs, and changelog. There is deliberately no `docs/api-reference.md` or guides tree — TypeScript types (e.g. `SimulationBridge` in `src/game/simulation/createSimulationBridge.ts`) are the API reference.
